The VFS and the page cache

Lesson 1 covered the calls a program makes. Lessons 2 to 4 covered the blocks and trees on the disk. This lesson covers the kernel layer between them: how a read() finds the right filesystem, and why most reads and writes never touch the disk at all.

The VFS: a common interface and shared caches

Every filesystem call a program makes lands in the same kernel subsystem first: the Virtual File System, or VFS.1 It has two jobs.

  1. Dispatch. The VFS owns the generic parts of every file operation: looking up the file descriptor, checking permissions, walking path names, keeping the file offset. When it needs something only a specific filesystem knows, such as how to find block 7 of a file, it calls that filesystem through a table of function pointers.2
  2. Caching. The VFS and the memory manager keep three big caches that every filesystem shares: the dentry cache (names), the inode cache (file metadata) and the page cache (file contents). A filesystem driver fills them on a miss. On a hit, the driver is often not called at all.34

Because of the first job, ext4, XFS, btrfs, tmpfs, procfs, NFS and FUSE all look the same to cat. Because of the second job, a warm read() costs a memory copy, while a cold one costs a trip to the device that can be a thousand times slower.5

Key idea

The VFS is the place where "a file" stops being the program's idea and becomes a filesystem's data structures. Everything above it is generic; everything below it is specific to one filesystem or one device.

The four VFS objects and their operations

The VFS models every mounted filesystem with four kinds of in-memory object. Each has a pointer to a table of functions that the filesystem supplies. In C this is the usual way to get polymorphism: a struct full of function pointers, filled in once per filesystem type.

ObjectRepresentsLivesIts operations
struct super_blockone mounted filesystem instance: block size, root, device, list of inodesfrom mount to unmountsuper_operations: alloc_inode, write_inode, evict_inode, sync_fs, statfs, put_super6
struct inodeone file or directory: i_ino, i_mode, i_size, timestamps, link countwhile anything refers to it, then in the inode cache until reclaimedinode_operations: lookup, create, mkdir, unlink, rename, setattr, getattr, permission7
struct dentryone name in one directory, linking that name to an inode (or to nothing)in the dentry cache until reclaimeddentry_operations: d_revalidate, d_hash, d_compare, d_release8
struct fileone open file description: offset f_pos, flags, access modefrom open() to the last close()file_operations: read_iter, write_iter, llseek, fsync, open, release, unlocked_ioctl, fallocate910

A fifth table matters as much as the four above. Each inode has an i_mapping pointer to a struct address_space: the page cache for that file. Its address_space_operations are how the generic page cache code asks a filesystem to move data between memory and disk: read_folio, readahead, writepages, dirty_folio, write_begin, write_end, direct_IO, release_folio.1112

The struct file is the open file description from lesson 1. The number your program holds is an index into the process's fd table, and that slot points at a struct file. The in-memory struct inode is built from the on-disk inode you decoded by hand in lesson 3. Filesystems usually wrap it in a bigger struct of their own; ext4 embeds it inside struct ext4_inode_info and gets back to the wrapper with the EXT4_I() macro, which is container_of() underneath.13

Here is ext4's file table, exactly as it appears in fs/ext4/file.c in Linux 6.18 (one #ifdef removed):14

const struct file_operations ext4_file_operations = {
	.llseek		= ext4_llseek,
	.read_iter	= ext4_file_read_iter,
	.write_iter	= ext4_file_write_iter,
	.iopoll		= iocb_bio_iopoll,
	.unlocked_ioctl = ext4_ioctl,
	.mmap_prepare	= ext4_file_mmap_prepare,
	.open		= ext4_file_open,
	.release	= ext4_release_file,
	.fsync		= ext4_sync_file,
	.get_unmapped_area = thp_get_unmapped_area,
	.splice_read	= ext4_file_splice_read,
	.splice_write	= iter_file_splice_write,
	.fallocate	= ext4_fallocate,
	...
};

When the VFS wants to read from an ext4 file, it calls file->f_op->read_iter(...), and the pointer leads to ext4_file_read_iter. An NFS file's f_op points at nfs_file_operations instead, and the same call reaches the NFS client.15 Nothing above this line changes.

Mounts: struct mount and mount points

A mount attaches a filesystem's root to a directory of an already-mounted filesystem. The kernel records each one as a struct mount (with an embedded struct vfsmount) that says: at this dentry on that parent mount, continue in this other super_block.16 During a path walk, whenever the kernel reaches a dentry flagged as a mount point, it looks up the mount table and jumps to the root of the mounted filesystem.17

Every process sees the mount table of its mount namespace. Containers get their own namespace, which is why a container can have a different /.18 You can read your view of the table in /proc/self/mountinfo, or more readably with findmnt:19

$ findmnt -n -o SOURCE,FSTYPE,OPTIONS /
/dev/sdd ext4   rw,relatime,discard,errors=remount-ro,data=ordered

That line from this machine names the block device (/dev/sdd, lesson 2), the filesystem type whose operation tables will be used (ext4), and mount options that change behaviour inside those tables. data=ordered is the ext4 journaling mode from lesson 3.20 relatime limits how often a read updates the access time, because every access-time update is a metadata write.21

The dentry cache and the inode cache

In lesson 3 you resolved a path by hand: read the root inode, read its directory blocks, find the name, read the next inode, and repeat. Doing that for every open() would mean several disk reads per call. The kernel avoids it with the dentry cache (dcache).3

A dentry caches the answer to one question: in directory P, what does the name N refer to? The dcache is a hash table keyed by the pair (pointer to the parent dentry, hash of the name).22 A path walk for /home/artem/notes.txt becomes three hash lookups: ("/", "home"), then (home, "artem"), then (artem, "notes.txt"). Only a miss calls the filesystem's inode_operations->lookup, which reads the directory from disk and adds a new dentry.7

  • A positive dentry points at an inode.
  • A negative dentry records that a name does not exist. When a shell searches $PATH for a command, or a compiler probes twenty include directories for stdio.h, most of those lookups fail. Negative dentries make the second failure free.23
  • Unused dentries stay on an LRU list and are freed when memory is needed. Any dentry can be rebuilt from disk, so dropping one is always safe.323

Most lookups also avoid locks. The kernel first tries an RCU walk: it walks the dentries without taking reference counts or locks, and checks sequence counters at the end to make sure nothing changed underneath it. If something did change, or a dentry is missing, it falls back to the slower ref walk, which takes references step by step.24 This is why stat() on a hot path scales well on machines with many cores.

The inode cache holds the in-memory inodes that dentries point to, hashed by (super_block, inode number).25 A dentry holds a reference on its inode, so a cached name keeps its inode cached too.7 You can see both caches on this machine:

$ cat /proc/sys/fs/dentry-state     # nr_dentry nr_unused age_limit want_pages nr_negative dummy
423361	382943	45	0	107134	0
$ cat /proc/sys/fs/inode-nr         # nr_inodes nr_free_inodes
408281	51650

About 423,000 dentries, of which 107,000 are negative: the system remembers 107,000 names that do not exist. Most dentries are unused (nobody has the file open) and are kept only because the memory is otherwise idle.23

The read() path through the kernel

Now follow one call, read(fd, buf, 4096) on an ext4 file, through the kernel. These are the function names in Linux 6.18.2627 Names in this area change every few years (folios replaced pages in many of them), so check the source of the kernel you run.28

read(fd, buf, 4096)                                  user space
└ SYSCALL_DEFINE3(read) → ksys_read()                fs/read_write.c: fd → struct file
  └ vfs_read()                                       checks mode, range, then dispatches
    └ new_sync_read()                                wraps buf in a kiocb + iov_iter
      └ file->f_op->read_iter() = ext4_file_read_iter()   fs/ext4/file.c
        └ generic_file_read_iter()                   mm/filemap.c (O_DIRECT goes elsewhere)
          └ filemap_read()
            ├ filemap_get_pages()
            │ ├ filemap_get_read_batch()             look the page indexes up in the XArray
            │ ├ page_cache_sync_ra()                 miss: start readahead (mm/readahead.c)
            │ │ └ … read_pages() → a_ops->readahead() = ext4_readahead()
            │ │       └ ext4_mpage_readpages()       extent lookup, build bios, submit_bio()
            │ ├ filemap_readahead()                  hit a folio marked PG_readahead: read further ahead
            │ └ filemap_update_page()                folio present but not filled: a_ops->read_folio()
            └ copy_folio_to_iter()                   copy the bytes into buf, advance f_pos

Two things stand out. First, ext4's own code appears at only two points: the entry (ext4_file_read_iter) and the miss path (ext4_readahead, which uses the extent tree from lesson 4 to turn file block numbers into disk block numbers).2930 Everything else is generic page cache code that every disk filesystem shares. Second, on a cache hit the device is never touched: the call ends in a memory copy.

On a miss, the reading process sleeps. The bio goes to the block layer (lesson 2), the driver programs the device, and the device writes the data into the folio's memory by DMA. When the I/O completes, a completion callback marks the folio uptodate and unlocks it, which wakes the reader, and the copy proceeds as if it had been a hit.31

Page cache: address_space, XArray and folios

The page cache is the kernel's copy of file contents in RAM. Its shape follows from the objects above:

  • Each inode has one address_space, so each file has exactly one cache, shared by every process and every open file description.
  • Inside the address_space, the field i_pages is an XArray that maps a page index (file offset divided by 4096) to a folio.1132
  • A folio is a run of physically contiguous pages, a power of two in count, handled as one unit.33 Linux added folios in 5.16. Before that the cache was managed one 4 KiB struct page at a time.28 Large folios let a filesystem cache, say, 64 KiB of a file with one entry and one set of flags.

The XArray is a radix tree, and the design argument is the one you met for B-trees in lesson 4. Each node has 64 slots, so each level consumes 6 bits of the index.34 A 1 GiB file has 218 pages, so any page is at most three levels down (6 + 6 + 6 bits). High fanout keeps the tree shallow, and a shallow tree means few pointer chases per lookup.

Each folio carries state flags.35 The ones you will meet in this course:

FlagMeaning
uptodatethe folio's contents match (or are newer than) the file; reads can be served from it
dirtymodified in RAM and not yet written to the device
writebacka write to the device is in flight
lockedsomeone is doing I/O on it or changing it; others wait
referenced, activerecent use, consulted by reclaim
readaheadthe marker that triggers the next asynchronous readahead

File data is not the only thing cached here. Filesystem metadata that ext4 reads through the block device itself, such as bitmaps, inode table blocks and journal blocks, lives in the block device's own address_space. That is the Buffers line in /proc/meminfo.3637 Linux once had a separate "buffer cache" for disk blocks and a page cache for files, and could hold the same data twice. Since 2.4 the two are unified and there is one copy.438

free, buff/cache and MemAvailable

The page cache uses any RAM that nothing else wants. On this machine, right before running the lab:

$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       3.3Gi       1.4Gi       4.7Mi        11Gi        12Gi
Swap:          4.0Gi       608Ki       4.0Gi

Only 1.4 GiB is free, but 11 GiB is cache, and 12 GiB is available: the kernel can hand it to programs by dropping clean cached pages.3940 Read the available column, not free. Unused RAM does nothing, and RAM holding file pages makes the next read of those files fast.

Readahead

Programs usually read files from start to end. If the kernel waits for each read() to ask before fetching data, every call pays the full device latency. Readahead guesses that a sequential reader will want the next chunk and fetches it early, so the device works while the program is busy with the current chunk.

  • Synchronous readahead (page_cache_sync_ra()) runs on a miss. It reads more than was asked for. The first window rounds the request up to a power of two and, if that is small compared with the maximum, multiplies it by four.41
  • Asynchronous readahead (page_cache_async_ra()) is triggered by a marker. Inside each window the kernel flags one folio with PG_readahead. When the reader touches that folio, the kernel starts reading the next window while the current one is still being consumed.42 The window grows by four times while small, then doubles, up to the maximum.43
file:   |=====window 1=====|=========window 2=========|=================window 3================|
                     ^ PG_readahead            ^ PG_readahead
reader:  ---reads------->|  touching the marker starts window 2 while window 1 is still being read
                            touching the next marker starts window 3, and so on

The maximum is the device's read_ahead_kb.44 The kernel default is 128 KiB, and drivers can raise it.4546 This WSL virtual disk reports 8 MiB:

$ cat /sys/block/sdd/queue/read_ahead_kb
8192

Random access defeats readahead: the kernel sees the reads are not sequential and stops growing the window.47 A program can also say what it intends with posix_fadvise(): POSIX_FADV_SEQUENTIAL makes Linux use a larger window, and POSIX_FADV_RANDOM turns readahead off for that file.48

Reclaim: active and inactive LRU lists

When a program needs memory and little is free, the kernel reclaims pages. It keeps cached pages on LRU lists (least recently used), separately for file pages and anonymous memory (heap and stack), and separately per memory cgroup and NUMA node.4950

  • A newly cached folio enters the inactive list. If it is accessed again while still there, it is promoted to the active list. A single sequential scan of a huge file therefore fills the inactive list and ages out without pushing the truly hot data off the active list.51
  • Reclaim scans from the old end of the inactive list. A clean file folio is the cheapest thing to reclaim: the disk already has the same data, so the kernel just drops it. A dirty folio must be written back first. Anonymous memory must go to swap.52
  • The kernel thread kswapd reclaims in the background when free memory falls below a watermark. If a program allocates faster than that, the allocating program does direct reclaim itself, which shows up as a latency spike in that program.52

Since Linux 6.1 there is also a multi-generational LRU (MGLRU), which sorts pages into several age generations instead of two lists.5354 Some distributions enable it by default.5556 The idea is the same: drop what has not been used for longest, prefer clean file pages.

To empty the cache for an experiment, root can write to /proc/sys/vm/drop_caches (1 for page cache, 2 for dentries and inodes, 3 for both). It drops only clean objects, so run sync first.57 Without root you can do it per file with posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED), which is what this lesson's lab does.58 Both are for experiments. Dropping caches on a production machine only makes it slower.57

mmap and the page cache

mmap() of a file does not create a second copy. When the program touches a mapped address that is not yet mapped, the page fault handler (filemap_fault() for most filesystems) finds the folio in the same page cache that read() uses, reading it in if needed, and maps that physical memory into the process's page tables.59

  • A read() by one process and a load from a MAP_SHARED mapping by another see the same bytes, because they are the same bytes.60
  • A store to a MAP_SHARED page marks the folio dirty, through the filesystem's page_mkwrite hook on the first write.6162 It is then written back like any dirty folio. msync() forces that write-back for a range.63
  • MAP_PRIVATE maps the shared page read-only and copies it on the first write (copy-on-write). The private copy is anonymous memory and is never written to the file.60

Buffered write() and dirty pages

A buffered write() copies your bytes into the page cache and returns. The device is not involved. In Linux 6.18 the path for ext4 is:6465

write(fd, buf, n)
└ ksys_write() → vfs_write() → new_sync_write()
  └ f_op->write_iter() = ext4_file_write_iter()
    └ ext4_buffered_write_iter()
      └ generic_perform_write()                      mm/filemap.c, loops over the range
        ├ balance_dirty_pages_ratelimited()          maybe make this writer wait (below)
        ├ a_ops->write_begin() = ext4_da_write_begin()   find or create the folio, reserve space
        ├ copy_folio_from_iter_atomic()              copy user bytes into the folio
        └ a_ops->write_end()   = ext4_da_write_end()     mark the folio dirty, update i_size

The da stands for delayed allocation, from lesson 3. At this point ext4 reserves enough free space to guarantee the data will fit, so it can return ENOSPC now, but it does not choose disk blocks yet.66 When writeback happens later, it knows how much data the file has and can allocate one long contiguous extent instead of many small ones.67

Background writeback

Dirty folios are written to the device later, by kernel worker threads. Each block device has its own writeback work. In ps or top it appears as a kworker whose name includes flush-8:48, the device's major:minor number.6869 Writeback starts when any of these happens:

  • dirty data exceeds the background threshold;
  • a dirty folio has been dirty longer than dirty_expire_centisecs, checked every dirty_writeback_centisecs;7071
  • a program calls fsync(), fdatasync(), syncfs() or sync();
  • memory reclaim runs into dirty pages and asks the flusher to clean them.72

Writeback calls the filesystem's a_ops->writepages (ext4_writepages), which now allocates the delayed blocks, builds bios and submits them.73 The tunables, with the kernel defaults, which are also this machine's values:74

sysctl (vm.)DefaultMeaning
dirty_background_ratio10start background writeback when dirty data exceeds this % of dirtyable memory
dirty_ratio20the dirty limit: writers start being throttled halfway between the two ratios, and hardest at this %75
dirty_expire_centisecs3000data dirty for longer than 30 s is written on the next flusher pass
dirty_writeback_centisecs500the flusher wakes every 5 s to look for expired data
dirty_background_bytes, dirty_bytes0absolute limits in bytes; when non-zero they replace the ratios76

The percentages are of dirtyable memory (roughly free memory plus reclaimable page cache), not of total RAM.77 The kernel publishes the resulting limits in pages:78

$ grep -E 'nr_dirty(_background)?_threshold' /proc/vmstat
nr_dirty_threshold 603763
nr_dirty_background_threshold 301512

At 4 KiB per page that is about 1.15 GiB before background writeback starts and a dirty limit of about 2.3 GiB; writers start being throttled halfway between, at about 1.7 GiB.75 The default 30-second expiry is the number to remember: a buffered write() followed by a power cut can lose up to about half a minute of data.70

Dirty throttling: balance_dirty_pages

If a program could dirty pages faster than the device writes them, dirty memory would grow until RAM ran out. generic_perform_write() therefore calls balance_dirty_pages_ratelimited() as it goes. When dirty memory for the device is over its limit, the kernel makes the writing process sleep in short pauses, sized so that the writer's rate approaches the device's measured write bandwidth.79 Since Linux 3.2 the throttled writer only sleeps; the flusher does the I/O.7980 From the program's point of view, write() suddenly runs at disk speed instead of memory speed.

The lab shows the switch. Writing a 256 MiB file ran at about 1.5 GiB/s, entirely into the cache. Writing a 1 GiB file when only 1.4 GiB of memory was free slowed to about 345 MiB/s, and only about 390 MiB were still dirty when the last write() returned: the kernel had to reclaim memory and write back data while the program was still writing.

fsync, fdatasync, syncfs and O_SYNC

After write() returns, your data can be in four places, and only the last one survives a power cut:

  1. the page cache (lost if the machine crashes or loses power);
  2. in flight in the block layer;
  3. the drive's volatile write cache, a DRAM buffer inside the SSD or HDD (lost on power loss, unless the drive has power-loss protection);6781
  4. stable media: NAND flash cells or magnetic platters.

The system calls that move data down that list:

CallWhat it guarantees when it returns
fsync(fd)the file's data and all its metadata (size, block map, timestamps) are on stable storage, including a cache flush on the device82
fdatasync(fd)the data plus the metadata needed to read it back (size, block map). It may skip timestamps, which saves a journal commit82
open(…, O_SYNC) / O_DSYNCevery write() behaves as if followed by fsync / fdatasync83
syncfs(fd), sync()everything on that filesystem / every filesystem84
sync_file_range()starts or waits for writeback of a byte range. It does not commit metadata or flush the device cache, so it is not a durability guarantee85

The device flush is the part people forget. To make a write durable, the filesystem sends the device a FLUSH command (the bio flag REQ_PREFLUSH) to empty its write cache, or marks a write FUA, force unit access (REQ_FUA), so that write bypasses the cache.8687 ext4 does this as part of its journal commit (lesson 2 covers the device side).88 Without it, fsync would only prove that the data reached the drive's RAM.

Atomic file replacement: write, fsync, rename

Programs that save a whole file, such as editors, config tools and package managers, must never leave a half-written file after a crash. The standard recipe uses the fact that rename() replaces a directory entry in one journaled step:89

/* replace "config" with new contents, crash-safely */
int fd = open("config.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write_all(fd, data, len);        /* 1. new bytes into the page cache        */
fsync(fd);                       /* 2. new file's data + inode are durable    */
close(fd);
rename("config.tmp", "config");  /* 3. atomically swap the name               */
int dfd = open(".", O_RDONLY | O_DIRECTORY);
fsync(dfd);                      /* 4. the directory change itself is durable */
close(dfd);
  • Crash before step 3: config is the old file, intact. A stray config.tmp may exist.
  • Crash after step 3 but before step 4: the rename may or may not have reached the disk, so you get the old file or the new one, never a mix.82
  • After step 4: the new file, guaranteed.

Skipping step 2 is the classic bug. The rename can reach the disk before the data does, so after a crash config names an empty or partly written file.67 ext4 has a heuristic (the auto_da_alloc mount option, on by default) that forces data out early when it sees a file replaced by rename or truncation, because so many programs forgot step 2.67 Do not rely on it, and do not expect it from other filesystems.

fsync errors and errseq_t

Writeback is asynchronous, so a device error usually happens long after the write() that dirtied the page returned. The main places the kernel can report it are fsync(), fdatasync(), sync_file_range() and close() (on some filesystems, notably NFS).9091

Since Linux 4.13 each address_space records writeback errors in an errseq_t: an error code plus a counter.9092 Each struct file remembers the counter value it last saw. fsync() reports an error if one has been recorded since that file description last checked, and then advances its copy. Every open file description gets told about each error once.93

Pitfall: retrying fsync

In 2018 PostgreSQL developers found that their recovery logic assumed a failed fsync() could simply be retried.9495 On Linux, after a writeback error the affected pages are no longer dirty: the kernel has marked them clean or dropped them, depending on the filesystem.94 A second fsync() has nothing left to write and returns success, while the data never reached the disk.96

The lesson: an fsync() error means the data written since the last successful fsync() may be gone. Recover it from your own copy, a write-ahead log for example. PostgreSQL's fix was to treat an fsync() failure as fatal: crash, then replay its WAL.9597 The episode is known as "fsyncgate".98

O_DIRECT: bypassing the page cache

Opening a file with O_DIRECT asks the kernel to move data by DMA directly between your buffer and the device, skipping the page cache.83 ext4 routes it through ext4_dio_read_iter() and the iomap direct I/O code instead of filemap_read().99100

Why anyone wants this:

  • Databases such as InnoDB (with innodb_flush_method=O_DIRECT), Oracle and ScyllaDB keep their own buffer pool. With buffered I/O, every page would be cached twice, once in the database and once in the page cache.101102103
  • Memory use becomes predictable, and a huge scan cannot evict other applications' cached data.
  • No copy between the page cache and user memory.103

The price is strict rules and no help from the kernel:

  • The buffer address, the file offset and the length must all be aligned, traditionally to the device's logical block size (512 B or 4 KiB). Some filesystems demand more. Since Linux 6.1, statx() with STATX_DIOALIGN reports the exact requirements for a file.104 On ext4 a misaligned buffer or offset fails with EINVAL, and the lab triggers both cases; other filesystems may fall back to buffered I/O instead.104
  • No readahead and no write-behind. Each read() waits for the device, so a program needs many requests in flight (threads, io_uring or AIO) to get good throughput.103
  • O_DIRECT is not a durability guarantee. The data skips the page cache, but metadata changes (file size, newly allocated blocks) and the device's write cache still need fsync() or O_DSYNC.83
  • Mixing buffered and direct I/O on the same file works but is slow: before each direct I/O the kernel writes back any dirty cached pages in the range, and before a direct write it also drops them from the cache.104105

Cache hints and asynchronous I/O

Programs can influence I/O in two ways: give the kernel hints about which data they will use, and submit requests asynchronously through io_uring. Start with cache hints: they tell the kernel which ranges to prefetch or release.

CallEffect
posix_fadvise(fd, off, len, POSIX_FADV_SEQUENTIAL)larger readahead window
… POSIX_FADV_RANDOMno readahead
… POSIX_FADV_WILLNEED / readahead(2)start reading this range into the cache now58106
… POSIX_FADV_DONTNEEDstart writeback of dirty pages in the range and drop the clean ones107
madvise(addr, len, MADV_SEQUENTIAL | MADV_RANDOM | MADV_WILLNEED)the same hints for an mmap'd range108

io_uring (Linux 5.1) changes how requests are submitted rather than how they are cached.109 The program and the kernel share two ring buffers in memory: a submission queue where the program places requests, and a completion queue where the kernel places results.110 One io_uring_enter() call can submit hundreds of reads and writes, and with polling mode no system call is needed at all.110111 It works with buffered and direct I/O.109 The shape, a submission queue paired with a completion queue, is the same one NVMe uses in hardware (lesson 2) and RDMA uses for network transfers (lesson 8).

The cache stack from stdio to the drive

Put together, a single fwrite() passes through a stack of caches. Each one absorbs writes and serves reads, and each one is emptied by a different mechanism.

Aside: a cache below the disk

On a virtual machine there is often one more layer: the host caches the file that holds the virtual disk. WSL's root filesystem is ext4 inside a virtual disk file on Windows115, and Windows caches that file. That is why this lesson's lab sees "cold" reads at 0.9 to 1.8 GiB/s even after the guest dropped its cache. The data came from the host's RAM, not from the SSD. Every layer you cannot see can have a cache too.

Cache coherence on a single machine

Nothing in this lesson had to deal with stale data, and that is not luck. On one machine, coherence is free for three reasons:

  1. One copy. For a given (inode, page index) there is exactly one folio in RAM. Every process that reads or maps the file uses that folio. A write by one process is visible to the next read() by any other process immediately, because there is nothing else to update.
  2. One gatekeeper. Every change to a file or directory goes through this kernel's VFS. The same code path that changes a directory on disk also updates the dentry, so the dcache can never disagree with the disk.116
  3. Nobody writes behind the kernel's back. The disk changes only when this kernel tells it to. Caches never need to ask "has this changed?", because the answer is always no.

Now mount the same filesystem on a second machine over a network. Each machine has its own page cache, dcache and inode cache, and neither kernel sees the other's changes. All three reasons fail at once, and each failure has a visible symptom:

Cached on the clientWhat goes wrong when another machine changes the file
page cache (data)a read returns old contents after another client wrote new ones
inode cache (attributes)ls -l shows the old size and mtime; an O_APPEND write lands at the old end of file and overwrites someone else's append83
positive dentrythe name points at a file another client deleted or renamed; the next operation fails with ESTALE117
negative dentrya file another client just created is reported as missing
dirty foliosyour writes are invisible to others until written back, and a write error (ENOSPC, EIO, quota) can only be reported later, at fsync() or close()91
locksflock() and fcntl() locks in one kernel mean nothing to another; locking needs a protocol

A network filesystem has to decide, for every cache in this table, when to trust it and when to ask the server again.116 Ask too often and every stat() costs a network round trip. Ask too rarely and programs see stale data. Lesson 6 covers the NFS protocol itself, and lesson 7 covers how it answers this question: attribute timeouts, close-to-open consistency and delegations.

Check yourself

Two processes open and read the same 1 GiB file. How much page cache does it use?

About 1 GiB, once. The folios belong to the inode's address_space, not to either process or either struct file. The processes get separate offsets and share the cached data.

write() returned success, and a second later the power failed. Is the data on disk?

Probably not. A buffered write only copies into the page cache. Dirty data is written after it crosses a threshold or ages past 30 seconds (by default), or when someone calls fsync(). Even after writeback, it may sit in the drive's volatile cache until the filesystem sends a FLUSH.

In the atomic replace pattern, why fsync the directory after rename()?

The rename changes the directory, not the file. fsync on the file makes its data and inode durable, but the new directory entry is part of the directory's metadata. Until the directory is synced, a crash can bring back the old name.

fsync() returned EIO. You call it again and it returns 0. Is the data safe?

No. After a writeback error, Linux no longer treats the failed pages as dirty, so the second fsync() has nothing to write and reports success. Treat the data written since the last successful fsync() as lost and rewrite it from your own copy or log.

What is a negative dentry, and which workload benefits from it?

A cached record that a name does not exist in a directory. Anything that probes many paths that usually fail benefits: $PATH searches by the shell, include-path searches by compilers, library searches by the dynamic linker.

Why must O_DIRECT buffers, offsets and lengths be aligned?

The device transfers data by DMA, in units of its logical block size, straight into or out of your buffer. There is no page cache folio in between that could absorb a partial block or do a read-modify-write, so the request has to line up with what the hardware can do.

How does the kernel start the next readahead before the program asks for it?

It flags one folio inside each readahead window with PG_readahead. When the program's reads reach that folio, filemap_get_pages() sees the flag and calls page_cache_async_ra(), which starts reading the next, usually larger, window while the program is still consuming the current one.27

Name two caches that make local coherence free, and say what replaces that guarantee on a network filesystem.

The page cache (one folio per file page, shared by everyone) and the dcache (updated by the same code that changes the directory). On a network filesystem each client has its own copies, so the client must decide when to revalidate with the server, or get the server to promise to notify it. Lessons 6 and 7 cover how NFS does that.
