Lesson 8 · Network

RDMA and NFS over RDMA

At 100 to 400 Gb/s the network is no longer the slow part. The CPU is, because it copies every byte and processes every packet. RDMA hands that work to the network card. This lesson builds the model from the hardware up, then shows exactly how NFS uses it.

After this lesson you can
  • explain where the CPU time goes in an ordinary TCP read, and which part RDMA removes;
  • tell InfiniBand, RoCE v2 and iWARP apart, and say why RoCE cares about lossless Ethernet;
  • name every verbs object (PD, MR, QP, CQ, WR, WC) and what it is for;
  • say which CPUs take part in SEND, RDMA WRITE, RDMA READ and atomics;
  • trace an NFS READ and an NFS WRITE over RPC-over-RDMA, chunk by chunk;
  • set up soft-RoCE in a VM and mount NFS with proto=rdma.

CPU cost of a read over TCP

Follow one 1 MiB NFS READ over TCP, the way lesson 6 set it up, and count the work on the client.

  1. The NIC (Network Interface Card) receives Ethernet frames and writes them by DMA into kernel memory that the driver set aside in advance: a ring of receive buffers. Each frame becomes a socket buffer (sk_buff, usually called an skb).
  2. The NIC raises an interrupt, or the kernel notices new frames by polling network queues through NAPI, its packet-processing mechanism.1 The CPU runs the IP and TCP code for each packet: checksums (often offloaded), sequence numbers, acknowledgements, reassembly into a byte stream.
  3. The SUNRPC layer finds the RPC record boundaries in that stream, matches the reply to its request by XID, and decodes the XDR.
  4. The NFS client copies the READ data out of the skbs into the page-cache pages of the file (lesson 5).
  5. The application's read() copies again, from the page cache into the user buffer.

The server pays a similar bill on the way out, although sending is easier to make zero-copy than receiving (the kernel can hand page-cache pages to the NIC with sendfile-style paths).2

Each copy costs memory bandwidth twice, because the CPU reads every byte and then writes it. Do the arithmetic for a fast link:

At 10 Gb/s one core keeps up and nobody cares. At 400 Gb/s the copies alone eat a large share of a server socket's memory bandwidth, and the per-packet protocol work needs several cores.3 Offloads such as TSO (TCP Segmentation Offload: the NIC splits large sends into packets) and GRO (Generic Receive Offload: the kernel merges received packets) cut the per-packet cost.45 They do nothing about the copies or about the CPU having to look at every byte.

DMA and descriptor rings

Direct memory access means a device reads and writes host RAM by itself. The CPU writes a small descriptor ("put the next frame at physical address X, up to 2048 bytes") into a ring in memory, and the device does the transfer. Two consequences matter for everything below. The memory must stay where it is while the device uses it, so it is pinned: the kernel will not swap or migrate those pages. And the device needs addresses it can use, either physical addresses or addresses translated by an IOMMU (Input/Output Memory Management Unit, device address translation and access control). You already saw this pattern in lesson 2: an NVMe SSD reads commands from a submission queue and DMAs data straight into the buffers they name.

How RDMA moves data

Remote Direct Memory Access extends DMA across the network. Your NIC can write into, or read from, memory on another machine, and the other machine's NIC does the work on its side. Three ideas make that possible.

  • The transport runs on the NIC. Segmentation, acknowledgements, retransmission and ordering are done in NIC hardware.6 The CPU posts a request ("send these 1 MiB") and later reads one completion.
  • Memory is registered up front. Before the NIC may touch a buffer, the program registers it. Registration pins the pages and loads their addresses into the NIC's translation table.7 From then on the NIC can DMA to that buffer directly, so no intermediate kernel buffer exists to copy from. This is zero-copy.
  • The data path bypasses the kernel. Setting things up (opening the device, registering memory, creating queues) goes through the kernel driver. Moving data does not. The NIC's queues are mapped into the process, so posting work is a write to ordinary memory plus one write to a NIC register. No system call, no context switch.68

Kernel bypass only matters for user-space programs (MPI jobs, databases, AI frameworks). Kernel users of RDMA such as the NFS client and server, NVMe over Fabrics or iSER are in the kernel already. For them the gains are zero-copy and the offloaded transport.

Key idea

RDMA moves the transport into the NIC and lets the NIC place data exactly where the application said it should go. The receiving CPU does not copy the bytes and, for one-sided operations, does not even know they arrived.

The price is a different programming model. A socket is a byte stream that the kernel buffers for you. RDMA is a set of queues, explicit memory registrations, and explicit permission keys. The rest of this lesson is that model.

Fabrics: InfiniBand, RoCE and iWARP

The same programming interface, called verbs, runs over three families of networks.6 They differ in what carries the packets and in how they cope with loss.

FabricRuns overAddressesHow loss is handledWhere you meet it
InfiniBandits own links, switches and routers (a complete stack, L1 to L4)LID: 16-bit local ID inside a subnet, assigned by the subnet manager. GID: 128-bit global ID, for routing between subnets9credit-based link-level flow control: a port transmits only when the next hop has advertised buffer space, so switches do not drop packets under congestion1011HPC (High-Performance Computing) clusters, AI training clusters, storage back-ends

An InfiniBand network needs a subnet manager (OpenSM, or one built into a switch). It discovers the topology, assigns LIDs and programs every switch's forwarding table.1118 Nothing works until it has run, which is the first thing to check on a broken IB cluster (ibstat shows the port state and LID).1819

RoCE (RDMA over Converged Ethernet) puts the InfiniBand transport layer on top of Ethernet. Version 2 wraps it in UDP/IP so it can be routed like any IP traffic.12 The catch is loss. The InfiniBand transport was designed for a fabric that does not drop packets, and the original retransmission scheme is go-back-N: after a loss, the sender resends everything from the lost packet onward.10 On a congested Ethernet that is slow. So most RoCE deployments make Ethernet behave more like InfiniBand10:

  • PFC (Priority Flow Control, IEEE 802.1Qbb) lets a switch port tell its neighbour "pause traffic of priority 3" when its buffer fills. RoCE traffic goes in a paused-not-dropped priority class.1420 PFC brings its own problems: pauses spread backwards through the network (head-of-line blocking, pause storms), and badly designed topologies can deadlock.321
  • ECN (Explicit Congestion Notification) lets switches mark packets instead of dropping them. With DCQCN, the receiving NIC turns marks into congestion notification packets and the sending NIC lowers its rate.22 The aim is to slow senders down before PFC has to pause anything.23

Newer NICs recover from loss better (selective retransmission), and some operators run RoCE with little or no PFC.2024 Which configuration is right depends on the NIC and switch generation, so follow the vendor's guidance for your hardware.

iWARP takes the opposite route: it runs RDMA over TCP inside the NIC, so it inherits TCP's congestion control and works on any network.25 It never became as common as RoCE.

Soft-RoCE

The Linux driver rdma_rxe implements RoCE v2 in software on top of any Ethernet interface.2627 It is slow and burns CPU, which defeats the purpose in production, but the verbs API, the packets and the NFS behaviour are real. The lab uses it.

Verbs objects: PD, MR, QP and CQ

The InfiniBand specification describes what an RDMA NIC can do as abstract verbs.9 On Linux the user-space library is libibverbs (part of the rdma-core project) and the kernel side is the ib_core subsystem.2829 Kernel users like NFS call the same verbs through in-kernel functions.30 You create the objects in this order.

The two keys returned by registration are the core of RDMA's security model:

  • the lkey (local key) goes into your own work requests. It proves to your NIC that the buffer you name belongs to a region you registered37;
  • the rkey (remote key) is what you give a peer. A peer that holds your buffer's address and rkey can read or write that region directly, within the access flags you chose at registration (IBV_ACCESS_REMOTE_WRITE, IBV_ACCESS_REMOTE_READ, IBV_ACCESS_REMOTE_ATOMIC).738

Each work request carries a 64-bit wr_id that you choose and the completion hands back.3536 Programs usually store a pointer to their own request context there, so a completion leads straight back to whatever was waiting for it.

RDMA operations

RDMA has two kinds of operation, and the difference decides which CPUs do any work.

Two-sided: SEND and RECV

The sender posts a SEND with a buffer. The receiver must already have posted a RECV with a buffer large enough to hold the message. The receiving NIC takes the next posted RECV from the receive queue, writes the message into its buffer, and produces a completion on the receiver's CQ.5556 Both CPUs take part: one posts, the other pre-posts and then polls.

If no RECV is posted when a SEND arrives, the receiving NIC answers RNR (receiver not ready) and the sender's NIC retries after a delay, up to rnr_retry_count times. Seven means retry forever.495758 RNR retries waste time, so protocols built on SEND/RECV make sure it does not happen, usually with credits (below).

One-sided: RDMA WRITE, RDMA READ, atomics

  • RDMA WRITE: the initiator names a local buffer and a remote (address, rkey). The target's NIC checks the rkey, the range and the access rights, then DMAs the data into place. The target's CPU gets no completion and does not know anything happened.555659
  • RDMA WRITE with immediate: the same, plus a 32-bit value that consumes one posted RECV on the target and produces a completion there.3557 "Data is in place, here is a tag" in a single operation.
  • RDMA READ: the initiator names a remote (address, rkey) and a local buffer. The target's NIC reads its own memory and returns the data. Again the target's CPU is not involved. The number of READs in flight per QP is limited by the initiator_depth and responder_resources negotiated at connect time.4955
  • Atomics: 64-bit compare-and-swap and fetch-and-add on remote memory, executed by the target NIC.9 Useful for distributed locks and counters without waking the remote CPU.

That last point leads to the classic pattern in rc_hello.c: RDMA WRITE the data, then SEND a small message. On a reliable connected QP operations are delivered in order, so by the time the target sees the SEND's completion, the bytes of the earlier WRITE are already in its memory.5660 (RDMA READs are an exception to the simple ordering story. A later operation can overtake a READ unless you set IBV_SEND_FENCE.)3560

RDMA costs and limitations

Memory registration cost and pinning

ibv_reg_mr pins every page (the kernel walks the page tables and takes references) and loads the translations into the NIC. That takes tens of microseconds even for a small buffer and much longer for a large one, which is far too slow to do for each I/O.76162 Programs avoid it in three ways:

  • Register once, reuse forever. Allocate a pool of buffers at start-up and keep it registered. Simple, but the data must be copied into the pool, which brings back a copy.
  • Registration caches. Libraries such as UCX remember which user buffers are already registered and reuse the registration. The hard part is knowing when the application frees or remaps that memory, because a stale registration still points at the old pages.63
  • Fast registration (FRWR). Kernel users pre-allocate MR objects and register pages by posting a REG_MR work request on the QP itself, inline with the data traffic. Afterwards the registration is invalidated with a LOCAL_INV work request, or remotely by the peer with SEND with Invalidate. The Linux NFS/RDMA client uses FRWR by default.646566

rkeys and memory protection

Anyone who knows (address, rkey) and can reach a QP in the right protection domain can read or write that memory, within the registered access rights.67 An rkey is a 32-bit value, and only part of it changes between registrations, so treat it as easy to guess rather than secret.5968 Careful protocols register memory per I/O, expose it only for as long as the I/O lasts, then invalidate it. NFS over RDMA does exactly this, and in addition never gives the client an rkey for server memory at all (see below).69 Memory windows offer finer-grained, revocable remote access. Network isolation (InfiniBand partition keys, VLANs for RoCE) is the outer fence.970

Receive buffers and credits

Every SEND consumes a RECV that the receiver posted in advance. Post too few and senders hit RNR; post too many and memory sits idle (a shared receive queue, SRQ, lets many QPs draw from one pool).9 Protocols solve this with credits: the receiver tells the sender how many receives it has posted, and the sender never has more SENDs outstanding than that. Credit-based flow control appears at every level of RDMA, from the InfiniBand link layer up to RPC-over-RDMA.671

CQ polling vs completion events

Spinning on ibv_poll_cq gives the lowest latency and keeps one core at 100%. Event mode (ibv_req_notify_cq plus a completion channel) sleeps until an interrupt, which saves the core and adds microseconds.7273 Real systems mix the two: poll for a while, then arm the interrupt and sleep.

QP count and connection scaling

RC needs a QP per pair of communicating endpoints. An all-to-all job with thousands of processes needs millions of QPs. Each QP's state is kept in host memory and cached in the NIC's limited memory; as the count grows, that cache starts missing, and every miss costs a read across PCIe.7475 XRC, DC and UD-based transports exist to reduce that count.

Fabric configuration: PFC, ECN, MTU and GID

Most RDMA trouble in practice is configuration: PFC and ECN settings that do not match across switches, MTU mismatches, the wrong GID index on RoCE, firmware versions. Useful first tools are ibv_devinfo, rdma link, rdma statistic, ibstat on InfiniBand, and the NIC's own counters in ethtool -S.

Pitfall

Raw verbs are rarely the right level for an application. Most user-space software uses a library that hides registration, connection management and protocol choice: UCX, libfabric, MPI, or NCCL for GPUs. Kernel code uses the in-kernel verbs through subsystems like NFS, NVMe-oF and iSER. Learn verbs to understand those systems, not to replace them.

Storage protocols over RDMA

Nearly every storage protocol on RDMA follows one pattern. Small control messages (commands, RPC headers, replies) travel by SEND/RECV. Bulk data moves by RDMA READ or WRITE, which the server or target initiates against buffers the client described in its request.4076

RPC-over-RDMA version 1 (RFC 8166)

NFS itself does not change. The compound operations, state, delegations and caching from lessons 6 and 7 are identical. What changes is the transport under SUNRPC. Linux has pluggable RPC transports: xprtsock for TCP and UDP, and xprtrdma (client) and svcrdma (server) for RDMA. Both RDMA halves live in the rpcrdma kernel module.878889

The protocol is RPC-over-RDMA version 1, defined in RFC 8166.90 RFC 8267 says how NFS uses it, and assigns the service name nfsrdma on port 20049, which NFSv4 servers must use for RDMA.9192 RFC 8797 adds a way for the two peers to tell each other their real buffer sizes in the rdma_cm private data at connect time.93

The RPC-over-RDMA header

Every RPC message travels in a SEND, prefixed by a small XDR header9495:

RPC-over-RDMA v1 header (on every SEND)
  rdma_xid      copy of the RPC XID
  rdma_vers     1
  rdma_credit   credits requested (in a call) or granted (in a reply)
  rdma_proc     RDMA_MSG (0)    the RPC message follows inline
                RDMA_NOMSG (1)  the RPC message itself is in a chunk
                RDMA_ERROR (4)
  read list     0..n read segments  { position, handle, length, offset }
  write list    0..n write chunks, each an array of { handle, length, offset }
  reply chunk   0 or 1 array of { handle, length, offset }
then, for RDMA_MSG: the RPC message, minus any data moved through chunks

A segment is the triple a remote NIC needs: handle is the rkey, offset is the address, length is the size. A chunk is one or more segments that together hold one XDR data item.9697

Inline threshold and credits

The inline threshold is the largest message one SEND can carry, set by the size of the receive buffers the peer posted. RFC 8166 says both sides must assume 1024 bytes unless they learn otherwise.9899 Linux uses larger buffers and advertises them through the RFC 8797 private data.50100 Anything that fits goes inline in a single SEND. Anything that does not goes through a chunk.101

Credits are the receive-buffer accounting from the previous section, built into the protocol. In rdma_credit the client asks for a number of credits and the server grants a number. The server keeps that many RECVs posted, and the client never has more calls outstanding than its grant. A grant of zero is forbidden, because it would deadlock the connection.71

For NFSv4 they are the data of WRITE arguments, the data of READ results, and the link text of READLINK and of a symlink CREATE.104 Everything else, such as file handles, attributes and stateids, never gets a chunk of its own: it travels inline, or inside a whole call or reply moved through a Position Zero Read chunk or a Reply chunk.101105

Key idea

The client only ever exposes its own memory. The server performs every RDMA READ and RDMA WRITE.5076 A client never holds an rkey for server memory, so a buggy or hostile client cannot scribble on the server, and the server decides how much RDMA traffic it has in flight.96

RPC-over-RDMA version 2

Work on RPC-over-RDMA version 2 aimed to make the protocol extensible and to fix version 1's pain points, such as small default inline sizes forcing RDMA operations for modest payloads. It exists only as an IETF Internet-Draft whose last revision (-07, June 2022) has expired.109110 Everything deployed today speaks version 1.

Enabling NFS over RDMA on Linux

On the server, load the transport, add an RDMA listener, and export with insecure (an RDMA connection has no privileged source port for the server to check)111112:

# modprobe rpcrdma
# echo 'rdma 20049' > /proc/fs/nfsd/portlist     # at runtime
# or permanently, in /etc/nfs.conf:
#   [nfsd]
#   rdma=y              (rdma-port=20049 is the default)
# cat /etc/exports
/srv/data  *(rw,sync,no_subtree_check,insecure)

On the client, ask for the RDMA transport and the RDMA port111113:

# modprobe rpcrdma
# mount -t nfs -o vers=4.2,proto=rdma,port=20049 server:/srv/data /mnt/data
$ nfsstat -m        # the options line shows proto=rdma,port=20049

The per-mount statistics in /proc/self/mountstats (lesson 7) gain a transport line that starts with xprt: rdma. After the generic counters (connects, sends, receives) come RDMA-specific ones, in this order: read chunks, write chunks, reply chunks, total bytes moved by RDMA for requests and replies, pull-up and fix-up copies, registrations done the slow way (hardway_registers), marshalling failures, bad replies, no-message calls, then memory-registration counts (recycled, orphaned, allocated), local invalidations needed, empty send-context events, and replies that had to wait for their Send to complete.114 A large sequential write raises the read-chunk counter; a large read raises the write-chunk counter. The lab has an awk line that labels every field.

Lab 07

Soft-RoCE, a verbs program, and NFS over RDMA

~/storage-course/labs/07-rdma/

This WSL kernel is built without InfiniBand or soft-RoCE support (CONFIG_INFINIBAND and CONFIG_RDMA_RXE are not set), so this lab runs in a Linux VM. Ubuntu 24.04 under any hypervisor is fine; two VMs on one virtual network are best. The steps are untested on this machine. rc_hello.c was compiled and linked here against the Ubuntu 24.04 rdma-core headers with no warnings, but it has not been run.

  1. Create an RDMA device on top of the VM's Ethernet interface115: 
    $ sudo apt install rdma-core ibverbs-utils rdmacm-utils perftest \
       libibverbs-dev librdmacm-dev linux-modules-extra-$(uname -r)
$ sudo modprobe rdma_rxe
$ sudo rdma link add rxe0 type rxe netdev enp0s3   # your interface name
$ ibv_devinfo -d rxe0 -v | less                    # limits, ports, GID table
    Find the GID index that holds your IPv4 address (often 1). The tools call it -g or -x.
  2. Move real RDMA traffic. ibv_rc_pingpong swaps QP numbers and GIDs over TCP, walks both QPs to RTS, then ping-pongs SENDs: 
    $ ibv_rc_pingpong -d rxe0 -g 1                # server
$ ibv_rc_pingpong -d rxe0 -g 1 <server-ip>    # client
$ ib_write_bw -d rxe0 -x 1   /   ib_write_bw -d rxe0 -x 1 <server-ip>
$ ib_read_lat -d rxe0 -x 1   /   ib_read_lat -d rxe0 -x 1 <server-ip>
    With soft-RoCE the absolute numbers are meaningless. Compare WRITE with SEND and READ latency with SEND latency on the same setup.
  3. Build and run the verbs program. Read its comments top to bottom first: they follow the order of this lesson. 
    $ gcc -Wall -Wextra -O2 -o rc_hello rc_hello.c -lrdmacm -libverbs
$ ./rc_hello server 7471
$ ./rc_hello client <server-ip> 7471
    The server prints (empty), then after the client's SEND arrives it prints the message the client placed by RDMA WRITE. The server never gets a completion for the WRITE itself. Then break it on purpose: drop IBV_ACCESS_REMOTE_WRITE from the server's registration (remote access error), or remove the pre-posted RECV (receiver-not-ready retries).
  4. Mount NFS over the rxe device, following the server and client commands in the section above (the README has them in full). Then: 
    $ dd if=/dev/zero of=/mnt/nfsrdma/big bs=1M count=256 oflag=direct
$ dd if=/mnt/nfsrdma/big of=/dev/null bs=1M iflag=direct
$ grep -E 'xprt:[[:space:]]+rdma' /proc/self/mountstats
    The write raises the read-chunk counter (the server pulled the data); the read raises the write-chunk counter (the server pushed it). mrs_allocated stays small while mrs_recycled climbs, because registrations are reused.

Advanced alternative: build your own WSL kernel with CONFIG_INFINIBAND, CONFIG_INFINIBAND_USER_ACCESS, CONFIG_RDMA_RXE and CONFIG_SUNRPC_XPRT_RDMA, and point kernel= in .wslconfig at it. That changes the kernel for every WSL distribution on the machine8116117; the VM is simpler.

Check yourself

At 400 Gb/s, what limits a TCP receiver that RDMA does not?

The CPU. It must run TCP/IP for millions of packets per second and copy every byte at least once (skb to page cache) and often twice (page cache to user buffer). Each copy reads and writes memory, so one receive copy at 50 GB/s costs about 100 GB/s of memory traffic. RDMA runs the transport on the NIC and DMAs data straight to its final address.

What do the lkey and the rkey of a memory region each authorise?

The lkey goes in your own work requests and lets your NIC access the buffer for local operations. The rkey is given to a peer and lets the peer's operations (RDMA READ, WRITE, atomics) access the region remotely, within the access flags chosen at registration.

The target of an RDMA WRITE gets no completion. How does it learn the data has arrived?

Either the initiator uses RDMA WRITE with immediate, which consumes a posted RECV and creates a completion on the target, or it follows the WRITE with a SEND. On an RC queue pair operations are delivered in order, so when the SEND's RECV completes, the WRITE's data is already in memory.

Why must a receiver post RECVs in advance, and how do credits help?

A SEND is placed into the buffer of the next posted RECV. If none is posted, the receiving NIC answers receiver-not-ready and the sender retries, which wastes time. With credits the receiver tells the sender how many RECVs it has posted, and the sender never has more SENDs in flight than that. RPC-over-RDMA carries credits in the rdma_credit header field.

Why does RoCE v2 usually run on Ethernet configured with PFC and ECN?

The InfiniBand transport it carries was designed for a fabric that does not drop packets, and its go-back-N retransmission performs badly under loss. PFC pauses traffic per priority instead of dropping it; ECN marking with DCQCN slows senders before buffers fill. Newer NICs tolerate loss better, so the exact configuration depends on hardware.

In an NFS WRITE over RDMA, who performs the RDMA operation, in which direction, and through which kind of chunk?

The server. The client registers the data pages for remote read and describes them in a read chunk. The server pulls the data with RDMA READ, rebuilds the call, and nfsd writes the file. For an NFS READ it is the reverse: a write chunk, and the server pushes the data with RDMA WRITE.

Why is it a good design that only the server initiates RDMA in RPC-over-RDMA v1?

The client never learns an rkey for server memory, so a faulty or malicious client cannot read or corrupt the server. The server also controls how many RDMA operations it has in flight, so clients cannot overload it with RDMA traffic.

What changes in NFS semantics when you mount with proto=rdma?

Nothing. Compounds, state, delegations, close-to-open and the attribute cache behave exactly as over TCP. Only the SUNRPC transport underneath changes, along with the port (20049).
