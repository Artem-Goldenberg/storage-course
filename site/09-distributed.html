Lesson 9 · Network

Distributed Filesystems

Sooner or later one server runs out of disks, bandwidth or uptime. A distributed filesystem spreads one namespace over many machines. Every design answers the same handful of questions, and this lesson walks through them using the systems you are most likely to meet: Lustre, Ceph, GPFS, HDFS and pNFS.

After this lesson you can
  • name the six problems every distributed filesystem must solve;
  • place a system in the architecture taxonomy and predict its strengths and weak spots;
  • compute which Lustre OST holds a given byte of a striped file;
  • follow a Ceph object from its name to a placement group to a list of OSDs;
  • compare replication and erasure coding on overhead, failure tolerance and rebuild cost;
  • explain leases, quorum and fencing, and why a cluster can never be sure a silent node is dead.

Why distribute, and what gets hard

A single NFS server (lesson 6) is the simplest network filesystem, and it hits four walls:

  • Capacity. A chassis holds a fixed number of drives.
  • Bandwidth. Every byte passes through one machine's NICs, memory and CPUs. Two 400 Gb/s ports cap it at about 100 GB/s, and the server usually saturates well before that.
  • Metadata rate. Every create, lookup and rename runs on that one machine's CPUs and its local filesystem's locks.
  • Availability. One machine is one failure domain. High-availability pairs help with crashes, not with the other three walls.

Scaling out means adding servers instead of growing one. As soon as there are several, six problems appear, and every system in this lesson is a set of answers to them:

  1. Metadata scaling. Who knows the namespace (names, directories, attributes, which servers hold a file), and how many operations per second can they serve?
  2. Data placement. Which servers hold which bytes, and how does a client find them?
  3. Redundancy. How do the bytes survive the loss of a disk, a server, or a rack?
  4. Consistency and caching. What does a client see while other clients write? This is lesson 7's question with many more participants.
  5. Failure detection and recovery. Who decides that a node is dead, and how is its state rebuilt?
  6. Rebalancing. What has to move when servers are added or removed?
Key idea

The biggest single design choice is where metadata lives and how a client goes from a file name to the servers holding its data: ask a server, read a table, or compute it.

Scale-up NAS and shared-disk clusters

The single NFS server is the baseline. It is simple, every client already supports it, and its semantics are the ones from lessons 6 and 7. High availability usually means two heads in front of the same storage: when the active head dies, the standby imports the storage, takes over the IP address, and clients reclaim their state during the NFSv4 grace period. Capacity and bandwidth still stop at one head.

Shared-disk clusters

A shared-disk cluster removes the single head. Every node sees the same block devices (a SAN, iSCSI or NVMe over Fabrics), and every node runs the whole filesystem itself: it reads and writes the on-disk inodes, bitmaps and directories from lesson 3 directly. The hard part is that each node has its own page cache and inode cache (lesson 5). Two nodes caching the same allocation bitmap and both allocating from it would corrupt the filesystem.

So every structure is protected by a cluster-wide lock. GFS2 and OCFS2 use an in-kernel distributed lock manager (DLM): before a node reads an inode it takes a shared lock on it, before changing it an exclusive one. When another node asks for a conflicting lock, the holder is told to write back its dirty data, drop its cached copy, and release. The cache is valid only while you hold the lock. That rule turns up in every coherent design in this lesson.

IBM Storage Scale (long known as GPFS) is the large-scale member of this family. Its disks are usually reached over the network through NSD servers (Network Shared Disk), so it looks like architecture 3 on the wire while keeping the shared-disk design inside. A token manager hands out tokens. Byte-range tokens let one node cache and write part of a file while another node works on a different range of the same file. For each open file, one node acts as the metanode and is the only one that updates that file's inode and block map. GPFS is fully POSIX-coherent and runs some of the largest HPC filesystems.

Pitfall

A node that hangs for 30 seconds and then wakes up still believes it holds its locks. If the cluster has already given those locks to someone else, its delayed writes corrupt the shared disks. Shared-disk clusters therefore require fencing: cut the node's power or its storage access before handing its locks out. See failures below.

Metadata server plus data servers

This is the most common design for high-bandwidth file storage. Split the work in two:

  • a metadata server (MDS) holds the namespace: directories, names, permissions, and for each file a layout saying which data servers hold its bytes and in what pattern;
  • many data servers hold the bytes and do nothing else.

A client asks the MDS once, at open, for the layout, then talks to the data servers directly and in parallel. The metadata server stays off the data path, so bandwidth grows with the number of data servers. You met the standard version of this in lesson 6: pNFS, where an NFSv4.1+ client gets a layout from the MDS and performs I/O against data servers.

Lustre

Lustre is the dominant open-source parallel filesystem in HPC. Its pieces:

ComponentRole
MGS management serverholds the configuration; clients and servers fetch it at mount time
MDS / MDTmetadata server and its metadata target (a storage device formatted with ldiskfs, a modified ext4, or ZFS). Holds directories and inodes; each file's layout is stored as an extended attribute of its inode
OSS / OSTobject storage server and its object storage targets. A file's data lives in one or more objects on OSTs
Clienta kernel filesystem module. Presents POSIX to applications
LNetLustre's own network layer. Its drivers (LNDs) include socklnd for TCP and o2iblnd for RDMA over InfiniBand or RoCE (lesson 8). LNet routers can join different fabrics

Striping is RAID 0 across OST objects. A layout has a stripe_size (how many bytes go to one object before moving on) and a stripe_count (how many objects). Many sites default to one stripe of 1 MiB and let users raise the count for big files. The arithmetic is the same kind you did in lesson 2:

stripe_number = offset / stripe_size
object_index  = stripe_number % stripe_count          # which object in the layout
object_offset = (stripe_number / stripe_count) * stripe_size
              + offset % stripe_size                  # where inside that object

# stripe_size = 1 MiB, stripe_count = 4, offset = 5.5 MiB
stripe_number = 5,  object_index = 1,  object_offset = 1 MiB + 0.5 MiB = 1.5 MiB
$ lfs setstripe -c 4 -S 4M /lustre/project/run42      # default layout for new files in this dir
$ lfs getstripe /lustre/project/run42/output.h5        # show a file's layout and its OST objects
$ lfs setstripe -E 32M -c 1 -E 1G -c 4 -E -1 -c -1 big.dat   # a progressive layout

The last command is a progressive file layout (PFL, Lustre 2.10): the first 32 MiB use one stripe, up to 1 GiB use four, and the rest use every OST (-c -1). Small files stay cheap and big files get bandwidth, without anyone knowing the size in advance.

Metadata scales through DNE (distributed namespace), which spreads the namespace over several MDTs. A remote directory places a whole subtree on another MDT (lfs mkdir -i 1 dir). A striped directory (Lustre 2.8) hashes the entries of one directory over several MDTs (lfs mkdir -c 4 dir), which helps when thousands of clients create files in the same directory.

Coherence comes from the Lustre distributed lock manager, LDLM. Each MDT and OST runs a lock server for its own resources. Before a client caches file data, it takes an extent lock on a byte range of the OST object; reads take shared locks and writes take exclusive ones. When another client wants a conflicting range, the server sends the holder a blocking callback. The holder flushes its dirty pages, drops the cached pages in that range, and releases the lock. Metadata uses inodebits locks on the MDT. This is how Lustre lets clients cache aggressively and still gives POSIX semantics: a client may cache only what it holds a lock for.

The authoritative size of a striped file lives with its OST objects, so a stat() may have to ask the OSTs that hold the file's objects. ls -l on a huge directory of striped files is slower on Lustre than on a local disk for exactly this reason.

Failure handling. Servers commit transactions to disk asynchronously, and clients keep a copy of every request until the server reports that it has committed it (the last_committed transaction number). If a server restarts, clients reconnect and replay their uncommitted requests in order. Traditionally Lustre does not replicate data across servers. Each OST sits on RAID, and servers are arranged in failover pairs that share storage, so a partner can mount the target if its server dies. File Level Redundancy (FLR, Lustre 2.11) adds optional mirroring of a file across OSTs.

BeeGFS

BeeGFS follows the same pattern with a management service, metadata services (each directory is owned by one metadata server, so the namespace spreads across them), storage services with storage targets, and a kernel client. It supports RDMA and can mirror metadata and data between pairs of servers, which it calls buddy mirroring. Many sites choose it because it is easier to set up than Lustre.

HDFS

The Hadoop Distributed File System, modelled on the Google File System paper, makes different trade-offs because it serves batch analytics jobs that read whole files and write new ones:

  • The NameNode keeps the whole namespace and the block map in RAM. Every file costs NameNode memory, so millions of small files hurt.
  • DataNodes store blocks, typically 128 MB each, as ordinary files on their local disks.
  • Each block has three replicas by default, placed rack-aware: the first on the writer's node (or a random node in the writer's rack), the second on a node in a different rack, the third on a different node in that same remote rack.
  • Files are write-once: one writer, then only appends and truncates. No writes in the middle of an existing file. That single rule removes almost the whole cache-coherence problem.
  • High availability uses an active and a standby NameNode sharing an edit log through a quorum of JournalNodes, with ZooKeeper deciding which one is active.

HDFS is not POSIX, and applications reach it through a client library rather than a kernel mount. For the workloads it was built for (scan huge files, write new ones), that is the right trade.

pNFS, the standard version

pNFS puts the same architecture inside the NFS protocol. The layout types are files, blocks and flexible files (RFC 8435). Flex files is the one most relevant now. Its data servers can be plain NFSv3 or NFSv4 servers, and the layout can tell the client to mirror writes to several data servers itself. An unmodified Linux NFSv4.2 client can therefore do parallel, client-replicated I/O against a scale-out back-end without any special client software.

Computed placement: Ceph

Ceph removes the lookup step for data altogether. Its base layer, RADOS (Reliable Autonomic Distributed Object Store), stores named objects on OSDs (object storage daemons, usually one per disk). Any client can compute where an object lives from a small, shared cluster map. Block devices (RBD), S3-compatible object storage (RGW) and the filesystem (CephFS) are all built on RADOS.

The pieces

  • Monitors (MONs): a small odd number, typically 3 or 5, that use Paxos to agree on the cluster maps: which monitors exist, which OSDs exist and whether they are up, the CRUSH map, and the CephFS metadata server map. Every map has an epoch number that increases with each change.
  • OSDs store objects. The current backend, BlueStore, writes data directly to the raw block device and keeps its own metadata (object names, extent maps, allocation state) in RocksDB, an LSM-tree key-value store. That is the write-optimised alternative to the B-trees of lesson 4.
  • Managers (mgr) collect statistics and run the dashboard and orchestration modules.
  • MDS daemons exist only for CephFS, to serve the namespace.

From an object name to disks

object "rbd_data.1f2e.0000000000000a3c" in pool 7
   │  hash(name), stable-mod pg_num (say 256)
   ▼
placement group 7.b2
   │  CRUSH(7.b2, pool's rule, cluster map)
   ▼
acting set [osd.6, osd.1, osd.11]        osd.6 is the primary

A pool is a namespace with its own redundancy settings. Objects in a pool are hashed into a fixed number of placement groups (PGs), and CRUSH maps each PG to a list of OSDs. Every object follows its PG. PGs make the system manageable. Ceph tracks state, peers replicas and recovers data per PG, so it deals with thousands of PGs rather than billions of objects. A typical target is around a hundred PGs per OSD, and the PG autoscaler adjusts pools toward it.

The client computes the mapping itself and sends the operation straight to the PG's primary OSD. For a replicated pool the primary forwards the write to the other OSDs in the set and acknowledges the client only when all of them have persisted it. No metadata server and no lookup table sit in the data path.

CRUSH

CRUSH (Controlled Replication Under Scalable Hashing) is a deterministic function over a hierarchy of the cluster: root, then data centres, rooms, racks, hosts, and OSDs at the leaves, each with a weight (usually its capacity in TiB). A rule says how to descend. For example, "choose 3 distinct racks, then one OSD under each" makes the rack the failure domain: losing a rack loses at most one copy of anything.

At each level CRUSH chooses among the children with the straw2 algorithm. Every child draws a pseudo-random straw length from a hash of (PG, child), scaled by its weight, and the longest straw wins. The draw for one child does not depend on the others, so adding or removing a disk only moves data to or from that disk. The lab implements straw2 and measures exactly this.

Replicated and erasure-coded pools

A replicated pool keeps size copies (typically 3) and keeps serving I/O while at least min_size (typically 2) are available. An erasure-coded pool splits each object into k data chunks plus m coding chunks on k+m OSDs, and survives the loss of any m. Erasure coding saves capacity and costs CPU, latency and small-write performance. It suits object storage and capacity tiers, and it can back CephFS and RBD data when overwrites are enabled on the pool.

When an OSD stops responding, its PGs become degraded and keep serving from the remaining copies. If it stays down past a timeout (ten minutes by default), the monitors mark it out, CRUSH computes new homes for its PGs, and recovery copies the data from the surviving replicas spread across the whole cluster.

CephFS

CephFS adds a POSIX namespace. File data is striped into RADOS objects (4 MiB by default) whose names derive from the inode number and the object index, so clients compute data locations exactly as above. Metadata lives in its own RADOS pool, served and cached by MDS daemons that journal their changes into RADOS too.

  • Several MDS daemons can be active at once, each owning a rank. Dynamic subtree partitioning moves busy parts of the directory tree between ranks as load shifts. Administrators can also pin a subtree to a rank with the ceph.dir.pin extended attribute. Standby daemons take over a failed rank.
  • Coherence uses capabilities (caps). The MDS grants a client caps on each inode it uses: to read and cache, to write and buffer, to cache attributes. When another client needs conflicting access, the MDS revokes caps, and the holder flushes and gives them back. Lustre's locks, GPFS's tokens and NFS delegations follow the same idea.
  • Clients are the in-kernel ceph filesystem (in mainline Linux) or the userspace ceph-fuse, which is slower but can be upgraded without touching the kernel.
  • If a client stops answering cap revocations, the MDS evicts it and adds it to the OSD map's blocklist. Every OSD then rejects that client's I/O even if it comes back to life. That is fencing done through the cluster map.

Three more designs

  • GlusterFS has no metadata server. Each directory's hash space is split into ranges, one per brick (a server directory that stores data), recorded as extended attributes on the directory. A client hashes a file's name to find its brick. Translators stack features such as replication and dispersal (erasure coding) on top. Renames and rebalancing are awkward, because a renamed file's new name hashes elsewhere and needs a pointer file. Red Hat's commercial Gluster product reached end of life at the end of 2024, so check the state of the upstream project before choosing it.
  • JuiceFS keeps metadata in a database you choose (Redis, TiKV, MySQL, PostgreSQL, SQLite and others) and file data in an object store such as S3, cut into large chunks that are stored as smaller blocks. The client is usually FUSE (from lesson 5's point of view, a userspace filesystem) with a local cache. The filesystem's metadata performance is the database's performance.
  • Google Colossus, the successor to the Google File System, uses a scalable metadata service whose Curators store filesystem metadata in Bigtable. Data flows directly between clients and file servers called D servers. A database solves the metadata scaling problem the single GFS master could not.

Computation costs nothing at lookup time, but every participant needs the same map, and a map change moves data whether you like it or not. Consistent hashing needs many virtual nodes per server to balance well; straw2 balances without them. The lab measures all of this.

Erasure coding halves the hardware bill compared with triple replication, at the price of more network and disk traffic during rebuilds and slower small writes. That is why many systems replicate hot or metadata-heavy data and erasure-code the bulk.

Where the redundancy lives matters as much as which scheme:

  • Inside each server: RAID or a local erasure code. A dead disk is rebuilt inside the box, but a dead server makes its data unavailable until a failover partner takes over. Classic Lustre works this way.
  • Across servers: replicas or chunks on different machines, chosen by placement rules. A dead server or rack does not interrupt service. Ceph, HDFS, GlusterFS and BeeGFS buddy mirroring work this way.
  • By the client: the client writes each copy itself. pNFS flex files mirroring and Lustre FLR work this way.

Spreading replicas over many servers also speeds up recovery. When one disk fails, its data is rebuilt from many disks onto many disks in parallel (declustered recovery), instead of from one mirror onto one spare. The lab shows each surviving node contributing an almost equal share of the rebuild.

Consistency and caching at scale

POSIX promises that a read() after a write() sees the new data, even on another machine, that rename() is atomic, and that byte-range locks work. On one machine these promises are cheap because one kernel sees everything (lesson 5). Across many machines, every access that might conflict requires coordination. The systems differ in how much they coordinate:

Metadata hot spots

Parallel jobs have two classic I/O patterns:

  • N-to-N: each of N processes writes its own file. Data bandwidth is easy, but N creates in one directory at the same instant all go to the metadata server that owns that directory and serialise on its lock. At tens of thousands of processes that becomes the bottleneck.
  • N-to-1: all processes write different regions of one shared file. Metadata is cheap, but locks become the problem. If two processes' regions share a stripe or a lock extent, their locks bounce back and forth. Aligning each process's region to the stripe size avoids it.

The fixes are spreading one directory over several metadata servers (Lustre striped directories, CephFS directory fragmentation and pinning), or changing the application to create files in many subdirectories. Benchmarks such as mdtest exist because metadata rates, not bandwidth, are the usual limit.

Failure detection, quorum and fencing

Nodes check on each other with heartbeats, and a timeout declares a silent node failed. A timeout cannot tell a dead node from a slow one, a partitioned one, or one paused for a long garbage collection or a kernel hang. Every design must stay correct when a node declared dead comes back and carries on as if nothing happened.

  • Leases. Grant rights for a limited time only. A holder that cannot renew must stop using them, and the grantor waits until the lease has surely expired before giving the rights to someone else. NFSv4 state (lessons 6 and 7), Lustre lock callbacks and CephFS client sessions all work this way.
  • Quorum. Decisions about membership and maps require agreement from a majority of a small, odd-sized group: Paxos in Ceph's monitors, Raft in etcd and many newer systems, ZooKeeper for HDFS failover. Three members survive one failure; five survive two. In a network split, at most one side can have a majority, so at most one side keeps changing state. That prevents split brain, where two halves each believe they are in charge.
  • Fencing. Make the old owner harmless before anyone takes over: cut its power through a management controller (STONITH, "shoot the other node in the head"), revoke its storage access (SCSI persistent reservations), or blocklist it (Ceph). Epoch numbers are a lighter form: every map or lease carries a number that only grows, and servers reject requests stamped with an old one.
  • Replay and reconciliation. After a restart, state is rebuilt from the survivors: Lustre clients replay uncommitted requests, NFSv4 clients reclaim locks during the grace period, Ceph OSDs compare PG logs during peering, and HDFS DataNodes send block reports to the NameNode.
Key idea

You cannot tell a dead node from a slow one. So a distributed system makes a node harmless before it treats the node as dead: its lease runs out, it is fenced, or its requests carry an epoch the others will refuse.

Thinking about performance

  • Aggregate bandwidth grows roughly with the number of data servers, provided there are enough clients and files are striped widely enough. One file's bandwidth is limited by its stripe count.
  • Metadata operations are usually the real limit. Creating a file can mean a metadata-server transaction plus object creation on data servers. A stat() can involve several servers.
  • Tail latency adds up. A read striped over 16 servers finishes when the slowest one answers, so one sick disk slows everything that touches it.
  • Network transport matters at the top end. This is where RDMA (lesson 8) comes in: Lustre's o2ib, GPFS verbs, BeeGFS RDMA and NFS over RDMA all exist to stop the CPU being the bottleneck.

The standard tools: fio for single-node workloads of any shape, IOR for parallel bandwidth from many MPI processes (both N-to-N and N-to-1), mdtest for metadata operations per second, and elbencho for distributed file, block and object tests. The IO500 list combines bandwidth and metadata results into one ranking. Always benchmark the access pattern your applications actually have.

Where NFS 4.2 and RDMA fit

Native clients (Lustre, GPFS, CephFS, BeeGFS) know the layout and speak the coherence protocol directly, which gives them the best performance and full POSIX semantics. They also have to be installed and kept compatible with the servers on every client machine.

NFS is the client every operating system already has. Several pieces from this course let it reach scale-out performance:

  • pNFS with flex files gives an NFSv4.2 client layouts, parallel I/O to many data servers, and client-side mirroring;
  • multiple connections (the nconnect mount option) and session trunking spread one mount's traffic over several TCP connections or server addresses;
  • NFS over RDMA (lesson 8) removes the copies and protocol work that limit a single client at high link speeds;
  • the NFSv4.2 operations from lesson 6 (server-side copy, clone, sparse files, space reservation) move work to the servers.

A common modern pattern is therefore a scale-out back-end, open source or commercial, that presents NFSv3 or NFSv4.x, often over RDMA, to unmodified clients. The trade-off is semantics. Unless the server hands out delegations, those clients get close-to-open consistency (lesson 7). A native Lustre or GPFS client gets lock-based POSIX coherence.

Check yourself

Why does hash mod N move about 90% of the data when an 11th node joins a 10-node cluster?

An object stays put only if h mod 10 == h mod 11, which holds for about one value in eleven. Every other object changes node. Consistent hashing and straw2 move only the objects the new node takes over, about 1/11.

A Lustre file has stripe_size 1 MiB and stripe_count 4. Which object in its layout holds byte offset 9.25 MiB, and at what offset inside that object?

Stripe number 9, so object index 9 mod 4 = 1. Inside it: (9 / 4) × 1 MiB + 0.25 MiB = 2 MiB + 0.25 MiB = 2.25 MiB.

What must a Lustre client have before it may cache a file's data, and where does each piece come from?

The file's layout, which comes from the MDS when the file is opened, and an LDLM extent lock covering the byte range, which comes from the lock server on the OST holding that object. The cache is valid only while the lock is held. A conflicting request makes the server send a blocking callback, and the client flushes and drops that range.

What is a Ceph placement group, and why not run CRUSH for every object?

A PG is a hash bucket of objects within a pool. CRUSH maps PGs to OSDs, and objects follow their PG. That bounds the state the cluster must track, peer and recover to thousands of PGs instead of billions of objects, and it still spreads data evenly when there are enough PGs per OSD.

Compare 3× replication and 8+3 erasure coding on raw overhead, failures survived, and rebuild reads.

Replication: 3.0× raw, survives 2 failures, a lost copy is rebuilt by reading 1 replica. 8+3: 1.375× raw, survives 3 failures, but rebuilding one lost chunk reads 8 chunks, and small overwrites need read-modify-write of the stripe.

Why can't a cluster simply wait for a timeout and then give a silent node's locks to someone else?

The node may only be slow. If it wakes up, it still believes it holds the locks and may write stale data over the new owner's changes. The cluster must first make it harmless: wait for its lease to expire, fence it (power, storage access, blocklist), or reject its requests by epoch.

Ten thousand processes each create one file in the same directory at the same moment. Why is that slow, and what are two remedies?

All the creates go to the one metadata server that owns the directory and serialise on that directory's lock. Remedies: spread the directory over several metadata servers (Lustre striped directories, CephFS fragmentation or pinning), or have the application create files in many subdirectories.

Why is HDFS not POSIX, and why is that acceptable for its job?

Files are write-once (appends and truncates only, one writer), access is through a library, and the NameNode holds all metadata in RAM. Analytics jobs scan large files and write new ones, so they do not need in-place updates or cross-client coherence, and dropping them removes most of the hard problems.
