Lesson 7 · Network

Caching across the network

Every NFS client keeps its own copy of the data, the attributes and the names it has seen. This lesson is about when those copies are allowed to be wrong, for how long, and what the protocol and the Linux client do to bound it.

After this lesson you can
  • list what the Linux NFS client caches and what makes each cache go stale;
  • predict how long a change made on one machine stays invisible on another, from the mount options alone;
  • explain close-to-open consistency and write programs that rely on it correctly;
  • follow a write from write() to stable storage on the server, and say where errors surface;
  • describe how delegations replace polling with a promise, and compare that with AFS, SMB, CephFS, Lustre and GPFS;
  • diagnose a "my change did not show up" report with mountstats, cache counters and tracepoints.

Two kernels, one file

On a single machine, cache coherence comes for free. Lesson 5 showed that there is one page cache per file, inside one kernel. When process A writes and process B reads, B reads the very page A modified. There is no second copy to go stale.

With NFS there are at least three copies of every popular file: the server's page cache (and its disk), and the page cache of each client that has read the file. When client A writes, nothing happens on client B. B's kernel has no idea the file changed until it asks the server, and asking costs a round trip. So every network filesystem picks a point on a spectrum:

  • Ask every time. Every read and every stat goes to the server. Always correct, and slow: a round trip per call, and the server carries the full load of every client.
  • Poll. Keep a copy and recheck it now and then. Fast, but a change can stay invisible until the next check. NFSv3 does this, and so does NFSv4 when it has nothing better.
  • Get a promise. The server promises to tell the client before anyone else changes the file. While the promise holds, the client's copy is correct by construction and it never needs to ask. NFSv4 delegations, AFS callbacks, SMB leases, CephFS capabilities and Lustre locks are all versions of this idea.

NFS chose polling as its base and added promises later. The rest of this lesson follows that order: what is cached, how polling works and what it guarantees, then delegations, then how other systems made different choices.

What the client caches

"The NFS cache" is really several caches with different lifetimes. All of them live in the client's RAM unless you add FS-Cache.

The server caches too. Its page cache holds recently read and written data, nfsd keeps recently used files open in its own file cache so it does not reopen them for every NFSv3 READ, and it caches export decisions it got from rpc.mountd. None of these change what clients see, because the server's caches sit behind its own kernel's coherent page cache. The hard problem is purely on the client side.

Key idea

The attribute cache is the gatekeeper. Data and names are trusted exactly as long as the attributes say nothing changed. Almost every NFS coherence rule is a rule about when to refetch attributes.

Polling: the attribute cache

When the client needs a file's attributes (for stat, for a read that must check the size, for a permission check), it looks at how old its cached copy is. If the copy is younger than the file's current attribute timeout, it uses it. If not, it sends GETATTR, or gets fresh attributes some other way. Many replies carry attributes as a side effect: NFSv3 READ, WRITE and LOOKUP replies include post-operation attributes, and the Linux NFSv4 client appends GETATTR to most COMPOUNDs. Every such reply refreshes the cache.

The four timeouts

The timeout adapts

The timeout of each inode starts at the minimum. Each time the client refetches the attributes after the timeout has run out and finds nothing changed, it doubles the timeout, up to the maximum. As soon as a refetch shows a change, the timeout drops back to the minimum. Files that never change are checked about once a minute; files that keep changing are checked every few seconds. The code is a few lines in nfs_update_inode() in fs/nfs/inode.c, operating on nfsi->attrtimeo.

This is the worst case to keep in mind: on a default mount, a client that only calls stat or keeps reading a file it already has open can serve stale attributes and stale data for up to acregmax seconds (60 by default) after another machine changed the file. Directories use acdirmin/acdirmax, so a file created by another client can take 30 to 60 seconds to appear in a cached listing.

From stale attributes to stale data

When fresh attributes arrive, the client compares them with what it had. If the file changed and the change was not its own doing, it sets NFS_INO_INVALID_DATA on the inode. The next read() or mmap fault sees the flag and throws away every cached page of the file with invalidate_inode_pages2(), then rereads from the server. The invalidation is whole-file. One byte changed by another client in a 10 GiB file costs this client its whole cached copy of that file.

"Not its own doing" matters. When this client writes, the server's change attribute moves too, and the client must not throw away its own fresh pages. NFSv3 solves this with weak cache consistency (WCC) data: WRITE, SETATTR, CREATE and other modifying replies carry the file's size, mtime and ctime from just before the operation as well as after. If the "before" values match the client's cache, nobody else touched the file in between, and the client can simply adopt the "after" values. NFSv4 operations that modify a directory return the directory's change attribute from before and after the operation (change_info4) for the same purpose.

Tuning: noac, actimeo, lookupcache

  • noac makes every attribute check a GETATTR and every write synchronous. Use it only for files that several machines change concurrently without locks, and expect a large slowdown. Lab B4 counts roughly one GETATTR per stat.
  • actimeo=N with a large N suits read-only data that never changes, such as a published software tree. With nocto as well, the client almost never asks.
  • lookupcache=all (default) caches positive and negative lookups. lookupcache=positive stops caching "no such file" answers, which helps when one machine waits for a file another machine will create. lookupcache=none revalidates every lookup with the server.

Detecting change: timestamps and the change attribute

To decide "did the file change?", an NFSv3 client compares mtime, ctime and size. That only works if every change produces a different value. Timestamps in Linux are taken from a coarse clock that ticks once per jiffy (1 to 10 ms, depending on the kernel's HZ setting), because reading a fine-grained clock on every write is expensive. Two writes inside the same tick get the same mtime. If client B fetches attributes between those two writes, it caches mtime T, the second write also leaves mtime T, and B never notices the second change. Its cache stays wrong until something else changes the file.

NFSv4 fixes the comparison with the change attribute: a 64-bit value that the server must change every time the file's data or metadata changes. Linux filesystems keep it in inode->i_version. ext4, XFS and btrfs maintain a real counter, and nfsd returns it. For filesystems without one, nfsd builds the change attribute from ctime, which brings back the granularity problem.

Two refinements followed.

  • change_attr_type (NFSv4.2) lets the server state whether its change attribute only ever increases. If it does, a client can tell which of two values is newer, so a reply that arrives late cannot roll its cache back to old attributes.
  • Multigrain timestamps (Linux 6.13) make the kernel use a fine-grained clock for ctime and mtime only when someone has queried the file's timestamps since the last change. Nobody looking means coarse and cheap; a recent stat or GETATTR means the next change gets a distinct timestamp. That keeps ctime-based change detection reliable without paying the fine-grained cost on every write. Filesystems opt in with a flag; ext4, XFS, btrfs and tmpfs were converted in 6.13.

Close-to-open consistency

Polling alone gives no ordering guarantee at all: a change shows up "eventually, usually within a minute". NFS clients add one rule on top that makes ordinary workflows correct. It is called close-to-open consistency (CTO):

The guarantee

If client A writes a file and closes it, and client B opens the file after A's close() has returned, B sees everything A wrote.

Two mechanisms implement it:

  • Flush on close. A's close() calls the NFS ->flush method, which writes every dirty page of the file to the server and waits for the COMMIT. close() does not return until the server has the data on stable storage.
  • Revalidate on open. B's open() fetches fresh attributes from the server even if the cached ones have not timed out. NFSv3 sends a GETATTR (or ACCESS, which returns attributes too). NFSv4 asks for the attributes inside the OPEN COMPOUND, so this costs no extra round trip. If the change attribute differs from B's cached value, B's cached pages are invalidated.

The rule says nothing about files that stay open. In the diagram, B opened the file before A closed it, so B's later reads may return old data for as long as its attribute cache allows. That is correct behaviour under CTO. Programs that coordinate through NFS must therefore follow the pattern the rule supports: the writer finishes and closes; the reader opens after that. A very common correct use is "write to a temporary name, close, then rename() over the real name": the rename is atomic on the server, and any reader that opens the name afterwards gets the complete new file.

The cost of CTO is one attribute round trip per open (free inside an NFSv4 OPEN) and a synchronous flush on every close of a written file. The mount option nocto drops the open-time revalidation and trusts the attribute cache instead. That suits read-only or single-writer data and makes open() cheaper. Lab B1 shows the difference: after a change on the server, a default mount sees it at the next open, and a nocto,actimeo=60 mount keeps showing the old contents for up to a minute.

Pitfall

mmap with MAP_SHARED is not coherent between clients, and appends are not atomic across clients. The open(2) man page warns that O_APPEND on NFS can corrupt files when several clients append at once: each client computes "end of file" from its own idea of the size, so two clients can write to the same offset. Logs written by several machines into one NFS file need locking, or one file per writer.

Locks as coherence points

Close-to-open covers programs that open, work and close. Databases and mail servers keep files open for hours and coordinate with byte-range locks (fcntl(F_SETLKW), lockf). The Linux client turns locking into a coherence point as well. In do_setlk() in fs/nfs/file.c:

  1. Before asking the server for the lock, the client writes back the file's dirty pages.
  2. It sends LOCK (NFSv4) or an NLM request (NFSv3) and waits until the server grants it.
  3. Unless it holds a delegation for the file, it then marks the cached attributes and data invalid. The next read refetches attributes, and if the file changed, rereads the data.

Unlocking flushes dirty data first, so the next locker on another client sees it. Together these give the guarantee a lock-based program expects: whatever the previous lock holder wrote is visible to the next one. Lab B6 shows a lock pulling fresh data through a nocto,actimeo=60 mount that otherwise shows stale contents.

Two consequences surprise people:

  • Locking is expensive on NFS. Every lock costs a round trip, a flush, and possibly a reread of the file. Some applications take and drop locks thousands of times a second and become unusable on NFS for this reason.
  • Byte-range locks invalidate the whole file. Locking bytes 0 to 99 still discards cached pages for the rest of the file if the change attribute moved.

The local_lock= mount option (flock, posix, all) makes the chosen lock types local to the client. That is only safe if a single client uses the files, because the server and other clients never see those locks.

Errors arrive late

Because write() returns before any RPC is sent, it cannot report errors that only the server knows about: a full filesystem (ENOSPC), an exceeded quota (EDQUOT), or an I/O failure (EIO). Those errors come back on the WRITE or COMMIT reply, and the client records them against the file's mapping (the errseq_t mechanism from lesson 5). The application sees them on the next fsync() or on close().

On a local filesystem close() almost never fails, so much code ignores its return value. On NFS, close() runs the flush, and it is often the first and only place a write error is reported. A program that writes a file, ignores close()'s result, and prints "saved" may have saved nothing. Robust code calls fsync() and checks it, then checks close().

The server helps from its side. If nfsd sees a writeback error on a file, it changes its write verifier. Every client with uncommitted data then sees a verifier mismatch on its next COMMIT and resends, instead of assuming data reached disk that never did.

The async export, again

Lesson 6 warned about the async export option. In terms of the diagram above: with async, nfsd answers WRITE and COMMIT without waiting for its disk, with the same verifier as always. The client marks the page clean and frees it. If the server then loses power, the data is gone, the verifier after reboot does not help (the client no longer has the pages), and no application ever gets an error. sync, the default, keeps the protocol honest: UNSTABLE writes may still sit in server RAM, but COMMIT really waits for the disk.

Delegations: the server promises to call

Polling has a floor: the client must ask, at least at every open. NFSv4 delegations remove that floor for files that only one client is using, which in practice is most files.

When a client OPENs a file, the server may add a delegation to the reply. The client does not ask for it; the server decides, based on whether anyone else has the file open and whether it can reach the client's callback channel.

  • A read delegation promises that no other client will open the file for writing without the holder being told first. The holder may open the file for reading again without contacting the server, and may trust its cached attributes and data indefinitely.
  • A write delegation promises that no other client will open the file at all without the holder being told first. The holder may also cache writes past close(): the Linux client starts writeback at close but does not wait for it (nfs4_file_flush()), because nobody can see the file until the delegation is recalled, and the recall forces the flush. It can also handle locks locally.

While a delegation is held, opens, closes, stat calls and reads of cached data generate no RPCs at all. A build that opens the same headers thousands of times, or a program that repeatedly stats its config file, runs at local-filesystem speed.

The recall

When a conflicting request arrives, the server must take the promise back before it can proceed. It cannot block the other client indefinitely, so the recall is a short protocol of its own:

Step by step:

  1. B's OPEN for writing conflicts with A's read delegation. The server answers B with NFS4ERR_DELAY (in the Linux source, nfserr_jukebox), which tells B to retry after a short pause that grows on each retry.
  2. The server sends CB_RECALL to A, carrying the delegation's stateid. A replies at once to acknowledge it.
  3. A puts its state back on the server. With a write delegation it flushes dirty data. Any opens and locks it handled locally become real server state (an OPEN with claim type CLAIM_DELEG_CUR_FH in 4.1, then LOCK). Then it sends DELEGRETURN.
  4. B's retried OPEN succeeds. A's later opens of the file go to the server like any other, with close-to-open rules again.

If A does not return the delegation within one lease period (90 seconds by default on Linux), the server revokes it and lets B proceed. A learns about the revocation from status flags in its next SEQUENCE reply and must assume any of its unflushed changes conflict with B. Revocation is rare in practice and always means something went wrong on the client or the network.

A conflicting GETATTR does not always need a full recall. With a write delegation outstanding, the holder may have cached writes that changed the size and change attribute. The server can send CB_GETATTR to the holder to learn the current values and answer the other client without taking the delegation away. Recent Linux nfsd does this.

Delegations in Linux nfsd

nfsd implements a delegation as a VFS lease on the server's file (the same mechanism as fcntl(F_SETLEASE), which Samba also uses). Anything that would break a lease breaks the delegation: an NFSv4 OPEN from another client, an NFSv3 request that writes the file (the v3 client gets NFS3ERR_JUKEBOX and retries), and a local process on the server opening the file for writing. That last case is why Lab B7 can trigger a recall with a plain echo >> on the server: the echo blocks until the client returns the delegation.

Some practical details of the Linux server:

  • It has granted read delegations for many years. Write delegations arrived in Linux 6.6, for OPENs with write access when nothing else conflicts.
  • It only grants delegations to clients whose callback path works. An NFSv4.0 client behind NAT gets none (lesson 6).
  • It remembers recently recalled files for a short time and does not hand out a new delegation on them immediately, to avoid recall storms on contended files.
  • The delegations each client holds are listed in /proc/fs/nfsd/clients/*/states with type: deleg.

Newer promises: timestamps and directories

Delegated timestamps (RFC 9754) fix an awkward corner of write delegations. Without them, the server sets mtime when a WRITE arrives, which with a write delegation can be long after the application wrote, and stat on the client either shows a wrong mtime or forces a flush to get the real one. With delegated timestamps the delegation holder owns atime and mtime: it sets them as the application writes, reports them when the server asks with CB_GETATTR, and sends them with SETATTR when it returns the delegation. The Linux client supports this since 6.11. In the 6.18 WSL kernel used for this course the server side is compiled out (CONFIG_NFSD_V4_DELEG_TIMESTAMPS).

Directory delegations (NFSv4.1, GET_DIR_DELEGATION) do for directories what file delegations do for files. A client holding one can trust its cached listing and, more valuably, its negative dentries: "no file named config.local here" stays true until the server says otherwise. Build tools and language runtimes that probe dozens of non-existent paths for every import benefit most. Notifications (CB_NOTIFY) can tell the holder exactly which entries changed instead of recalling the whole delegation. Linux 6.19 added initial client support, used for ACCESS, CREATE, UNLINK and RENAME, with a module option to disable it.

How other systems keep caches coherent

NFS is the odd one out: its base protocol polls, and promises are an optimisation. Most other distributed filesystems were designed around promises from the start. Lesson 9 covers their architectures; here is how each one answers "may this client use its cached copy?".

The pattern is the same everywhere. A client may cache exactly as much as its current promise covers. A conflicting request makes the server (or lock manager) call the holder back, and the holder flushes before it gives up the promise. What differs is the granularity of the promise (whole file, byte range, attribute class), who keeps track (one server, a metadata server, a distributed lock manager), and what happens when a client stops answering. NFS without delegations falls back to the timer; the others fall back to revoking locks after a timeout and evicting the client.

Polling has one advantage that keeps NFSv3 alive: it costs the server nothing when a client disappears. Every promise is state that must be recovered after a crash and revoked when a client goes silent. Lesson 6 showed how NFSv4 handles that state with leases and grace periods; lesson 9 shows Lustre and Ceph doing the same with eviction and recovery.

FS-Cache: a disk cache under NFS

The page cache is fast but limited by RAM and lost at reboot. FS-Cache adds a second level on the client's local disk. With the mount option fsc, data the NFS client reads is also written to a local cache, and later reads of the same file can come from local disk instead of the network.

  • The kernel side is FS-Cache plus a backend, CacheFiles (CONFIG_CACHEFILES), which stores cached data as files in a directory on a local filesystem. The cachefilesd daemon configures it (/etc/cachefilesd.conf, cache in /var/cache/fscache by default) and culls old data when free space falls below thresholds.
  • NFS reaches FS-Cache through the kernel's netfs helper library, which several network filesystems share.
  • Coherence does not change. Each cached file is keyed by its file handle and stored with coherency data (change attribute, times and size). NFS revalidates attributes exactly as before; if they no longer match, the disk copy is discarded with the page cache.
  • Opening a file for writing invalidates its cached copy and switches caching off for it while it is open. FS-Cache is a read cache.

It pays off for large read-mostly data read by many clients, such as software installations, container images and machine-learning datasets: it removes load from the server and survives client reboots. It does nothing for metadata-heavy work, and a local disk slower than the network makes things worse.

This machine

The WSL kernel used here has CONFIG_FSCACHE=y and CONFIG_NFS_FSCACHE=y, but CONFIG_CACHEFILES is not set. Without a backend, fsc is accepted and caches nothing, so the lab has no FS-Cache experiment.

Failure modes

Hard and soft mounts

When the server stops answering, a hard mount (the default) retries forever. The kernel logs nfs: server X not responding, still trying, and every process touching the mount waits in state D until the server comes back, then continues as if nothing happened. The old intr option has been ignored since Linux 2.6.25; instead the waits are killable, so kill -9 ends a stuck process.

A soft mount gives up after retrans retries and returns EIO (softerr returns ETIMEDOUT instead). That sounds friendlier, but nfs(5) warns that it can silently corrupt data. A timed-out WRITE during background writeback has no system call to return an error to. The page is marked with an error, the data is lost, and only a later fsync or close might report it. Use soft only for read-only data where an error is better than a hang. The softreval option lets a soft mount keep serving cached attributes and names while the server is down.

Silly rename

On a local filesystem you can unlink a file that is still open, and it lives on until the last close. An NFSv3 server keeps no opens, so if the client sent REMOVE, the next READ would fail with ESTALE. The Linux client avoids this with silly rename: when you unlink a file that this client has open, it instead renames it to .nfs followed by 24 hex digits (built from the inode number and a counter), and sends the real REMOVE when the last local user closes it. Lab B8 shows the file appearing and disappearing.

  • rm on a .nfs… file fails with "Device or resource busy" while it is in use.
  • rm -rf dir fails with "Directory not empty" when such a file is inside.
  • If the client crashes, the .nfs… file stays on the server forever and must be cleaned up by hand.
  • Another client that has the file open still loses it: silly rename only protects the client that does the unlink.

NFSv4.1 lets a server promise to keep unlinked-but-open files itself, with the OPEN4_RESULT_PRESERVE_UNLINKED flag in the OPEN reply. Recent Linux clients skip the silly rename when the server sets it.

Stale file handles

ESTALE ("Stale file handle") means the server no longer recognises a handle the client cached. Usually another client removed the file, or replaced it with rename(), so the inode behind the handle is gone. For system calls that take a path, the Linux VFS retries the lookup once from scratch when it gets ESTALE, so stat("file") after another client replaced the file normally just works. A program holding an open descriptor to the replaced file gets ESTALE on its next read; it must reopen by name.

Lost leases and lost locks

If a client cannot reach the server for longer than the lease, the server may release its locks. Since Linux 5.19 nfsd is a "courteous server" that keeps an expired client's state until another client actually conflicts with it, so short partitions usually cost nothing. If the locks really were given away, the Linux client by default does not try to take them back, because the file may have changed in between. Operations that depend on the lost lock fail with EIO. The nfs.recover_lost_locks=1 parameter restores the old, riskier behaviour of re-requesting them.

Clocks

The server stamps mtime with its own clock. If client and server clocks differ, a client comparing file times with its own "now" gets confused: make prints "Clock skew detected" and may rebuild too much or too little, and tools that skip "recently modified" files misjudge them. Run NTP (chrony or systemd-timesyncd) on every machine that shares files.

Diagnosing a caching problem

A typical report: "machine B does not see the file machine A just wrote." Work through it in order.

  1. Check the options actually in force. nfsstat -m on both machines. Look for nocto, actimeo, noac, lookupcache, the version, and whether another mount of the same export (without nosharecache) set the options first.
  2. Check the access pattern against the guarantees. Did A close (or fsync, or unlock) before B opened (or locked)? If B kept the file open, or polls with stat, it is relying on the attribute timeout and up to 60 seconds of staleness is expected. If B is waiting for a file to appear, negative dentry caching may be hiding it; lookupcache=positive fixes that.
  3. Count what the clients do. opcount.sh shows the RPCs a command causes. events.sh shows the client's cache counters from the events: line of mountstats: inoderevalidates, datainvalidates, attrinvalidates, vfsflush, sillyrenames and 22 more. A cat that produces no GETATTR on a default mount means the client held a delegation, or the open was served from a cache you did not expect.
  4. Trace it. The client has tracepoints for exactly these decisions:

# trace-cmd report
    The server side adds -e nfsd. trace-cmd list -e nfs lists the rest.
  5. Check delegations on the server. /proc/fs/nfsd/clients/*/states shows which client holds what. A delegation that never gets returned shows up there and in the server's log as a revocation.
  6. Test cold. sync; echo 3 | sudo tee /proc/sys/vm/drop_caches on the client drops its page cache, dentries and inodes, so the next access shows the server's current state. If that fixes it, the bug is staleness, not a server problem.

Check yourself

Client B opened a file, then client A wrote it and closed it. B calls read() again on its open descriptor. What does B see?

Possibly the old data. Close-to-open only promises fresh data to opens that happen after the writer's close. B's open came first, so B relies on its attribute cache: it sees the change only once the attribute timeout runs out (3 to 60 seconds for files) and a GETATTR shows a new change attribute, or when it reopens the file or takes a lock.

A file has not changed for ten minutes. Another machine changes it now. On a default mount, how long can a client that only calls stat keep reporting the old size?

Up to 60 seconds. The adaptive timeout of an unchanged file has grown to acregmax, 60 s by default, so the next GETATTR can be up to a minute away.

Why can two writes in quick succession be invisible to an NFSv3 client, and what does NFSv4 use instead?

NFSv3 detects change through mtime, ctime and size. Timestamps come from a coarse clock, so two writes within one tick share an mtime; if the client fetched attributes between them, the second write looks like no change. NFSv4 uses the change attribute, which must differ after every change (on Linux, the inode's i_version counter). Multigrain timestamps in Linux 6.13 also make ctime and mtime fine-grained when someone has looked at them.

A program on an NFS mount takes and releases a POSIX lock around every small read. Why is it slow, and why does the lock help correctness?

Each lock and unlock is a round trip to the server, unlocking flushes dirty data, and after each lock the client marks its cached attributes and data invalid, so it may reread the whole file. That same invalidation is what makes the lock useful: whatever the previous lock holder wrote and flushed is visible after the lock is granted.

Client A holds a read delegation. Client B opens the file for writing. List the messages.

B's OPEN gets NFS4ERR_DELAY. The server sends CB_RECALL to A, A acknowledges it, moves any locally handled opens and locks to the server, and sends DELEGRETURN. B retries the OPEN and succeeds. If A does nothing for a lease period, the server revokes the delegation.

A program writes 1 GiB to an NFS file, ignores the return value of close(), and reports success. The user's quota was exceeded. What happened?

write() succeeded because it only filled the client's page cache. The WRITE replies came back with EDQUOT during writeback, and the error was reported by close(), which the program ignored. The data is not on the server. Checking fsync() and close() would have caught it.

Why is a soft mount risky for data you write?

A soft timeout during background writeback has no system call to report to. The pages are marked with an error and the data is dropped; a later fsync or close may report it, but a program that never calls them never learns. A hard mount just waits until the server is back and then completes the writes.

How does what a CephFS or Lustre client may cache differ from what an NFSv3 client caches?

An NFSv3 client caches on its own authority and polls to find out about changes. A CephFS client caches only what its capabilities from the MDS allow, and a Lustre client only what its LDLM locks cover. When another client conflicts, the server calls the holder back and the holder flushes before giving up the cap or lock. Applications get POSIX-like consistency instead of close-to-open.
