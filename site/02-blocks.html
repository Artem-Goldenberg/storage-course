Lesson 2 · The block layer and the device

Block devices and addressing

At the bottom of every storage stack sits a device that knows nothing about files. It stores numbered sectors and moves them by DMA. This lesson covers what that device is, how it is addressed, how Linux queues requests to it, and what "written" means once a request reaches it.

After this lesson you can
  • tell a block device from a character device and read its properties from /sys/block;
  • explain why spinning disks, SATA (Serial ATA, a storage-device interface) SSDs and NVMe drives perform so differently;
  • convert a byte offset to a filesystem block and to a sector address (LBA, Logical Block Address), and explain alignment;
  • trace a request from a filesystem through bio (block I/O, a descriptor of a block input/output operation), blk-mq (multi-queue block I/O) and the driver to the device and back;
  • describe NVMe submission and completion queues, the model that RDMA reuses in lesson 08;
  • explain the device's volatile write cache, FLUSH and FUA (Force Unit Access, durable completion of an individual write), and torn writes.

Block devices and character devices

Linux has two kinds of device file. A character device is a stream of bytes: a terminal, /dev/null, a serial port. You read whatever comes next and usually cannot seek. A block device is a fixed-size array of sectors that you can read and write in any order: a hard disk, an SSD (Solid-State Drive), a USB stick, a partition of one of those, or a virtual disk.

From above, a block device offers one abstraction. You can read sector range N..M into memory, or write memory to sector range N..M. There are no files, names or permissions down here. Everything else in this course is built on that.

ls -l shows the difference in the first character, and shows two numbers where a file would show its size:

$ ls -l /dev/null /dev/sda /dev/sdd
crw-rw-rw- 1 root root 1,  3 Oct  8 22:18 /dev/null
brw-rw---- 1 root disk 8,  0 Oct  8 22:18 /dev/sda
brw-rw---- 1 root disk 8, 48 Oct  8 22:18 /dev/sdd

SCSI stands for Small Computer System Interface, a family of standards that includes commands for storage devices. Linux uses the same SCSI layer for several types of disk.

c marks a character device and b a block device. The pair 8, 48 is the major:minor number. The major number picks the driver (8 is the SCSI disk driver, sd), and the minor number picks the device within it.12 The sd driver reserves 16 minors per disk, one for the whole disk and fifteen for partitions, which is why sda is 8:0, sdb 8:16 and sdd 8:48.2 The file in /dev is only a name; the kernel finds the device by these numbers.

Read that line as: 512-byte logical sectors on 4 KiB physical blocks, claims to be rotational, 4 hardware queues, a volatile write-back cache, and no I/O scheduler. The rotational flag is probably false in reality, since the .vhdx likely sits on an SSD. The kernel only knows what the device reports.

Storage hardware: HDD, SSD and NVMe

The same two operations, read sectors and write sectors, hide hardware that differs in speed by a factor of a thousand. Every design choice above this layer, from filesystem allocators to NFS caching, is shaped by these numbers.

Hard disks: platters, heads, CHS and LBA

A hard disk drive (HDD) stores data magnetically on spinning platters. Each platter surface has a head on an arm; the ring of data under a head at one arm position is a track; tracks are divided into sectors; and the set of tracks at the same arm position across all surfaces is a cylinder.2122

Early PCs addressed sectors by that geometry, as a (cylinder, head, sector) triple, called CHS. The old BIOS interface allowed 1024 cylinders, 255 heads and 63 sectors per track, which caps a disk at about 8.4 GB.24 Drives also stopped having fixed geometry: outer tracks are longer and hold more sectors than inner ones.25 So CHS was replaced by Logical Block Addressing (LBA): sectors are simply numbered 0, 1, 2, … and the drive maps each number to a physical location itself. The conversion from the old scheme, for reference, is LBA = (C × heads + H) × sectors_per_track + (S − 1).26 Every device in this lesson, including SSDs and NVMe drives, is addressed by LBA.

Reading a random sector costs three things:

  • Seek: moving the arm to the right track, typically several milliseconds.27
  • Rotational latency: waiting for the sector to come round. At 7200 rpm one revolution takes 60/7200 s = 8.33 ms, so the average wait is half that, 4.17 ms.
  • Transfer: reading the bits as they pass, very fast once in position.

So a random 4 KiB read costs around 10 ms, and one disk manages on the order of 100 random reads per second, under 1 MB/s.27 Read sequentially, the same disk streams around 200 MB/s.28 That gap of more than a hundred times is why filesystems work so hard to keep a file's blocks next to each other (lesson 03), and why I/O schedulers were invented to sort requests by position.2729

SSDs: NAND flash, the FTL and TRIM

An SSD stores data in NAND flash (named after the NOT-AND logic-gate arrangement), which has no moving parts but two awkward rules:

  • You read and program (write) flash in pages, typically 4 to 16 KiB.3031
  • You cannot overwrite a page. You must first erase it, and you can only erase a whole erase block of hundreds of pages, megabytes in all.3132 Each erase also wears the cells, which survive a limited number of program/erase cycles.33

To hide this, every SSD runs firmware called the Flash Translation Layer (FTL). The FTL keeps a map from each LBA to the flash page currently holding it. When the host writes LBA 1000, the FTL writes the new data to a fresh, already-erased page, updates the map, and marks the old page stale. Nothing is overwritten. Internally, then, an SSD is a log-structured store with a giant lookup table.34

Stale pages pile up, so the FTL runs garbage collection: it picks an erase block with many stale pages, copies the still-valid pages elsewhere, and erases the block. Those copies are writes the host never asked for.35 The ratio of flash writes to host writes is called write amplification, and it is why SSDs slow down and wear faster when nearly full or under heavy random writes.3436 Drives keep spare capacity, called over-provisioning, to give garbage collection room to work.3536

The FTL cannot know when a filesystem deletes a file, because deleting only changes the filesystem's own bitmaps. The discard command, called TRIM on SATA, UNMAP on SCSI and Deallocate on NVMe, tells the drive that a range of LBAs no longer holds useful data, so garbage collection can skip copying it.3537 Linux sends it either continuously (the discard mount option) or in batches (fstrim, usually from a weekly timer).3839

NVMe: submission and completion queues

NVMe stands for Non-Volatile Memory Express.40 It defines how software sends commands to a non-volatile storage device. NAND is the memory that stores the bits; NVMe is the interface used to access the drive. Here we discuss local NVMe devices connected through PCI Express.40

SATA was designed for spinning disks. Its host interface, AHCI (Advanced Host Controller Interface), has a single command queue holding up to 32 commands, shared by every CPU. NVMe was designed for flash on the PCIe (PCI Express, Peripheral Component Interconnect Express) bus, and its central idea is many independent queues in host memory.41

An NVMe queue pair is a submission queue (SQ) and a completion queue (CQ). Both are ring buffers in ordinary RAM. The driver puts 64-byte commands into the SQ; the controller puts 16-byte completion entries into the CQ.4243 The specification allows up to 65,535 I/O queues of up to 65,536 entries each,44 and Linux typically gives every CPU core its own queue pair, so cores submit I/O without sharing a lock.4245 The only thing the CPU writes to the device directly is a doorbell: a register on the device, mapped into memory, that the driver writes to say "the tail of my queue has moved".4246

Key idea: remember this picture

Work requests in a ring in host memory, a doorbell write to tell the hardware, DMA straight to and from application buffers, and a completion queue the host polls or gets interrupted about. This is exactly how an RDMA network card works. In lesson 08 the queue pair becomes a send queue and a receive queue, the completion queue keeps its name, and the device on the other end of the DMA is a network card that can reach another machine's memory.47

Bytes, blocks, sectors and LBA

Three units meet at this layer, and they are easy to mix up:

  • The byte offset is what programs use: "byte 1,000,000 of the disk".
  • The filesystem block is the unit a filesystem allocates and tracks, almost always 4096 bytes on Linux.5253 Block n starts at byte n × block size.
  • The sector is the device's addressing unit, named by its LBA. Its size is the device's logical block size, 512 or 4096 bytes.

Converting between them is division with remainder:

block_number    = byte_offset / block_size        offset_in_block  = byte_offset % block_size
lba             = byte_offset / sector_size       offset_in_sector = byte_offset % sector_size
first_lba(blk)  = blk * (block_size / sector_size)

Inside Linux

The Linux block layer counts in 512-byte units internally, whatever the device's real sector size. A bio's start sector, /sys/block/<dev>/size and the sector counters in /sys/block/<dev>/stat all use 512-byte sectors,54555657 and the driver converts at the bottom. On a 4 KiB-sector device, the kernel simply never issues a request that is not a multiple of 8 of these units.

Sector formats: 512n, 512e and 4Kn

Disks moved from 512-byte to 4096-byte physical sectors around 2010 because larger sectors need less error-correction overhead per byte.5859 Software expected 512, so three kinds of drive exist:

TypeLogical sectorPhysical sectorNotes

4Kn (native)40964096LBAs count 4 KiB sectors, so the same byte has an LBA eight times smaller.

Partition alignment and read-modify-write

On a 512e drive, what happens if you write a single 512-byte sector? The drive cannot write less than 4 KiB of media, so it must read the 4 KiB physical sector, replace the 512 bytes, and write all 4 KiB back. This is a read-modify-write (RMW): one extra read and a larger write, and a window in which a power cut can damage the neighbouring 3.5 KiB.6061

A filesystem writing whole 4 KiB blocks avoids this, but only if its blocks line up with the physical sectors. That depends on where the partition starts. Old DOS partitioning tools started the first partition at sector 63, byte 32,256, which is not a multiple of 4096.62 Every filesystem block then straddled two physical sectors, and every block write became two read-modify-writes:60

Read-modify-write is a pattern you will see at every layer. The page cache does it when you write 100 bytes into the middle of a file that is not cached: it reads the 4 KiB page first.64 RAID 5 does it for writes smaller than a stripe.65 In every case the cure is to write in whole, aligned units.

The Linux block layer

Filesystems do not talk to drivers directly. They hand requests to the block layer, which batches, merges, schedules and dispatches them. Its unit of work is the bio.6667

struct bio and bio_vec

bio (block I/O) describes a block I/O operation in the Linux kernel. For a read or write, it specifies the device, the range of sectors and the memory buffers to transfer data to or from. A bio_vec describes one memory segment by its starting page, byte offset and length; a bio can contain several segments.68

struct bio {                          // simplified, from include/linux/blk_types.h
    struct block_device *bi_bdev;     // which device
    blk_opf_t            bi_opf;      // REQ_OP_READ / WRITE / FLUSH / DISCARD + flags (REQ_FUA, REQ_PREFLUSH, REQ_SYNC)
    struct bvec_iter     bi_iter;     // bi_sector (start, 512-byte units), bi_size (bytes)
    struct bio_vec      *bi_io_vec;   // list of (page, offset, length) memory segments
    bio_end_io_t        *bi_end_io;   // called when the I/O completes
};

A bio says: "transfer bi_size bytes starting at sector bi_sector, to or from these pieces of memory, and call bi_end_io when done".5569 The memory does not have to be contiguous: the bio_vec list can point at scattered pages, and the device's DMA engine gathers or scatters them.4268 A filesystem builds a bio and calls submit_bio(); from then on it is the block layer's job.70

From bio to the device: blk-mq

Step by step:

  1. Plugging. A task that is about to submit several bios can plug its queue. The bios then collect in a per-task list instead of going straight down. When the task unplugs (or sleeps), the list is flushed. This creates batches large enough to merge.71
  2. Merging. A bio for sectors 1960–1967 arriving right after one for 1952–1959 is joined to it, forming one struct request for 1952–1967. Fewer, larger requests are cheaper for every device and much cheaper for a spinning disk.6772
  3. Software queues. Since the multi-queue block layer (blk-mq, released in Linux 3.13 in January 2014;73 the old single-queue path was removed in 5.0)74, each CPU has its own staging queue, so CPUs do not fight over one lock. If an I/O scheduler is configured, requests go into the scheduler at this stage instead, and it decides their order.666772
  4. Hardware queues. Software queues map onto hardware dispatch queues, which correspond to the device's real queues: NVMe queue pairs, or the single queue of a SATA disk.75 WSL's virtual disk exposes 4.
  5. Driver. The driver turns the request into a device command (an NVMe command, or a SCSI CDB) and rings the device's doorbell.
  6. Completion. The device signals completion by interrupt. For the fastest devices, interrupts cost more than they save, so the kernel can instead poll the completion queue in a loop;76 io_uring with IORING_SETUP_IOPOLL on NVMe poll queues does this.7477

Volatile write cache, FLUSH and FUA

When a device reports a write as complete, the data is not necessarily on the media. Many drives, especially consumer ones, have a volatile write cache: DRAM on the drive that accepts writes quickly and writes them to flash or platter later, possibly in a different order. If power fails first, the data in that cache is lost.258687 /sys/block/<dev>/queue/write_cache reads write back when such a cache is present.

Two mechanisms let software get real durability:

  • FLUSH (SCSI SYNCHRONIZE CACHE, ATA FLUSH CACHE, NVMe Flush): write everything currently in the cache to stable media, and only then report completion.8889 In Linux this is a bio with REQ_PREFLUSH.90
  • FUA, Force Unit Access: a flag on a single write meaning "do not report this write complete until it is on stable media". In Linux, REQ_FUA.91

A journaling filesystem's commit uses both: flush the cache so the journal entries written before are stable, then write the commit record with FUA.92 fsync ends in a flush.8693 If the device reports no volatile cache, the block layer drops these flags because there is nothing to flush.94

Pitfall: writing to write_cache

Writing write through into /sys/block/<dev>/queue/write_cache does not change the drive. It only tells the kernel to stop sending flushes.20 On a drive whose cache really is volatile, that turns every fsync into a promise the hardware does not keep.

Enterprise SSDs often have power-loss protection (PLP): capacitors that hold enough energy to write the cache out after power disappears.95 For such drives the cache is effectively non-volatile, flushes are cheap, and they can safely report write-through. This is one reason enterprise SSDs are so much faster than consumer ones for workloads that fsync often, such as databases and NFS servers committing client writes.96

Virtual disks add a layer. On WSL, the device is really a .vhdx file, and a flush from Linux becomes a request to Windows to flush that file and, ideally, the physical drive under it. Whether that happens end to end depends on the hypervisor's configuration,97 which is a good reason never to benchmark durability inside a VM and assume the result holds on bare metal.

Torn writes and atomic writes

A device generally guarantees that a single sector is written entirely or not at all, but makes no such promise for a multi-sector write. If power fails in the middle of a 16 KiB write, some sectors may hold new data and others old: a torn write.9899 NVMe drives advertise how much they can write atomically across a power failure (the AWUPF field),99 and Linux 6.11 added an RWF_ATOMIC flag for pwritev2 so applications can request untorn writes where the device and filesystem support it.100

Before that existed, databases protected themselves. PostgreSQL logs a full copy of a page the first time it changes after a checkpoint (full_page_writes),101 and MySQL's InnoDB writes each page twice, first to a doublewrite buffer, so a torn page can always be repaired from an intact copy.102 Filesystems face the same problem for their own metadata, and solve it with journaling or copy-on-write (lesson 03).

Who uses block devices directly

  • Filesystems, almost always. They turn the sector array into files, which is lesson 03.
  • Stacking drivers: device-mapper (LVM, dm-crypt, thin provisioning) and md RAID take block devices in and present new block devices out. Each layer receives bios, remaps or splits them, and submits new bios below.911
  • Programs reading raw devices: dd, partitioning tools, mkfs itself, backup tools, and some databases that manage their own space. Reading /dev/sdX with ordinary read calls goes through the page cache of the device itself; opening it with O_DIRECT bypasses that cache.103104
  • Network block protocols: iSCSI and NVMe over Fabrics carry sector reads and writes over a network, so a remote disk looks local.41105 Compare that with NFS, which carries file operations (lesson 06). Both run over RDMA (lesson 08).41106107

Lab 02 relies on the fact that a regular file is also an array of bytes. mkfs.ext4 does not care whether its target is /dev/sdd or disk.img,108 so you can build and dissect a filesystem with no root access and no risk to your real disk. The next lesson walks into that image structure by structure.

Check yourself

A filesystem with 4 KiB blocks sits on a device with 512-byte sectors, starting at LBA 0. Which block and which LBA hold byte 10,000,000? Which LBAs does that block cover?

10,000,000 / 4096 = 2441 remainder 1664, so block 2441, 1664 bytes in. 10,000,000 / 512 = 19531 remainder 128, so LBA 19531. Block 2441 covers LBAs 2441 × 8 = 19528 through 19535.

A 7200 rpm disk has an average seek time of 8.5 ms. Roughly how many random 4 KiB reads per second can it serve, and what throughput is that?

Each read costs about 8.5 ms seek + 4.17 ms average rotational latency + a tiny transfer time, roughly 12.7 ms. That is about 79 reads per second, or about 0.3 MB/s. The same disk streams around 200 MB/s sequentially.

On a 512e drive, what does a single 512-byte write cost inside the drive, and why do partitions start at 1 MiB?

The media writes 4 KiB physical sectors, so the drive reads the whole 4 KiB, changes 512 bytes and writes 4 KiB back: a read-modify-write. Starting partitions at 1 MiB (LBA 2048) makes every 4 KiB filesystem block line up with exactly one physical sector, and also with SSD pages and RAID stripes.

Why does an SSD get slower when it is nearly full, and how does discard (TRIM) help?

The FTL never overwrites in place, so it must garbage-collect: pick an erase block, copy its still-valid pages elsewhere, erase it. On a full drive, most pages are valid, so each reclaimed block needs many copies, raising write amplification. Discard tells the drive which LBAs the filesystem no longer uses, so those pages count as stale and need not be copied.

Why does NVMe use many queue pairs when AHCI had one queue of 32 commands?

Flash can serve many requests in parallel, and modern machines have many cores. One shared queue needs a lock that every core contends on and caps the number of requests in flight. With a queue pair per core, each core submits and completes I/O on its own rings with no locking, and tens of thousands of commands can be outstanding.

An application called write and then fsync, both succeeded, and the data was still lost in a power cut. Name two ways this can happen.

The device acknowledged the flush without really persisting its volatile cache, or someone set write_cache to write through so the kernel never sent a flush. In a virtual machine, the hypervisor may also have acknowledged the flush without forcing the host's cache to disk.

What is the difference between FLUSH and FUA?

FLUSH applies to the whole cache: every write completed before it is made durable before it completes. FUA applies to one write: that write is durable before it completes, and nothing is said about other cached writes. Journal commits use a flush followed by a FUA write of the commit record.
