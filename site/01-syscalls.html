Lesson 1 · User space, at the kernel's door

Syscalls and file descriptors

Every storage system in this course, from ext4 to an NFS server across an RDMA fabric, exists to answer a handful of calls like open, read and write. This lesson is about those calls: what actually happens when a C program makes one, and what the small integer called a file descriptor really points to.

After this lesson you can
  • explain what a system call is at the level of CPU modes and registers;
  • use open, read, write, lseek, pread, close and stat correctly, including short counts and errors;
  • draw the three tables behind a descriptor and predict who shares an offset after dup, fork or a second open;
  • tell a file from its name, and explain why a deleted file can still use disk space;
  • name every buffer your bytes pass through before they reach a disk.

Why start at the system call

A program cannot touch a disk, a network card or another process's memory. It runs in a sandbox the CPU enforces. Whenever it needs something from outside that sandbox, it asks the kernel, and the only way to ask is a system call (syscall for short).

That makes the syscall interface the contract for everything below it. When you call read(fd, buf, 4096), you do not know or care whether the bytes come from an NVMe drive, a USB stick, a pipe, or a server in another building speaking NFS over RDMA. The kernel picks the right code based on what fd refers to. Each later lesson in this course is about one implementation behind this same small set of calls, so it pays to know the calls precisely.

What a system call is

A modern CPU runs code at different privilege levels. On x86-64 these are called rings. Your program runs in ring 3, user mode: it can compute and touch its own memory, but the CPU refuses to let it execute privileged instructions, program devices, or read memory outside its own address space. The kernel runs in ring 0, kernel mode, where everything is allowed.

A system call is a controlled jump from ring 3 to ring 0 that can only land at one address the kernel chose at boot. On x86-64 Linux the mechanism is the syscall instruction, and the convention is:

  • the syscall number goes in register rax (read is 0, write is 1, open is 2, close is 3);
  • up to six arguments go in rdi, rsi, rdx, r10, r8, r9;
  • the CPU saves the return address in rcx and the flags in r11, switches to ring 0 and jumps to the kernel's entry point, entry_SYSCALL_64;
  • the kernel uses rax to pick the handler (classically by indexing an array called sys_call_table; recent x86 kernels compile the dispatch into a switch statement for security reasons), runs it, puts the result in rax, and returns to ring 3 with sysret.

The result is a single integer. A value from −4095 to −1 means failure, and its negation is the error number. Anything else is success: a byte count, a new descriptor, or zero.

The libc wrapper

You rarely write the syscall instruction yourself. The C library (glibc on most Linux systems) provides a small wrapper function for each call. The wrapper moves arguments into registers, executes syscall, and translates the result into the C convention: on failure it stores the positive error number in the thread-local variable errno and returns −1. That is why the man pages say "returns −1 and sets errno".

// Three ways to make the same call (lab 01 runs all three)
write(1, msg, len);                      // libc wrapper
syscall(SYS_write, 1, msg, len);         // generic libc entry: any syscall by number
asm volatile ("syscall" : "=a"(ret)      // the bare instruction
              : "a"(1L), "D"(1L), "S"(msg), "d"(len)
              : "rcx", "r11", "memory");

Wrappers sometimes call a different syscall than their name suggests. On current glibc, open() actually issues openat(AT_FDCWD, path, …), and fork() issues clone. You will see this if you run a program under strace.

What a syscall costs

The mode switch itself is cheap compared with I/O: tens to a few hundred nanoseconds on current CPUs, more with some CPU vulnerability mitigations turned on. It is expensive compared with a function call, though, so programs that make millions of tiny calls (one read per byte, say) spend most of their time crossing the boundary. Buffering in user space, batching interfaces like readv, and io_uring all exist to make fewer crossings.

Aside: the vDSO

A few calls only read information the kernel already publishes, such as the current time. For those, the kernel maps a small shared library called the vDSO into every process. clock_gettime and gettimeofday run there entirely in user mode, with no syscall at all. File I/O never qualifies: it always needs the kernel.

Opening a file

#include <fcntl.h>
int open(const char *pathname, int flags, ... /* mode_t mode */);
int openat(int dirfd, const char *pathname, int flags, ... /* mode_t mode */);

open resolves a path to a file, checks your permissions, creates the kernel's bookkeeping for this "open", and returns a file descriptor: a small non-negative integer. POSIX guarantees it is the lowest number not currently in use in your process. Descriptors 0, 1 and 2 are normally standard input, output and error, so the first file you open is usually 3.

The flags argument is a bitwise OR. Exactly one access mode, plus any number of modifiers:

FlagMeaning
O_RDONLY / O_WRONLY / O_RDWRThe access mode: read, write, or both. Checked against the file's permissions once, at open time.
O_CREATCreate the file if it does not exist. Requires the third argument, mode.
O_EXCLWith O_CREAT: fail with EEXIST if the name already exists. The check and the creation are one atomic step, which makes this the classic way to build a lock file.
O_TRUNCIf the file exists and is opened for writing, cut it to length 0.
O_APPENDBefore every write, move to the current end of file, atomically with the write. Explained below.
O_CLOEXECClose this descriptor automatically when the process calls execve. Prevents descriptors leaking into programs you launch.
O_NONBLOCKNever sleep waiting for data; return EAGAIN instead. Meaningful for pipes, sockets and terminals, not regular files.
O_SYNC / O_DSYNCEach write returns only once the data (and, for O_SYNC, all metadata) is on stable storage. Like calling fsync after every write.
O_DIRECTBypass the kernel's page cache and DMA straight between your buffer and the device. Comes with alignment rules. Covered in lesson 05.

When O_CREAT creates a file, its permission bits are mode & ~umask. The umask is a per-process mask, usually 022, which removes write permission for group and others. So the conventional open(path, O_WRONLY|O_CREAT|O_TRUNC, 0666) produces a file with mode 0644 (rw-r--r--).

Pitfall

Permissions are checked at open, not at each read. If someone chmods a file to 000 after you opened it, your descriptor keeps working. A descriptor is a capability: whoever holds it can use it, which is also why you can pass one to another process over a Unix socket.

Reading and writing, including the parts that go wrong

#include <unistd.h>
ssize_t read(int fd, void *buf, size_t count);
ssize_t write(int fd, const void *buf, size_t count);
int close(int fd);

read copies up to count bytes from the file into buf, starting at the descriptor's current offset, and advances the offset by the number of bytes copied. write does the reverse. Both return the number of bytes actually transferred. Three return values need care:

  • 0 from read means end of file (or, for a pipe or socket, that the other end closed). It is not an error.
  • Fewer bytes than asked, called a short count, is legal. A read from a pipe returns whatever is there. A read near the end of a file returns the remainder. A write to a nearly full disk, a full non-blocking pipe, or a socket may write part of the buffer. Your code must loop.
  • −1 means an error, with the reason in errno. Two of them are not really failures: EINTR (a signal handler ran before any data moved, so retry) and EAGAIN (non-blocking descriptor, nothing ready yet).

A correct "write everything" helper therefore looks like this:

static int write_all(int fd, const void *buf, size_t len)
{
    const char *p = buf;
    while (len > 0) {
        ssize_t n = write(fd, p, len);
        if (n < 0) {
            if (errno == EINTR)
                continue;           // interrupted before writing anything: retry
            return -1;              // real error: ENOSPC, EIO, EBADF, ...
        }
        p   += n;                   // short write: move past what was written
        len -= (size_t)n;
    }
    return 0;
}

The errors you will meet most often in storage work:

errnoTypical cause
ENOENTA component of the path does not exist.
EACCES / EPERMPermission denied by mode bits, an ACL, or a security module.
EEXISTO_CREAT|O_EXCL or mkdir on a name that exists.
EBADFThe descriptor is not open, or not open for this kind of access.
EMFILEYour process hit its descriptor limit.
ENOSPC / EDQUOTDisk full / quota exceeded. On network filesystems these can surface late, at close or fsync.
EIOThe device or server reported an I/O failure. Take it seriously; see the fsync story in lesson 05.
ESTALENFS only: the server no longer recognises the file handle. Lesson 06 explains file handles.
Pitfall: close can fail

close returns an error code too, and on NFS it is often where a deferred write error first appears, because the client flushes cached writes at close. Check it. On Linux, do not retry close after EINTR: the descriptor is already released, and retrying may close a descriptor another thread just opened with the same number.

Offsets, holes, and positional I/O

off_t   lseek(int fd, off_t offset, int whence);   // SEEK_SET, SEEK_CUR, SEEK_END, SEEK_DATA, SEEK_HOLE
ssize_t pread(int fd, void *buf, size_t count, off_t offset);
ssize_t pwrite(int fd, const void *buf, size_t count, off_t offset);

lseek only changes a number in the kernel. It does no I/O. lseek(fd, 0, SEEK_CUR) is the idiom for "what is my current offset?".

You may seek past the end of a file. If you then write, the file's length jumps to cover the new data, and the gap in between is a hole. A hole has no disk blocks behind it. Reads from a hole return zeros. The lab creates a file whose length is 1 GiB + 1 byte and whose disk usage is a single 4 KiB block:

st_size   = 1073741825 bytes (apparent size)
st_blocks = 8 x 512 B = 4096 bytes actually allocated
SEEK_DATA from 0 -> 1073741824 (everything before is a hole)

Files with holes are called sparse. Virtual machine disk images and database files are often sparse. SEEK_DATA and SEEK_HOLE let a program such as cp or tar skip the holes instead of reading gigabytes of zeros. NFS gained the same ability in version 4.2 with its SEEK and READ_PLUS operations (lesson 06).

pread and pwrite take the offset as an argument and leave the descriptor's offset untouched. Use them whenever several threads share one descriptor: separate lseek + read calls from two threads race with each other, while each pread is self-contained. Databases use pread/pwrite almost exclusively.

Aside: a documented Linux quirk

POSIX says pwrite writes at the offset you give it, even on a descriptor opened with O_APPEND. Linux instead appends to the end of the file. The pwrite(2) man page lists this under BUGS.

The three tables behind a descriptor

The descriptor number is an index. Following it takes you through three kernel structures, and knowing which state lives in which one explains most surprising behaviour around files.

  1. The per-process descriptor table. An array owned by each process (struct files_struct in the kernel). Slot n holds a pointer to an open file description, plus one per-descriptor flag: close-on-exec (FD_CLOEXEC).
  2. The open file description, the kernel's struct file. One is created by every successful open. It holds the current offset (f_pos), the access mode, the status flags such as O_APPEND and O_NONBLOCK, a reference count, and a pointer to the operations table for this kind of file (f_op). The open file descriptions of all processes together form the system-wide open file table.
  3. The in-memory inode (struct inode). One per file, no matter how many times it is opened. It holds what is true about the file itself: its size, owner, mode, timestamps, link count, and where its data lives. Lesson 03 shows the on-disk version.

Who shares what

  • dup(fd) creates a new descriptor (the lowest free number) pointing to the same open file description. dup2(old, new) does the same into a specific slot, closing whatever was there first. The shell uses this for redirection: cmd > out.txt is an open followed by dup2(fd, 1), and 2>&1 is dup2(1, 2).
  • fork() gives the child a copy of the parent's descriptor table. The copies point to the same open file descriptions, so parent and child share offsets. That is why a parent and child both writing to an inherited log file interleave their lines instead of overwriting each other.
  • A second open() of the same path, from the same process or another one, creates a new open file description with its own offset. The two only meet at the inode.

The flags also split along these lines. Close-on-exec lives in the descriptor table, so it is per descriptor and dup does not copy it. Status flags such as O_APPEND and O_NONBLOCK live in the open file description, so setting O_NONBLOCK through one descriptor with fcntl(fd, F_SETFL, …) affects every descriptor, in every process, that shares that description.

Two writers, and why O_APPEND exists

Suppose two processes each open the same log file for writing, without O_APPEND. Each has its own open file description, and both offsets start at 0. Process A writes AAAA. Process B, whose offset is still 0, writes BB on top of it. The file now holds BBAA. Lab 01 reproduces exactly this.

Seeking to the end first does not fix it: between A's lseek(fd, 0, SEEK_END) and A's write, B can append, and A then overwrites B's data. O_APPEND makes "move to the end, then write" a single step inside the kernel, done while the kernel holds the inode's lock, so two appenders on the same local filesystem can never overwrite each other. With O_APPEND the lab's file holds AAAABB.

Pitfall: O_APPEND over NFS

The atomicity of O_APPEND comes from one kernel holding one lock. Two NFS clients appending to the same file each have their own kernel and their own idea of where the end is, so their appends can overwrite each other. Lesson 07 explains why, and what to do instead.

Everything is a descriptor

The table holds pointers to struct file, and a struct file can represent almost anything with a read_iter or write_iter function behind it:

  • regular files and directories on any filesystem;
  • pipes (pipe()), Unix and network sockets (socket(), accept());
  • device files such as /dev/null, /dev/tty and raw disks like /dev/sda (lesson 02);
  • kernel event sources: eventfd, timerfd, signalfd, epoll, inotify, io_uring.

The same read, write and close calls work on all of them, which is what "everything is a file" means in practice.

Seeing your descriptors

Linux publishes each process's table under /proc/<pid>/fd, as symbolic links whose targets describe what each descriptor points to. /proc/self is the calling process. For each descriptor, /proc/<pid>/fdinfo/<n> shows the open file description's offset and flags. From lab 01:

fd 3   -> /home/artem/storage-course/labs/01-fds/scratch/alphabet.txt
fd 4   -> pipe:[81567245]
fd 5   -> pipe:[81567245]
/proc/self/fdinfo/3:
  pos:    7
  flags:  02100000
  mnt_id: 81
  ino:    2826040

The flags are in octal: 02000000 is O_CLOEXEC, 0100000 is O_LARGEFILE (set automatically on 64-bit), and the access mode in the low bits is 0, O_RDONLY. Both ends of the pipe show the same inode number in brackets. ls -l /proc/$$/fd shows your shell's own descriptors, and lsof -p PID shows the same information for any process you are allowed to inspect.

Limits and leaks

Each process has a limit on open descriptors, RLIMIT_NOFILE, which the shell shows with ulimit -n and a program reads with getrlimit. Many distributions default the soft limit to 1024; this WSL session reports 1048576. When a process hits it, open, socket and accept fail with EMFILE. A server that never closes descriptors eventually hits the limit, so "too many open files" in a log is almost always a leak.

Descriptors are inherited across execve unless marked close-on-exec. Setting it later with fcntl leaves a window in which another thread can fork and exec, carrying your descriptor into an unrelated program. Passing O_CLOEXEC to open closes that window, which is why careful code passes it everywhere.

Metadata and directories

stat

int stat(const char *path, struct stat *st);   // follows symlinks
int lstat(const char *path, struct stat *st);  // does not
int fstat(int fd, struct stat *st);            // by descriptor

stat returns the inode's attributes. The fields you will use in this course:

FieldMeaning
st_dev, st_inoThe device (filesystem) and inode number. Together they identify a file uniquely on this machine. Two paths with the same pair are hard links to one file.
st_modeFile type (regular, directory, symlink, device, pipe, socket) and permission bits.
st_nlinkHow many directory entries (names) point at this inode.
st_uid, st_gidOwner and group, as numbers. NFS carries these numbers or names across the network, which causes its own problems (lesson 06).
st_sizeLength in bytes, holes included.
st_blocksSpace actually allocated, always in 512-byte units whatever the real block size. du reports this; ls -l reports st_size.
st_blksizeThe preferred I/O size for efficiency, usually 4096 locally and often 1 MiB on NFS.
st_atim, st_mtim, st_ctimLast access, last data modification, and last inode change (data writes, but also chmod, chown, link). Nanosecond resolution on modern filesystems.

The newer statx call returns the same information plus extras such as the file's creation (birth) time, and lets the caller ask for only some fields. That matters on network filesystems, where some attributes are expensive to fetch.

Reading a directory

A directory is a file whose content is a list of (name, inode number) entries. You cannot read it directly. Linux provides getdents64, which fills a buffer with records of this shape:

struct linux_dirent64 {
    ino64_t        d_ino;     // inode number the name points to
    off64_t        d_off;     // opaque cookie: where the next read continues
    unsigned short d_reclen;  // length of this record
    unsigned char  d_type;    // DT_REG, DT_DIR, DT_LNK, ... or DT_UNKNOWN
    char           d_name[];  // NUL-terminated name
};

The C library's opendir/readdir wrap it with a buffer. Notice what is missing: sizes, owners, timestamps. A directory listing gives names and inode numbers, so ls -l must call stat once per entry. On a local disk that is cheap when cached. Over a network it was so slow that NFSv3 added READDIRPLUS, which returns attributes along with names. The d_off cookie plays the same role as the cookie NFS uses to resume a long listing across several requests.

Names: link, unlink, rename

  • link(old, new) adds a second name for an existing inode and increments st_nlink. Both names are equal; neither is the "original".
  • unlink(path) removes a name and decrements st_nlink. It does not necessarily delete anything; see the next section.
  • rename(old, new) moves a name, and if new exists, replaces it atomically: any other process sees either the old file or the new one under that name, never nothing and never a mix. Applications rely on this to update files safely: write a temporary file, fsync it, then rename it over the real name. Lesson 05 covers the full recipe, including the fsync of the directory it also needs.

A name is not a file

The kernel frees a file's inode and data only when two counts reach zero: the link count (names in directories) and the number of open references (open file descriptions, plus memory mappings). unlink only affects the first.

So a program can open a file, have its name removed, and keep reading and writing it. From the lab:

before unlink: inode 2826042, nlink 1
after unlink:  inode 2826042, nlink 0, access(path) -> No such file or directory
/proc/self/fd/3 -> /home/artem/storage-course/labs/01-fds/scratch/doomed.txt (deleted)
pread through the fd still returns "still here"

This is useful, since it gives you anonymous temporary files that clean themselves up when the process exits. It is also the source of a classic operations puzzle: df says the disk is full, du finds nothing big. Usually a long-running process is still writing to a log file that someone deleted. The space returns only when that process closes the file or exits. lsof +L1 lists open files with a link count below 1.

Forward pointer

An NFSv3 server has no idea which files its clients hold open. To keep "deleted but open" working, the NFS client fakes it: instead of removing a file that is still open, it renames it to .nfsXXXXXXXX and removes that name at last close. The Linux client still does this with NFSv4. You will meet these "silly renames" in lesson 07.

Where your bytes wait: buffers above and below the syscall

When write returns, your data is not on disk. It has been copied into the kernel's page cache, the in-memory copy of file contents, and marked dirty. The kernel writes dirty pages to the device later, typically within about 30 seconds. Most programs also add a buffer of their own above the syscall, through C's stdio library.

stdio is a cache in user space

fopen wraps a descriptor in a FILE object with a buffer. fprintf and fwrite copy into that buffer, and only when it fills (or you call fflush or fclose) does stdio call write. The buffering mode depends on the target: full buffering for files and pipes, line buffering for terminals, and no buffering for stderr. You can change it with setvbuf.

The lab shows two consequences. After fprintf, the kernel reports the file as 0 bytes long, because the data is still in your process. And mixing stdio with raw write on the same descriptor reorders output:

after fprintf:  file size on the kernel side = 0
after fflush:   file size on the kernel side = 19
...
2nd (write)
1st (fprintf)

Two more consequences matter in practice. A process killed with SIGKILL loses whatever sits in its stdio buffers, though everything it already passed to write survives in the page cache. And a fork with unflushed stdio data duplicates the buffer, so the same output can appear twice. Lab 01 turns off buffering on its own stdout for this reason.

fsync and fdatasync

int fsync(int fd);       // data + all metadata durable before returning
int fdatasync(int fd);   // data + only the metadata needed to read it back (e.g. size, not mtime)

These are the calls that turn "written" into "durable". They write the file's dirty pages to the device, wait for completion, and then ask the device to flush its own volatile cache. They are slow, milliseconds rather than microseconds, which is why programs batch them. Lesson 05 covers the page cache and writeback in detail, and lesson 02 covers what FLUSH means to the device.

mmap, briefly

mmap maps a file's page-cache pages directly into your address space, so ordinary memory loads and stores read and write the file with no read or write calls. MAP_SHARED mappings write back to the file; MAP_PRIVATE mappings give you a copy-on-write view that never reaches the file. Pages are loaded on first touch through a page fault. msync is the mmap version of fsync. mmap and the page cache are the same memory, which is why lesson 05 treats them together.

Where the call goes next

Inside the kernel, the descriptor led to a struct file, and the struct file led to an operations table. That table is filled in by whichever filesystem the file lives on. The layer that owns these objects and dispatches through them is the Virtual File System (VFS), and it is also where the page cache and the name cache live. That is lesson 05.

Before getting there, the course drops to the very bottom of the stack: the device that eventually stores the bytes, and how it is addressed. That is lesson 02. Lessons 03 and 04 then build a filesystem on top of it, so that by lesson 05 both ends of the path are familiar.

Check yourself

A process opens the same file twice, getting descriptors 3 and 4, and writes "hello" through 3. Then it reads 5 bytes through 4. What does it read, and what is 4's offset afterwards?

It reads "hello". The two opens created two open file descriptions with separate offsets, so descriptor 4 starts at 0. The data is shared, because both lead to the same inode and the same page cache, so the bytes written through 3 are visible. Afterwards 4's offset is 5 and 3's is also 5, each counted separately.

Why does cmd > log 2>&1 keep both streams intact, while cmd > log 2> log can lose output?

2>&1 is dup2(1, 2): both descriptors share one open file description and one offset, so writes from either land one after another. 2> log opens the file a second time, creating a second description whose offset starts at 0, so stderr output overwrites stdout output in the file, exactly like lab demo 2.

read returned 100 when you asked for 4096. Is that an error? What about 0? What about −1 with errno EINTR?

100 is a short read: legal, and you should loop if you need more. On a regular file it usually means you reached the end. 0 means end of file. −1 with EINTR means a signal interrupted the call before any data moved, so retry it.

df shows a filesystem 100% full, but du -sh / adds up to far less. What is the most likely explanation, and how do you confirm it?

A process holds a deleted file open. The name is gone, so du (which walks names) cannot see it, but the inode and its blocks stay allocated until the last reference closes. lsof +L1 lists such files; restarting or signalling the process to reopen its log frees the space.

A program calls fprintf(f, ...) and is then killed with SIGKILL. Is the text in the file? What if it called fflush(f) before being killed? What if the machine lost power right after the fflush?

Without fflush, no: the text was still in the stdio buffer in the process's memory. After fflush, the text is in the kernel's page cache and survives the process dying. A power loss right after fflush can still lose it, because nothing has forced the page cache or the drive's cache to stable media. That needs fsync.

ls -l says a file is 10 GiB and du says 12 KiB. How?

The file is sparse. ls -l shows st_size, the logical length including holes. du shows st_blocks, the space actually allocated. Most of the file is holes with no blocks behind them.

Why pass O_CLOEXEC to open instead of calling fcntl(fd, F_SETFD, FD_CLOEXEC) right afterwards?

In a multithreaded program, another thread can call fork and execve between your open and your fcntl, and the new program inherits the descriptor. Setting the flag inside open leaves no window.
