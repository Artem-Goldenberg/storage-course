Lesson 6 · Network

NFS from v3 to 4.2

What actually crosses the wire when a program calls read() on a file that lives on another machine, and how thirty years of NFS versions changed the answer.

After this lesson you can
  • trace a read() from an application through the Linux NFS client, SUNRPC and the wire into nfsd and the server's filesystem;
  • read an RPC call the way the server does: program, version, procedure, credentials, XDR-encoded arguments;

Why a network filesystem

Lessons 1 to 5 kept the disk inside the machine. A file was an inode on a local block device, every process went through one kernel, and that kernel's page cache was the only copy of the data in RAM. A network filesystem keeps the files on a server and lets many clients use them through the ordinary file API. The application still calls open, read and write. The client kernel turns those calls into messages to the server.

Three things change when the disk moves away:

  • Latency. A page-cache hit costs well under a microsecond. A round trip to a server in the same rack costs tens to hundreds of microseconds over TCP, before the server touches its own disk. Every design decision in NFS is about avoiding round trips.
  • Partial failure. A local disk and the kernel fail together. A server can reboot while the client keeps running, and the network can drop or duplicate messages. The protocol has to say what happens to half-finished writes and to locks.
  • More than one cache. Each client caches data and attributes in its own RAM. The server has its own page cache too. Keeping them consistent is lesson 7.

NFS shares files. Remote block protocols such as iSCSI and NVMe over Fabrics share a disk: the client runs its own filesystem on top, so only one client can mount it read-write unless a cluster filesystem coordinates them (lesson 9). NAS (network-attached storage) usually means file protocols like NFS and SMB. SAN (storage area network) usually means block protocols.

Versions and their RFCs

Sun Microsystems built NFS in 1984 and published the protocol so that anyone could implement it. Every version since has been specified in IETF RFCs. Later RFCs often replace earlier ones for the same version, which is why NFSv4.0 and NFSv4.1 each have two numbers.

A minor version of NFSv4 (4.0, 4.1, 4.2) is negotiated per connection. 4.2 is 4.1 plus a set of mostly optional operations, so a 4.2 server may still answer some 4.2 operations with NFS4ERR_NOTSUPP. The Linux client tries 4.2 first and negotiates down until the server agrees, so on a modern pair of machines a plain mount server:/export /mnt gives you 4.2.

The Linux NFS stack

Here is the path of one read() on a client whose page cache does not have the data. Every box is kernel code except the application.

  • VFS and page cache. The client VFS is the same one from lesson 5. NFS registers its own file_operations and address_space_operations, so a cache hit never reaches NFS code.
  • NFS client (fs/nfs). Decides when to revalidate caches, batches dirty pages into WRITE calls, tracks NFSv4 state (client ID, opens, locks, delegations), and maps each VFS operation to NFS procedures.
  • SUNRPC (net/sunrpc). The generic ONC RPC layer: assigns transaction IDs, encodes and decodes arguments in XDR, retransmits on timeout, and multiplexes many outstanding calls over a connection. Both the client and the server side live here.
  • Transport. TCP (xprtsock) almost everywhere today. RDMA (xprtrdma on the client, svcrdma on the server) moves the bulk data with RDMA reads and writes; that is lesson 8. UDP is legacy, and many kernels are built without NFS-over-UDP support.
  • nfsd (fs/nfsd). The in-kernel server. A pool of kernel threads, each handling one RPC at a time, calls into the server's VFS exactly as a local process would. Its replies come from the server's page cache when they can.
  • User-space helpers. rpc.mountd answers the MOUNT protocol and feeds export information to the kernel; rpcbind maps RPC program numbers to ports; rpc.statd handles NFSv3 lock recovery; nfsdcld records which NFSv4 clients may reclaim state after a server reboot; rpc.gssd and nfsidmap handle Kerberos and user-name mapping.
Aside

Not every NFS server is nfsd. NFS-Ganesha is a widely used user-space server that can export Ceph, GlusterFS and other backends, and many storage appliances run their own implementations. The protocol is the contract; the Linux client talks to all of them.

ONC RPC and XDR

NFS is a set of remote procedures. The framework underneath is ONC RPC (Open Network Computing Remote Procedure Call, RFC 5531), and the encoding is XDR (External Data Representation, RFC 4506). Every NFS message is an RPC call or reply.

The call header

xid         0x5a3c91e2      transaction id; the reply carries the same xid
msg_type    0 (CALL)         1 = REPLY
rpcvers     2
prog        100003           NFS
vers        3                or 4
proc        6                NFSv3 READ; NFSv4 has only NULL (0) and COMPOUND (1)
cred        AUTH_SYS { uid 1000, gid 1000, gids [27, 100] }
verf        AUTH_NONE
... then the procedure's arguments, XDR-encoded

The server finds the program and version, decodes the arguments, runs the procedure, and sends a reply with the same xid. The client matches replies to calls by xid, which is how many calls can be in flight on one connection. Over TCP each message is preceded by a 4-byte record mark that holds its length.

XDR in one minute

XDR encodes everything in big-endian 4-byte units. Integers are 4 or 8 bytes. Variable-length data (strings, opaque blobs such as file handles) is a 4-byte length followed by the bytes, padded with zeros to a multiple of 4. The name "hello" becomes 12 bytes:

00 00 00 05   68 65 6c 6c   6f 00 00 00
length = 5    h  e  l  l    o  padding

There are no field names or tags on the wire. Both sides know the layout from the protocol specification, which is written in XDR's own definition language. That keeps messages compact and parsing cheap, and it is why Wireshark needs an NFS dissector to show anything useful.

Who is calling: credentials

AUTH_SYS (once called AUTH_UNIX) sends numeric uid, gid and up to 16 supplementary group ids in every call. The server believes them. Security therefore depends on trusting the client machine and the network. The export option root_squash maps uid 0 to an anonymous user so that root on a client is not root on the server, but any user who is root on a trusted client can still claim to be any other uid. The 16-group limit is real: users in more groups lose access unless the server looks groups up itself (rpc.mountd --manage-gids).

RPCSEC_GSS uses Kerberos instead. The mount option sec= picks the level:

  • sec=krb5: the user is authenticated with a Kerberos ticket. Data is not protected.
  • sec=krb5i: adds an integrity checksum to every message.
  • sec=krb5p: adds encryption ("privacy"). This costs CPU on both ends.

A newer option encrypts the transport rather than each message: RPC-with-TLS (RFC 9289), enabled on recent Linux kernels with the xprtsec=tls or xprtsec=mtls mount option and the tlshd user-space handshake daemon. It protects the connection; it does not by itself authenticate individual users.

Identities in NFSv4. NFSv4 attributes name owners as strings, user@domain, rather than numbers. Client and server translate with nfsidmap, and a mismatched domain shows up as files owned by nobody. With sec=sys Linux sends the numeric id as a string by default, which avoids that failure as long as uids match across machines.

File handles

A local process names an open file with an fd, which only makes sense inside one kernel. An NFS client names a file with a file handle: an opaque blob the server created and the client stores without interpreting. NFSv3 handles are at most 64 bytes; NFSv4 handles at most 128. The client gets one from LOOKUP (or the MOUNT protocol, or NFSv4's PUTROOTFH), and every later operation on that file carries it.

  • Handles survive server reboots. The server needs no memory of having issued them. It decodes the filesystem id and the inode number and looks the inode up. That is what made a stateless server possible.
  • Handles go stale. If the file is deleted and its inode number reused, the generation number stored in the inode no longer matches the one in the handle, and the server answers ESTALE ("Stale file handle"). The same happens if an export is moved to a filesystem with a different id. Filesystems without a stable UUID need an explicit fsid= export option for the same reason.

NFSv3: a stateless server

An NFSv3 server keeps no record of which clients exist or which files they have open. Every request is self-contained: file handle, offset, count, credentials. There is no OPEN or CLOSE in the protocol. When a server crashes and comes back, clients just retransmit, and to them the crash looks like a slow server. That simplicity is why NFSv3 is still everywhere.

READDIRPLUS exists because ls -l on a 10,000-entry directory would otherwise cost one READDIR plus 10,000 GETATTRs. ACCESS exists because the client cannot evaluate permissions correctly by itself when the server uses ACLs or maps ids.

Unstable writes, COMMIT and the write verifier

NFSv2 required the server to put every WRITE on stable storage before replying, which made writes painfully slow. NFSv3 added a stable field to WRITE:

  • UNSTABLE: the server may reply as soon as the data is in its page cache.
  • DATA_SYNC: data on stable storage, metadata may lag.
  • FILE_SYNC: data and metadata on stable storage.

The client sends a stream of UNSTABLE writes and later one COMMIT for the range, which makes the server flush it (an fsync on the server side). Until the COMMIT succeeds, the client keeps its copy of the data, because the server might crash and lose it.

How does the client know the server crashed? Every WRITE and COMMIT reply carries an 8-byte write verifier, a value the server picks at boot. If the verifier in the COMMIT reply differs from the one in the WRITE replies, the server restarted in between, and the client resends every write it has not seen committed.

Side protocols and the duplicate request cache

NFSv3 left three jobs to other RPC programs. MOUNT (rpc.mountd) checks the export list and hands out the export's root file handle. NLM (lockd) implements fcntl byte-range locks, which need state the NFS protocol refuses to keep. NSM (rpc.statd) tells lock holders when a peer reboots, so clients can reclaim locks and servers can drop locks of dead clients. All of them sit behind rpcbind on port 111 with dynamic ports, which is why NFSv3 through a firewall means pinning ports in configuration.

Retransmission exposes a weakness of statelessness. A client sends REMOVE, the server removes the file, the reply is lost, the client retransmits. The second REMOVE fails with "no such file", although the operation succeeded. Servers paper over this with a duplicate request cache (DRC): recent replies to non-idempotent requests, keyed by xid and client address, are replayed on retransmission. The DRC is a heuristic of limited size, and NFSv4.1 sessions replace it with a guarantee.

NFSv4.0: state, compounds, one port

NFSv4 gave up statelessness on purpose. Opens, locks and caching promises need state, and keeping that state inside the NFS protocol, with clear recovery rules, is simpler than three side protocols that each half-recover.

Key idea

Every piece of NFSv4 state (a client ID, an open, a lock, a delegation, a layout) is covered by the client's lease. The client keeps it alive by talking to the server, the server may drop it when the client goes silent, and after a server reboot the client reclaims it during the grace period.

COMPOUND: many operations, one round trip

NFSv4 has exactly two RPC procedures: NULL and COMPOUND. A COMPOUND carries a list of operations that the server executes in order. The server keeps a current file handle while it works through the list: PUTFH or PUTROOTFH sets it, LOOKUP moves it to a child, and most operations act on it. SAVEFH and RESTOREFH keep a second handle for two-file operations such as RENAME, LINK, COPY and CLONE. Execution stops at the first operation that fails, and the reply holds the results up to and including that one.

Client ID, opens and stateids

Before doing anything stateful, a client introduces itself. In 4.0 that is SETCLIENTID and SETCLIENTID_CONFIRM; in 4.1 it is EXCHANGE_ID. The client presents a long-lived name (Linux builds it from the hostname, or from nfs4_unique_id) and a boot verifier; the server returns a short client ID. A changed boot verifier tells the server the client rebooted, so its old state can be thrown away.

OPEN is a real operation. It names the file in the current directory, says whether to create it, and asks for share access (read, write, both) and optionally a share deny mode (Windows-style "nobody else may write"). The reply carries a stateid: 16 bytes, a 4-byte sequence number plus 12 bytes that identify the state. READ, WRITE, SETATTR of the size, LOCK and CLOSE all present a stateid, so the server always knows which open a request belongs to. CLOSE releases it.

Byte-range locks are part of the protocol: LOCK, LOCKT (test) and LOCKU (unlock), each with its own lock stateid. No lockd, no statd.

Leases and the grace period

State on a server is dangerous if the client that owns it disappears. NFSv4 solves this with a lease: the client's state is valid for a lease period, and any successful stateful operation renews it. An idle 4.0 client sends RENEW; a 4.1 client's SEQUENCE operation renews implicitly. The Linux server's lease time is 90 seconds by default (/proc/fs/nfsd/nfsv4leasetime, or lease-time in nfs.conf).

When a client's lease expires, the server may release its opens and locks so others can proceed. Since Linux 5.19, nfsd is a "courteous server": it keeps an expired client's state until another client actually needs a conflicting lock or open, for up to a day, so a client that was cut off by a network partition can often resume without losing anything.

The reverse case is the server rebooting. Its in-memory state is gone, but clients still believe they hold opens and locks. For a grace period after boot (by default as long as the lease), the server refuses new opens and locks with NFS4ERR_GRACE and lets clients reclaim what they held. To know who is allowed to reclaim, it records clients on stable storage (nfsdcld on Linux). A 4.1 client sends RECLAIM_COMPLETE when it is done, so a server whose known clients have all finished can end grace early. Applications see the grace period as a pause of up to a minute and a half after a server restart.

Delegations and callbacks

A delegation is a promise from the server: "until I call you back, no other client will write this file" (a read delegation) or "no other client will open it at all" (a write delegation). While it holds one, the client can serve opens, reads and attribute queries from its cache without asking the server. When another client wants conflicting access, the server sends a CB_RECALL callback, the holder flushes and answers with DELEGRETURN, and the newcomer proceeds. Lesson 7 works through the timeline.

Callbacks reverse the usual direction: the server calls the client. In NFSv4.0 the server opens a new TCP connection to an address the client advertised in SETCLIENTID. Behind NAT or a client firewall that connection fails, and a 4.0 server then quietly stops granting delegations. Nothing breaks, but caching gets worse. NFSv4.1 fixed this by sending callbacks over the client's own connection.

The pseudo-filesystem and ACLs

An NFSv4 server presents all its exports as one tree, the pseudo-filesystem. A client can mount server:/ and walk down into any export it is allowed to see; the directories that only join exports together are synthetic. Old Linux setups marked the root with fsid=0; current nfs-utils builds the pseudo-root automatically, so the NFSv4 path to an export is its real path on the server.

NFSv4 also defined its own ACL model: ordered lists of ALLOW and DENY entries with inheritance flags, much closer to Windows ACLs than to POSIX mode bits. nfs4_getfacl and nfs4_setfacl from nfs4-acl-tools manipulate them. The Linux server stores them by translating to POSIX ACLs, which cannot express everything, so some NFSv4 ACLs are rejected or approximated.

NFSv4.1: sessions, trunking and pNFS

Sessions and exactly-once semantics

After EXCHANGE_ID, a 4.1 client calls CREATE_SESSION. The two sides negotiate channel attributes: largest request and reply, most operations per COMPOUND, and the number of slots, which is the number of requests the client may have outstanding at once. Every COMPOUND then starts with a SEQUENCE operation:

SEQUENCE { sessionid, slotid = 3, sequenceid = 118, highest_slotid = 15, cachethis = true }

The server keeps the last reply for each slot. A retransmission with the same slot and sequence id gets that reply back instead of being executed twice. That is exactly-once semantics (EOS), and it replaces the DRC heuristic with a guarantee whose memory cost the server chose at CREATE_SESSION. The slot count doubles as flow control: a busy server can shrink highest_slotid to slow a client down. On Linux the client's upper bound is the nfs.max_session_slots module parameter.

The backchannel and trunking

A session has a fore channel (client to server) and a backchannel (server to client). The backchannel normally rides on the same TCP connection the client opened, so callbacks work through NAT and firewalls. That is a large practical reason to prefer 4.1 or 4.2 over 4.0.

Trunking means using several connections for one client. Session trunking binds several connections to one session (BIND_CONN_TO_SESSION), for example one per network interface. Client ID trunking uses several sessions under one client ID. On Linux, nconnect=N (up to 16) opens N TCP connections to the same server address and spreads RPCs over them; it also works with NFSv3. It helps when one TCP connection, and the single CPU that tends to process it, is the bottleneck.

pNFS: separate the data path from the metadata path

A single NFS server is a bottleneck for bandwidth: every byte passes through one machine. pNFS (parallel NFS) splits the server into a metadata server (MDS), which handles the namespace, opens and locks, and one or more data servers (DS), which hold the file contents. The MDS gives the client a layout: a map saying which data servers hold which byte ranges and how the file is striped. The client then reads and writes directly to the data servers, in parallel.

  • LAYOUTGET asks for a layout for a byte range and access mode. Layouts are state, with their own stateid, and the MDS can recall them with CB_LAYOUTRECALL.
  • GETDEVICEINFO turns the device ids in a layout into addresses (IP addresses for file layouts, SCSI identifiers for block layouts).
  • LAYOUTCOMMIT tells the MDS about writes done through the data servers, so it can update the file size and modification time.
  • LAYOUTRETURN gives the layout back.

Linux nfsd can act as an MDS for block and SCSI layouts (clients and server share the storage, typically with XFS on the server), and has a flexible-files mode whose Kconfig help warns that it implements the bare minimum and is meant for testing clients. Large pNFS deployments mostly run on commercial or purpose-built servers. Lesson 9 compares pNFS with Lustre and Ceph, which separate metadata and data in similar ways.

Directory delegations

4.1 also defined directory delegations (GET_DIR_DELEGATION, with CB_NOTIFY for changes), so a client could cache a directory's listing and its negative lookups safely. For years almost nobody implemented them. The Linux client gained initial support in 6.19, used for ACCESS, CREATE, UNLINK and RENAME, with a module option to turn it off.

Server-side copy

Copying a 10 GiB file with read() and write() over NFSv3 moves 20 GiB over the network: down to the client and back up. With 4.2 the client sends one COPY with the source and destination stateids, offsets and a length. The source file handle goes in with SAVEFH, the destination with PUTFH, and the server copies locally, usually through its own copy_file_range.

  • Synchronous or asynchronous. The client may let the server run a long copy in the background. The COPY reply then carries a stateid, the client can poll with OFFLOAD_STATUS or stop it with OFFLOAD_CANCEL, and the server reports the result with a CB_OFFLOAD callback.
  • Intra-server or inter-server. If source and destination are on different servers, the client first sends COPY_NOTIFY to the source server, which authorises the destination server to read the file. The client then sends COPY to the destination server with the source server's address, and the destination server reads the data directly from the source as an NFSv4.2 client itself. Linux supports this, but it is off by default on the server: the destination needs nfsd.inter_copy_offload_enable=1 and a kernel built with CONFIG_NFSD_V4_2_INTER_SSC.

CLONE

CLONE asks the server to make a range of the destination file share the source's blocks, like cp --reflink locally. It only works if the exported filesystem supports reflinks: XFS (created with reflink, the default in recent xfsprogs), btrfs, and a few others. ext4 does not, so CLONE on an ext4 export fails with EOPNOTSUPP. The Linux client remembers a NOTSUPP answer for the rest of the mount and stops sending the operation.

Sparse files: SEEK and READ_PLUS

A sparse file has holes: ranges never written, which read as zeros and take no disk space (lesson 3). Before 4.2 a client could not tell holes from real zeros, so cp had to read every zero over the network and a sparse VM image became fully allocated on copy. SEEK implements lseek with SEEK_DATA and SEEK_HOLE on the server. READ_PLUS is a READ whose reply is a list of segments, each either data or "a hole of N bytes". The Linux client uses READ_PLUS when it is built with CONFIG_NFS_V4_2_READ_PLUS, which has defaulted to on since 6.6 after an earlier attempt was reverted. The WSL kernel this course was tested on turns the option off, so it always sends READ.

ALLOCATE and DEALLOCATE

fallocate(fd, 0, off, len) becomes ALLOCATE: the server reserves real blocks, so a later write cannot fail with ENOSPC. fallocate(fd, FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE, off, len) becomes DEALLOCATE: the server frees the blocks and the range reads as zeros. Before 4.2, glibc's posix_fallocate emulated reservation by writing to every block, over the network.

IO_ADVISE, WRITE_SAME, Labeled NFS

IO_ADVISE carries hints like "I will read this sequentially" or "I will not need this again", so the server can read ahead or drop pages. WRITE_SAME fills ranges with a repeated block pattern, aimed at databases that initialise files with a fixed header in each block; it is rarely implemented. As far as current kernels go, the Linux client sends neither. Labeled NFS adds the sec_label attribute so that SELinux labels on the server's files are visible to and enforced on clients; Linux enables it per export with the security_label option.

Extended attributes (RFC 8276)

Before RFC 8276, setfattr -n user.color on an NFS file failed. The four xattr operations carry user.* attributes only; the security. and trusted. namespaces do not cross the wire this way. Linux added client and server support in 5.9. The client caches xattrs, so repeated getxattr calls may not reach the server.

RFC 9754: opening and delegating files

RFC 9754 (March 2025) extends 4.2 opens and delegations:

  • Delegated timestamps. The holder of a write delegation becomes the authority for the file's access and modify times. It no longer has to send SETATTR or force GETATTRs just to keep times right, and the server asks it with CB_GETATTR when another client needs them. The Linux client added support in 6.11. On the server side, the 6.18 kernel used for this course has it behind CONFIG_NFSD_V4_DELEG_TIMESTAMPS, which is off.
  • Only a delegation. An OPEN flag asks the server to return either an open stateid or a delegation stateid, not both, which reduces state on both sides.
  • Discovering OPEN flags. A new attribute lists which OPEN flags the server supports.
  • Offline files. A client can learn that a file's data is not immediately available (for example, archived to tape), so it can avoid hanging on it.

Export options

/etc/exports (and files in /etc/exports.d/ ending in .exports) lists what the server shares and with whom:

/srv/data   10.0.0.0/24(rw,sync,no_subtree_check)   build01(ro)
OptionMeaning
rw / roread-write or read-only (default ro)
sync / asyncsync (the default) replies to WRITE and COMMIT only after the data is on stable storage. async replies first. The exports man page says it plainly: async lets the server violate the protocol, and a crash can lose or corrupt data that clients were told was safe. The verifier cannot save you, because the client already dropped its copy.
root_squash / no_root_squash / all_squashmap uid 0 (or every uid) to the anonymous user. root_squash is the default.
no_subtree_checkdo not check that every file handle lies inside the exported subtree. Default since nfs-utils 1.1.0; subtree checking breaks when files are renamed while open.
fsid=give the export a fixed filesystem id, needed when the filesystem has no stable UUID; fsid=0 or fsid=root marks the NFSv4 pseudo-root (legacy)

pnfs, security_labeloffer pNFS layouts; carry SELinux labels

Apply changes with exportfs -ra; list the active exports with exportfs -v.

Server settings

/etc/nfs.conf configures the user-space tools and the server. The [nfsd] section takes threads, lease-time, grace-time, vers3, vers4.0, vers4.1, vers4.2 and rdma, among others. The live values are in /proc/fs/nfsd/:

$ cat /proc/fs/nfsd/versions /proc/fs/nfsd/threads /proc/fs/nfsd/nfsv4leasetime /proc/fs/nfsd/portlist
+3 +4 +4.1 +4.2
8
90
tcp 2049

(Illustrative values: rpc.nfsd starts eight threads unless told otherwise.) Each nfsd thread handles one RPC at a time, including any wait for the disk. Eight threads cannot keep a fast server busy under hundreds of clients; production servers run dozens to hundreds. Too few threads shows up on the clients as RPCs that wait in a queue.

LOCALIO

Since Linux 6.12, when an NFS client and nfsd run on the same host (containers using a local NFS server, for example), the LOCALIO extension lets the client detect this and do READ, WRITE and COMMIT by calling into the local filesystem directly, skipping XDR and the network stack. It needs CONFIG_NFS_LOCALIO, which the WSL kernel does not enable, so the loopback lab below exercises the real RPC path.

Observing NFS

Most NFS problems are visible from the client, without root, in one file.

/proc/self/mountstats

Each NFS mount has a block: the options in force, NFSv4 details such as lease_time, event counters, byte counters, transport statistics, and then one line per RPC type:

device 127.0.0.1:/srv/nfslab mounted on /mnt/nfs42 with fstype nfs4 statvers=1.1
	opts:	rw,vers=4.2,rsize=1048576,wsize=1048576,...,hard,proto=tcp,timeo=600,retrans=2,sec=sys,...
	nfsv4:	bm0=0xfdffbfff,...,sessions,pnfs=not configured,lease_time=90,lease_expired=0
	...
	per-op statistics
	        READ: 6 6 0 1176 4196712 0 9 10 0
#             ops  transmissions  major timeouts  bytes sent  bytes received
#             queue ms  RTT ms  execute ms  errors     (the last three are cumulative)

Divide the cumulative RTT by the op count to get the average round-trip time; divide execute time the same way for the time the application waited. A large gap between execute and RTT means requests queued on the client (too few slots or connections). A large RTT means a slow network or a slow server. Transmissions above ops means retransmissions. For NFSv4, remember that each row counts COMPOUNDs of one kind: the OPEN row counts OPEN compounds.

Tools

  • nfsstat -c / -s: client or server operation counts since boot. nfsstat -m: each mount with its options.
  • mountstats /mnt/x (nfs-utils): formats one mount's mountstats block with per-op averages.
  • nfsiostat 5: per-mount operations per second, throughput, RTT and execute time, like iostat.
  • /proc/fs/nfsd/clients/ (server, Linux 5.3 and later): one directory per NFSv4 client, with info (name, address, minor version) and states (its opens, locks, delegations and layouts). nfsdclnts prints them as a table.
  • rpcdebug -m nfs -s all: turns on the kernel's old debug messages (very noisy). Tracepoints are the modern alternative: trace-cmd record -e nfs -e nfs4 -e sunrpc on the client, -e nfsd on the server.
  • tcpdump -s 0 -w f.pcap port 2049 and Wireshark or tshark: the operations inside every COMPOUND.

Check yourself

Why could an NFSv3 server be stateless, and what did that cost?

File handles let the server find any file from the request alone: they encode the filesystem id, the inode number and a generation number, so no per-client table is needed and a reboot looks like a slow server. The cost: no opens, so no share modes and no way to know who caches what; locking had to live in separate stateful protocols (NLM and NSM); and non-idempotent retransmissions needed the duplicate request cache heuristic.

A client wrote 2 MiB as UNSTABLE writes. The COMMIT reply carries a different verifier from the WRITE replies. What happened and what does the client do?

The server restarted between the writes and the commit, so data that was only in its page cache may be gone. The client still has the pages, so it resends every uncommitted WRITE and commits again.

What does the current file handle do in a COMPOUND, and why do RENAME and COPY need SAVEFH?

Each operation acts on the current file handle, which PUTFH, PUTROOTFH and LOOKUP set. Two-file operations need a second handle: SAVEFH stores the source (the old directory, or the source file), PUTFH sets the target, and the operation uses both.

Your NFSv4.0 clients sit behind NAT. Nothing fails, but caching seems poor. Why, and what fixes it?

4.0 callbacks require the server to connect back to the client. Through NAT that fails, so the server stops granting delegations and clients must revalidate on every open. NFSv4.1 and later send callbacks over the client's own connection, so mounting with vers=4.1 or 4.2 fixes it.

How do NFSv4.1 sessions give exactly-once semantics?

Each request carries a slot id and a sequence id. The server caches the last reply per slot. A retransmission arrives with the same slot and sequence id and gets the cached reply instead of running again, so a lost reply never causes a second REMOVE or a second lock.

Which system calls produce COPY, CLONE, SEEK, ALLOCATE and DEALLOCATE, and which need special support from the exported filesystem?

copy_file_range → COPY; ioctl(FICLONE) → CLONE; lseek(SEEK_DATA/SEEK_HOLE) → SEEK; fallocate → ALLOCATE; fallocate(PUNCH_HOLE) → DEALLOCATE. CLONE needs reflink support (XFS with reflink, btrfs; not ext4). Hole punching and allocation need fallocate support, which ext4 and XFS have.

A mount's mountstats shows WRITE with an average RTT of 2 ms but an average execute time of 40 ms. Where is the time going?

Mostly on the client: requests wait in a queue before they are sent, because all session slots or the connection are busy. Look at more connections (nconnect), the session slot limit, or the application's I/O pattern. The server and network answer in 2 ms.

Why is the async export option dangerous even though NFS has write verifiers?

With async the server acknowledges WRITE and COMMIT before the data is stable. After a COMMIT succeeds the client frees its copy. If the server then crashes, the verifier changes, but the client no longer has the data to resend. The loss is silent.
