Network filesystems: latency, partial failure, several caches

Lessons 1 to 5 kept the disk inside the machine. A file was an inode on a local block device, every process went through one kernel, and that kernel's page cache was the only copy of the data in RAM. A network filesystem keeps the files on a server and lets many clients use them through the ordinary file API. The application still calls open, read and write. The client kernel turns those calls into messages to the server.

Three things change when the disk moves away:

  • Latency. A page-cache hit costs well under a microsecond. A round trip to a server in the same rack costs tens to hundreds of microseconds over TCP, before the server touches its own disk. Every design decision in NFS is about avoiding round trips.
  • Partial failure. A local disk and the kernel fail together. A server can reboot while the client keeps running, and the network can drop or duplicate messages. The protocol has to say what happens to half-finished writes and to locks.
  • More than one cache. Each client caches data and attributes in its own RAM. The server has its own page cache too. Keeping them consistent is lesson 7.

NFS shares files. Remote block protocols such as iSCSI and NVMe over Fabrics share a disk: the client runs its own filesystem on top, so only one client can mount it read-write unless a cluster filesystem coordinates them (lesson 9). NAS (network-attached storage) usually means file protocols like NFS and SMB. SAN (storage area network) usually means block protocols.

The Linux NFS stack

Here is the path of one read() on a client whose page cache does not have the data. Every box is kernel code except the application.

  • VFS and page cache. The client VFS is the same one from lesson 5. NFS registers its own file_operations and address_space_operations, so a cache hit sends no READ: NFS only checks that the cache is still valid and lets the generic page-cache code copy the data.3334
  • NFS client (fs/nfs). Decides when to revalidate caches, batches dirty pages into WRITE calls, tracks NFSv4 state (client ID, opens, locks, delegations), and maps each VFS operation to NFS procedures.
  • SUNRPC (net/sunrpc). The generic ONC RPC layer: assigns transaction IDs, encodes and decodes arguments in XDR, retransmits on timeout, and multiplexes many outstanding calls over a connection. Both the client and the server side live here.
  • Transport. TCP (xprtsock) almost everywhere today. RDMA (xprtrdma on the client, svcrdma on the server) moves the bulk data with RDMA reads and writes; that is lesson 8. UDP is legacy, and many kernels are built without NFS-over-UDP support.35
  • nfsd (fs/nfsd). The in-kernel server. A pool of kernel threads, each handling one RPC at a time, calls into the server's VFS exactly as a local process would.36 Its replies come from the server's page cache when they can.
  • User-space helpers. rpc.mountd answers the MOUNT protocol and feeds export information to the kernel;37 rpcbind maps RPC program numbers to ports;38 rpc.statd handles NFSv3 lock recovery;39 nfsdcld records which NFSv4 clients may reclaim state after a server reboot;40 rpc.gssd and nfsidmap handle Kerberos and user-name mapping.4142
Aside

Not every NFS server is nfsd. NFS-Ganesha is a widely used user-space server that can export Ceph, GlusterFS and other backends,4344 and many storage appliances run their own implementations. The protocol is the contract; the Linux client talks to all of them.

ONC RPC and XDR

NFS is a set of remote procedures. The framework underneath is ONC RPC (Open Network Computing Remote Procedure Call, RFC 5531), and the encoding is XDR (External Data Representation, RFC 4506).4546 Every NFS message is an RPC call or reply.

The server finds the program and version, decodes the arguments, runs the procedure, and sends a reply with the same xid. The client matches replies to calls by xid, which is how many calls can be in flight on one connection.47 Over TCP each message is preceded by a 4-byte record mark that holds its length.48

XDR encoding rules

XDR encodes everything in big-endian 4-byte units. Integers are 4 or 8 bytes.495051 Variable-length data (strings, opaque blobs such as file handles) is a 4-byte length followed by the bytes, padded with zeros to a multiple of 4.52 The name "hello" becomes 12 bytes:

00 00 00 05   68 65 6c 6c   6f 00 00 00
length = 5    h  e  l  l    o  padding

There are no field names or tags on the wire. Both sides know the layout from the protocol specification, which is written in XDR's own definition language.53 That keeps messages compact and parsing cheap, and it is why Wireshark needs an NFS dissector to show anything useful.

RPC credentials: AUTH_SYS and RPCSEC_GSS

AUTH_SYS (once called AUTH_UNIX) sends numeric uid, gid and up to 16 supplementary group ids in every call.6364 The server believes them. Security therefore depends on trusting the client machine and the network.65 The export option root_squash maps uid 0 to an anonymous user so that root on a client is not root on the server, but any user who is root on a trusted client can still claim to be any other uid.66 The 16-group limit is real: users in more groups lose access unless the server looks groups up itself (rpc.mountd --manage-gids).67

RPCSEC_GSS uses Kerberos instead. The mount option sec= picks the level:41

  • sec=krb5: the user is authenticated with a Kerberos ticket. Data is not protected.
  • sec=krb5i: adds an integrity checksum to every message.
  • sec=krb5p: adds encryption ("privacy"). This costs CPU on both ends.68

A newer option encrypts the transport rather than each message: RPC-with-TLS (RFC 9289), enabled on recent Linux kernels with the xprtsec=tls or xprtsec=mtls mount option and the tlshd user-space handshake daemon.3269 It protects the connection; it does not by itself authenticate individual users.70

Identities in NFSv4. NFSv4 attributes name owners as strings, user@domain, rather than numbers.71 Client and server translate with nfsidmap, and a mismatched domain shows up as files owned by nobody.4271 With sec=sys Linux sends the numeric id as a string by default, which avoids that failure as long as uids match across machines.72

NFS file handles

A local process names an open file with an fd, which only makes sense inside one kernel. An NFS client names a file with a file handle: an opaque blob the server created and the client stores without interpreting.73 NFSv3 handles are at most 64 bytes; NFSv4 handles at most 128.7475 The client gets one from LOOKUP (or the MOUNT protocol, or NFSv4's PUTROOTFH), and every later operation on that file carries it.

  • Handles go stale. If the file is deleted and its inode number reused, the generation number stored in the inode no longer matches the one in the handle, and the server answers ESTALE ("Stale file handle").7778 The same happens if an export is moved to a filesystem with a different id. Filesystems without a stable UUID need an explicit fsid= export option for the same reason.66

NFSv3: a stateless server

An NFSv3 server keeps no record of which clients exist or which files they have open. Every request is self-contained: file handle, offset, count, credentials. There is no OPEN or CLOSE in the protocol. When a server crashes and comes back, clients just retransmit, and to them the crash looks like a slow server.13 That simplicity is why NFSv3 is still everywhere.

Unstable writes, COMMIT and the write verifier

NFSv2 required the server to put every WRITE on stable storage before replying, which made writes painfully slow.82 NFSv3 added a stable field to WRITE:

  • UNSTABLE: the server may reply as soon as the data is in its page cache.
  • DATA_SYNC: data on stable storage, metadata may lag.
  • FILE_SYNC: data and metadata on stable storage.82

The client sends a stream of UNSTABLE writes and later one COMMIT for the range, which makes the server flush it (an fsync on the server side). Until the COMMIT succeeds, the client keeps its copy of the data, because the server might crash and lose it.83

How does the client know the server crashed? Every WRITE and COMMIT reply carries an 8-byte write verifier, a value the server picks at boot.7482 If the verifier in the COMMIT reply differs from the one in the WRITE replies, the server restarted in between, and the client resends every write it has not seen committed.83

MOUNT, NLM, NSM and the duplicate request cache

NFSv3 left three jobs to other RPC programs. MOUNT (rpc.mountd) checks the export list and hands out the export's root file handle.37 NLM (lockd) implements fcntl byte-range locks, which need state the NFS protocol refuses to keep.59 NSM (rpc.statd) tells lock holders when a peer reboots, so clients can reclaim locks and servers can drop locks of dead clients.39 All of them sit behind rpcbind on port 111 with dynamic ports, which is why NFSv3 through a firewall means pinning ports in configuration.6784

Retransmission exposes a weakness of statelessness. A client sends REMOVE, the server removes the file, the reply is lost, the client retransmits. The second REMOVE fails with "no such file", although the operation succeeded.85 Servers paper over this with a duplicate request cache (DRC): recent replies to non-idempotent requests, keyed by xid and client address, are replayed on retransmission.8586 The DRC is a heuristic of limited size, and NFSv4.1 sessions replace it with a guarantee.8586

NFSv4.0: state, compounds, one port

NFSv4 gave up statelessness on purpose. Opens, locks and caching promises need state, and keeping that state inside the NFS protocol, with clear recovery rules, is simpler than three side protocols that each half-recover.

Key idea

Every piece of NFSv4 state (a client ID, an open, a lock, a delegation, a layout) is covered by the client's lease. The client keeps it alive by talking to the server, the server may drop it when the client goes silent, and after a server reboot the client reclaims it during the grace period.8788

COMPOUND and the current file handle

NFSv4 has exactly two RPC procedures: NULL and COMPOUND.89 A COMPOUND carries a list of operations that the server executes in order. The server keeps a current file handle while it works through the list: PUTFH or PUTROOTFH sets it, LOOKUP moves it to a child, and most operations act on it. SAVEFH and RESTOREFH keep a second handle for two-file operations such as RENAME, LINK, COPY and CLONE.9091 Execution stops at the first operation that fails, and the reply holds the results up to and including that one.89

Client ID, opens and stateids

Before doing anything stateful, a client introduces itself. In 4.0 that is SETCLIENTID and SETCLIENTID_CONFIRM; in 4.1 it is EXCHANGE_ID.9293 The client presents a long-lived name (Linux builds it from the hostname, or from nfs4_unique_id) and a boot verifier; the server returns a short client ID.9294 A changed boot verifier tells the server the client rebooted, so its old state can be thrown away.92

OPEN is a real operation. It names the file in the current directory, says whether to create it, and asks for share access (read, write, both) and optionally a share deny mode (Windows-style "nobody else may write").95 The reply carries a stateid: 16 bytes, a 4-byte sequence number plus 12 bytes that identify the state.96 READ, WRITE, SETATTR of the size, LOCK and CLOSE all present a stateid, so the server always knows which open a request belongs to.97 CLOSE releases it.

Byte-range locks are part of the protocol: LOCK, LOCKT (test) and LOCKU (unlock), each with its own lock stateid.9899 No lockd, no statd.

Leases and the grace period

State on a server is dangerous if the client that owns it disappears. NFSv4 solves this with a lease: the client's state is valid for a lease period, and any successful stateful operation renews it. An idle 4.0 client sends RENEW; a 4.1 client's SEQUENCE operation renews implicitly.8797 The Linux server's lease time is 90 seconds by default (/proc/fs/nfsd/nfsv4leasetime, or lease-time in nfs.conf).100101

When a client's lease expires, the server may release its opens and locks so others can proceed.87 Since Linux 5.19, nfsd is a "courteous server": it keeps an expired client's state until another client actually needs a conflicting lock or open, or until the server needs to free memory, so a client that was cut off by a network partition can often resume without losing anything.102103104

The reverse case is the server rebooting. Its in-memory state is gone, but clients still believe they hold opens and locks. For a grace period after boot (by default as long as the lease), the server refuses new opens and locks with NFS4ERR_GRACE and lets clients reclaim what they held.88100 To know who is allowed to reclaim, it records clients on stable storage (nfsdcld on Linux).4088 A 4.1 client sends RECLAIM_COMPLETE when it is done, so a server whose known clients have all finished can end grace early.88 Applications see the grace period as a pause of up to a minute and a half after a server restart.

Delegations and callbacks

A delegation is a promise from the server: "until I call you back, no other client will write this file" (a read delegation) or "no other client will open it at all" (a write delegation).105 While it holds one, the client can serve opens, reads and attribute queries from its cache without asking the server.105 When another client wants conflicting access, the server sends a CB_RECALL callback, the holder flushes and answers with DELEGRETURN, and the newcomer proceeds.106 Lesson 7 works through the timeline.

Callbacks reverse the usual direction: the server calls the client. In NFSv4.0 the server opens a new TCP connection to an address the client advertised in SETCLIENTID.62107 Behind NAT or a client firewall that connection fails, and a 4.0 server then quietly stops granting delegations.106 Nothing breaks, but caching gets worse. NFSv4.1 fixed this by sending callbacks over the client's own connection.2162

The pseudo-filesystem and ACLs

An NFSv4 server presents all its exports as one tree, the pseudo-filesystem. A client can mount server:/ and walk down into any export it is allowed to see; the directories that only join exports together are synthetic.108 Old Linux setups marked the root with fsid=0; current nfs-utils builds the pseudo-root automatically, so the NFSv4 path to an export is its real path on the server.66109

NFSv4 also defined its own ACL model: ordered lists of ALLOW and DENY entries with inheritance flags, much closer to Windows ACLs than to POSIX mode bits.110111 nfs4_getfacl and nfs4_setfacl from nfs4-acl-tools manipulate them.112 The Linux server stores them by translating to POSIX ACLs, which cannot express everything, so some NFSv4 ACLs are rejected or approximated.111113

NFSv4.1: sessions, trunking and pNFS

Sessions and exactly-once semantics

After EXCHANGE_ID, a 4.1 client calls CREATE_SESSION. The two sides negotiate channel attributes: largest request and reply, most operations per COMPOUND, and the number of slots, which is the number of requests the client may have outstanding at once.86114 Every COMPOUND then starts with a SEQUENCE operation:115

SEQUENCE { sessionid, slotid = 3, sequenceid = 118, highest_slotid = 15, cachethis = true }

The server keeps the last reply for each slot. A retransmission with the same slot and sequence id gets that reply back instead of being executed twice. That is exactly-once semantics (EOS), and it replaces the DRC heuristic with a guarantee whose memory cost the server chose at CREATE_SESSION.21116 The slot count doubles as flow control: a busy server can shrink highest_slotid to slow a client down.86 On Linux the client's upper bound is the nfs.max_session_slots module parameter.72

The backchannel and trunking

A session has a fore channel (client to server) and a backchannel (server to client). The backchannel normally rides on the same TCP connection the client opened, so callbacks work through NAT and firewalls.21114 That is a large practical reason to prefer 4.1 or 4.2 over 4.0.

Trunking means using several connections for one client. Session trunking binds several connections to one session (BIND_CONN_TO_SESSION), for example one per network interface. Client ID trunking uses several sessions under one client ID.117 On Linux, nconnect=N (up to 16) opens N TCP connections to the same server address and spreads RPCs over them; it also works with NFSv3.32118 It helps when one TCP connection, and the single CPU that tends to process it, is the bottleneck.

pNFS: metadata server, data servers and layouts

A single NFS server is a bottleneck for bandwidth: every byte passes through one machine. pNFS (parallel NFS) splits the server into a metadata server (MDS), which handles the namespace, opens and locks, and one or more data servers (DS), which hold the file contents. The MDS gives the client a layout: a map saying which data servers hold which byte ranges and how the file is striped. The client then reads and writes directly to the data servers, in parallel.119

  • LAYOUTGET asks for a layout for a byte range and access mode. Layouts are state, with their own stateid, and the MDS can recall them with CB_LAYOUTRECALL.119121
  • GETDEVICEINFO turns the device ids in a layout into addresses (IP addresses for file layouts, disk signatures for block layouts, SCSI device identifiers for SCSI layouts).122123124125
  • LAYOUTCOMMIT tells the MDS about writes done through the data servers, so it can update the file size and modification time.126
  • LAYOUTRETURN gives the layout back.127

Directory delegations

4.1 also defined directory delegations (GET_DIR_DELEGATION, with CB_NOTIFY for changes), so a client could cache a directory's listing and its negative lookups safely.135 For years almost nobody implemented them. COPY: server-side copy

Copying a 10 GiB file with read() and write() over NFSv3 moves 20 GiB over the network: down to the client and back up. With 4.2 the client sends one COPY with the source and destination stateids, offsets and a length.91 The source file handle goes in with SAVEFH, the destination with PUTFH, and the server copies locally, usually through its own copy_file_range.91150

  • Synchronous or asynchronous. The client may let the server run a long copy in the background. The COPY reply then carries a stateid, the client can poll with OFFLOAD_STATUS or stop it with OFFLOAD_CANCEL, and the server reports the result with a CB_OFFLOAD callback.151152
  • Intra-server or inter-server. If source and destination are on different servers, the client first sends COPY_NOTIFY to the source server, which authorises the destination server to read the file. The client then sends COPY to the destination server with the source server's address, and the destination server reads the data directly from the source as an NFSv4.2 client itself.91152153 Linux supports this, but it is off by default on the server: the destination needs nfsd.inter_copy_offload_enable=1 and a kernel built with CONFIG_NFSD_V4_2_INTER_SSC.72154155

CLONE and reflinks

CLONE asks the server to make a range of the destination file share the source's blocks, like cp --reflink locally.151 It only works if the exported filesystem supports reflinks: XFS (created with reflink, the default in recent xfsprogs), btrfs, and a few others.156157 ext4 does not, so CLONE on an ext4 export fails with EOPNOTSUPP.158 The Linux client remembers a NOTSUPP answer for the rest of the mount and stops sending the operation.159

Sparse files: SEEK and READ_PLUS

A sparse file has holes: ranges never written, which read as zeros and take no disk space (lesson 3). Before 4.2 a client could not tell holes from real zeros, so cp had to read every zero over the network and a sparse VM image became fully allocated on copy.160 SEEK implements lseek with SEEK_DATA and SEEK_HOLE on the server.161162 READ_PLUS is a READ whose reply is a list of segments, each either data or "a hole of N bytes".163 The Linux client uses READ_PLUS when it is built with CONFIG_NFS_V4_2_READ_PLUS, which has defaulted to on since 6.6 after an earlier attempt was reverted.164165166 The WSL kernel this course was tested on turns the option off, so it always sends READ.167

ALLOCATE and DEALLOCATE

fallocate(fd, 0, off, len) becomes ALLOCATE: the server reserves real blocks, so a later write cannot fail with ENOSPC.144168 fallocate(fd, FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE, off, len) becomes DEALLOCATE: the server frees the blocks and the range reads as zeros.169170 Before 4.2, glibc's posix_fallocate emulated reservation by writing to every block, over the network.171172

IO_ADVISE, WRITE_SAME, Labeled NFS

IO_ADVISE carries hints like "I will read this sequentially" or "I will not need this again", so the server can read ahead or drop pages.145 WRITE_SAME fills ranges with a repeated block pattern, aimed at databases that initialise files with a fixed header in each block;173 it is rarely implemented. As far as current kernels go, the Linux client sends neither. Labeled NFS adds the sec_label attribute so that SELinux labels on the server's files are visible to and enforced on clients; Linux enables it per export with the security_label option.66147

Extended attributes (RFC 8276)

Before RFC 8276, setfattr -n user.color on an NFS file failed.174 The four xattr operations carry user.* attributes only; the security. and trusted. namespaces do not cross the wire this way.175 Linux added client and server support in 5.9.176177 The client caches xattrs, so repeated getxattr calls may not reach the server.178

RFC 9754: opening and delegating files

RFC 9754 (March 2025) extends 4.2 opens and delegations:28

  • Delegated timestamps. The holder of a write delegation becomes the authority for the file's access and modify times. It no longer has to send SETATTR or force GETATTRs just to keep times right, and the server asks it with CB_GETATTR when another client needs them.179 The Linux client added support in 6.11.180 On the server side, the 6.18 kernel used for this course has it behind CONFIG_NFSD_V4_DELEG_TIMESTAMPS, which is off.181182
  • Only a delegation. An OPEN flag asks the server to return either an open stateid or a delegation stateid, not both, which reduces state on both sides.183
  • Discovering OPEN flags. A new attribute lists which OPEN flags the server supports.184
  • Offline files. A client can learn that a file's data is not immediately available (for example, archived to tape), so it can avoid hanging on it.185

Check yourself

Why could an NFSv3 server be stateless, and what did that cost?

File handles let the server find any file from the request alone: they encode the filesystem id, the inode number and a generation number, so no per-client table is needed and a reboot looks like a slow server. The cost: no opens, so no share modes and no way to know who caches what; locking had to live in separate stateful protocols (NLM and NSM); and non-idempotent retransmissions needed the duplicate request cache heuristic.

A client wrote 2 MiB as UNSTABLE writes. The COMMIT reply carries a different verifier from the WRITE replies. What happened and what does the client do?

The server restarted between the writes and the commit, so data that was only in its page cache may be gone. The client still has the pages, so it resends every uncommitted WRITE and commits again.

What does the current file handle do in a COMPOUND, and why do RENAME and COPY need SAVEFH?

Each operation acts on the current file handle, which PUTFH, PUTROOTFH and LOOKUP set. Two-file operations need a second handle: SAVEFH stores the source (the old directory, or the source file), PUTFH sets the target, and the operation uses both.

Your NFSv4.0 clients sit behind NAT. Nothing fails, but caching seems poor. Why, and what fixes it?

4.0 callbacks require the server to connect back to the client. Through NAT that fails, so the server stops granting delegations and clients must revalidate on every open. NFSv4.1 and later send callbacks over the client's own connection, so mounting with vers=4.1 or 4.2 fixes it.

How do NFSv4.1 sessions give exactly-once semantics?

Each request carries a slot id and a sequence id. The server caches the last reply per slot. A retransmission arrives with the same slot and sequence id and gets the cached reply instead of running again, so a lost reply never causes a second REMOVE or a second lock.

Which system calls produce COPY, CLONE, SEEK, ALLOCATE and DEALLOCATE, and which need special support from the exported filesystem?

copy_file_range → COPY; ioctl(FICLONE) → CLONE; lseek(SEEK_DATA/SEEK_HOLE) → SEEK; fallocate → ALLOCATE; fallocate(PUNCH_HOLE) → DEALLOCATE. CLONE needs reflink support (XFS with reflink, btrfs; not ext4). Hole punching and allocation need fallocate support, which ext4 and XFS have.170

A mount's mountstats shows WRITE with an average RTT of 2 ms but an average execute time of 40 ms. Where is the time going?

Mostly on the client: requests wait in a queue before they are sent, because all session slots or the connection are busy. Look at more connections (nconnect), the session slot limit, or the application's I/O pattern. The server and network answer in 2 ms.

Why is the async export option dangerous even though NFS has write verifiers?

With async the server acknowledges WRITE and COMMIT before the data is stable. After a COMMIT succeeds the client frees its copy. If the server then crashes, the verifier changes, but the client no longer has the data to resend. The loss is silent.
