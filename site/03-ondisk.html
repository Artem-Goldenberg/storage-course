Lesson 3 · Filesystem layer

Inside an ext4 image

A disk is a numbered array of blocks. This lesson opens a real ext4 filesystem and shows the handful of records that turn those numbers into directories, names and files, down to the byte offset of every field you need.

After this lesson you can
  • find and decode the superblock, a group descriptor and an inode in a hex dump;
  • turn an inode number into a byte offset on the device with two divisions;
  • follow an inode's extents to the file's data, and recognise a hole;
  • resolve a path on disk the way the kernel does, one directory per component;
  • say what the journal protects after a crash, and what it does not.

The job: names on top of numbers

In lesson 02 the device gave us two operations: read block n and write block n. Programs want something else. They ask for /docs/notes/hello.txt, expect it to have an owner, a size and permissions, and expect its bytes to come back in order. A filesystem bridges the two. It is a data structure stored in the blocks themselves, and it has to answer five questions quickly:

  1. Where does the filesystem begin, and what shape does it have? The superblock answers that.
  2. For a given file, who owns it, how big is it, and when was it changed? That is the inode.
  3. Which disk blocks hold the file's bytes, in which order? The inode's block map, which on ext4 is a set of extents.
  4. Which file does a name refer to? A directory, which is a file full of (name, inode number) records.
  5. Which blocks and inodes are free? The bitmaps.

On top of those it needs a way to keep them consistent when the power fails halfway through an update. ext4 uses a journal.

We use ext4 as the worked example because it is the default on Debian and Ubuntu, it is the filesystem under this WSL's own root (df -T / says ext4), and its format is documented down to the byte in the kernel tree. Every number in this lesson comes from a 16 MiB image built in Lab 03, so you can reproduce each one.

Key idea

A filesystem is a data structure whose nodes are disk blocks. Every operation (open, read, create, delete) is a walk over that structure. If you can follow the pointers by hand, nothing a filesystem does is mysterious.

The map of an ext4 volume

ext4 cuts the volume into block groups. Each group covers s_blocks_per_group blocks, which is 8 × block size: one block of bitmap has 8 bits per byte, and each bit tracks one block. With 4 KiB blocks a group is 32,768 blocks, or 128 MiB. A 1 TiB disk has 8,192 groups.

Each group can carry:

  • a backup copy of the superblock and the group descriptor table (with the sparse_super feature, only groups 0, 1 and powers of 3, 5 and 7 carry them);
  • a block bitmap: one bit per block in the group, 1 = in use;
  • an inode bitmap: one bit per inode slot in the group;
  • an inode table: the group's inodes, stored as an array of fixed-size records;
  • data blocks: everything else, including file contents, directory contents and extent tree blocks.

The groups exist for locality. ext4 tries to put a file's inode, its directory and its data in the same group, so a spinning disk does not seek across the platter to read one file. Groups also keep each bitmap to one block, and let independent allocations proceed in different groups.

Modern ext4 adds flex_bg. It packs the bitmaps and inode tables of 16 consecutive groups together at the start of the first one, so the metadata of a whole flex group is contiguous and large data extents are not chopped up by metadata every 128 MiB. Step 1: the superblock

The superblock is always at byte 1024, whatever the block size. The first 1024 bytes are left free for a boot sector. Reading by byte offset lets a driver find the superblock before it knows the block size, which is itself stored in the superblock. With 4 KiB blocks the superblock sits inside block 0. With 1 KiB blocks it fills block 1, and s_first_data_block is 1.

All multi-byte fields are little-endian. The magic number 0xEF53 is stored at byte 1024 + 0x38 = 0x438 as the two bytes 53 ef:

$ xxd -s $((1024 + 0x38)) -l 2 disk.img
00000438: 53ef                                     S.

The three feature masks are how one on-disk format grew from ext2 (1993) through ext3 (journal) to ext4 (extents, 64-bit block numbers, checksums) without breaking old kernels unsafely:

  • compat (has_journal, dir_index, ext_attr): an old driver that does not know the bit can still mount read-write.
  • ro_compat (metadata_csum, huge_file, dir_nlink): an old driver may mount read-only, because writing would leave the new structures stale.
  • incompat (extents, 64bit, flex_bg, filetype): an old driver must refuse, because it would misread the data.

The lab image has has_journal ext_attr resize_inode dir_index filetype extents 64bit flex_bg sparse_super large_file huge_file dir_nlink extra_isize metadata_csum, which is what mkfs.ext4 on Ubuntu 24.04 turns on by default (see /etc/mke2fs.conf).

Step 2: the group descriptor table

The group descriptor table (GDT) starts in the block after the one holding the superblock, block s_first_data_block + 1. It is an array with one descriptor per group. Each descriptor is 32 bytes on filesystems without 64bit. With 64bit it is s_desc_size bytes (64 in practice), and the extra 32 bytes carry the high halves of the block numbers.

OffsetFieldSizeMeaning
0x00bg_block_bitmap_lo4block number of this group's block bitmap
0x04bg_inode_bitmap_lo4block number of the inode bitmap
0x08bg_inode_table_lo4first block of the inode table (35 in the lab)
0x0Cbg_free_blocks_count_lo2free blocks in the group
0x0Ebg_free_inodes_count_lo2free inodes in the group
0x10bg_used_dirs_count_lo2directories in the group (the allocator uses it to spread them)
0x12bg_flags2e.g. INODE_ZEROED: the table was zeroed
0x1Ebg_checksum2checksum of the descriptor
0x20bg_block_bitmap_hi4high 32 bits (64-byte descriptors only)
0x28bg_inode_table_hi4high 32 bits of the inode table block

The bitmaps are the simplest structure in the filesystem. Bit i of a group's block bitmap says whether block group_start + i is in use. Finding a free block means scanning for a 0 bit. Freeing a block means clearing one bit and bumping the free counts in the descriptor and the superblock. The inode bitmap does the same for inode slots.

The free counts are duplicated on purpose. df reads them from the superblock in constant time instead of scanning every bitmap, which is why df is instant on a full 20 TB volume while du on the same volume takes minutes.

Step 3: an inode number is an address

Every file and directory has an inode, and inodes are numbered from 1. Because each group's inode table is a fixed array of fixed-size records, an inode number is effectively an address. Two divisions and a multiply find it:

group  = (ino - 1) / s_inodes_per_group
index  = (ino - 1) % s_inodes_per_group
offset = bg_inode_table[group] * block_size + index * s_inode_size

Some inode numbers are reserved. Inode 1 tracks bad blocks, inode 2 is always the root directory, inode 7 holds reserved GDT blocks for online resize, inode 8 is the journal, and the first ordinary inode is s_first_ino, normally 11, which mkfs gives to lost+found.

This design has a consequence you can hit in production. The inode tables are allocated by mkfs and never grow, so the number of files is fixed at format time by the inode_ratio (one inode per 16 KiB of disk by default). A disk filled with millions of tiny files can report No space left on device while df shows free gigabytes. df -i shows the inode count running out. XFS avoids this by allocating inodes dynamically, as we will see at the end of the lesson.

The inode record

An inode holds everything about a file except its name and its data. The first 128 bytes are the classic ext2 layout. The rest of a 256-byte inode holds extensions such as nanosecond timestamps, creation time and small extended attributes.

Aside

The 32-bit timestamps would overflow in 2038. The extra fields in a 256-byte inode add nanoseconds and two extra epoch bits, which push the limit out to the year 2446. Filesystems made with 128-byte inodes do not have that room, and newer mkfs versions warn about it.

From inode to data: block maps and extents

The 60 bytes of i_block say where the file's data is. ext2 and ext3 used them as 15 block pointers of 4 bytes each:

The pointer scheme is simple and works, but it needs one pointer per block, however neatly the blocks are laid out. A 1 GiB file stored contiguously still needs 262,144 pointers, which is 1 MiB of indirect blocks, and deleting it means reading all of them to learn which blocks to free. The scheme also tops out at 232 blocks.

An extent describes a run: "file blocks L to L+n−1 live at disk blocks P to P+n−1". ext4 packs that into 12 bytes:

StructFields (offset: name)Role
ext4_extent_header0x0 eh_magic (0xF30A), 0x2 eh_entries, 0x4 eh_max, 0x6 eh_depth, 0x8 eh_generationstarts every node of the tree
ext4_extent0x0 ee_block, 0x4 ee_len, 0x6 ee_start_hi, 0x8 ee_start_loleaf entry: one run of blocks
ext4_extent_idx0x0 ei_block, 0x4 ei_leaf_lo, 0x8 ei_leaf_hiindex entry: "file blocks from here on are described by the node in this block"

One extent covers up to 32,768 blocks (128 MiB at 4 KiB). If ee_len is above 32,768 the extent is unwritten: the blocks are reserved, for example by fallocate(), but have never been written, so reads return zeros without touching the disk. A file of 100 KB written in one go needs one extent. In the lab, /data/big.txt is 102,000 bytes: 25 blocks in one extent.

The inode's 60 bytes hold a 12-byte header and four extents. A file needing a fifth extent grows a tree: the four entries move to a new block that holds 340 of them, and the inode's root becomes an index node pointing to it. That tree is a B+tree, and it is the subject of lesson 04.

Holes

If no extent covers a file block, that block is a hole. It has no disk block, and reading it returns zeros. /data/sparse.dat in the lab is 1,048,726 bytes long but occupies two blocks: ls -ls shows 8 KiB allocated, and its i_blocks is 16 (512-byte units). i_size is the logical length, and i_blocks is what the file costs on disk. du reports the second, and ls -l the first.

Symlinks

A symbolic link is an inode whose data is the target path. When the target is shorter than 60 bytes, ext4 stores it directly in i_block and allocates no data block at all. That is a fast symlink, and it has no EXTENTS_FL. Longer targets get a data block like any file. The lab has one of each.

Directories are files of names

A directory is an inode with type S_IFDIR whose data blocks contain directory entries. Each entry is an ext4_dir_entry_2:

OffsetFieldSizeMeaning
0x0inode4inode number; 0 means "unused entry"
0x4rec_len2bytes from this entry to the next one
0x6name_len1length of the name
0x7file_type11 file, 2 dir, 3 char dev, 4 block dev, 5 fifo, 6 socket, 7 symlink
0x8namename_lennot NUL-terminated; the entry is padded to a 4-byte boundary

Entries are packed one after another. rec_len is the link to the next entry, and the last entry's rec_len stretches to the end of the block. Here is the /docs directory block of the lab image, decoded:

A few consequences follow from this layout:

  • . and .. are real entries, written into every directory.
  • Deleting an entry does not shift anything. The previous entry's rec_len grows to swallow it, and the bytes stay on disk until reused.
  • Creating an entry means finding an entry with enough slack after its own name, splitting its rec_len, or appending a new block.
  • The file_type byte duplicates information from the inode. It is there so readdir can report each entry's type (d_type) without reading every inode, which makes find -type d and ls --color much cheaper.
  • Lookup is linear. Finding one name means reading the directory's blocks until it appears. In a directory with 100,000 files, a single open() could scan megabytes. ext4 fixes this with an index called the htree, a B-tree keyed by a hash of the name, covered in lesson 04.

Resolving a path on disk

Now the pieces combine. To open /docs/notes/hello.txt with nothing cached, a reader does this:

  1. Read inode 2, the root directory. Map its data with its extents.
  2. Scan the root's directory blocks for docs. Get inode 16.
  3. Read inode 16, check it is a directory, scan it for notes. Get inode 19.
  4. Read inode 19, scan it for hello.txt. Get inode 17.
  5. Read inode 17. Its extents say where the bytes are.

This is what ext4walk from the lab prints (trimmed):

-- "/"
  inode 2: group = (2-1) / 4096 = 0, index = (2-1) % 4096 = 1
    inode at byte 143616 = 35 * 4096 + 1 * 256
    i_mode 0040755 (directory)  i_size 4096  i_links_count 5  i_flags 0x80000 EXTENTS
      extent: file blocks 0..0 -> disk blocks 4..4 (1 block)
    dir block 0 = disk block 4: .(2) ..(2) lost+found(11) data(12) docs(16)  <- "docs" found
-- "docs"
  inode 16: ... dir block 0 = disk block 1320: .(16) ..(2) hello-again.txt(17) latest(18) notes(19)  <- "notes" found
-- "notes"
  inode 19: ... dir block 0 = disk block 1322: .(19) ..(16) hello.txt(17)  <- "hello.txt" found
-- "hello.txt"
  inode 17: i_mode 0100644 (regular file)  i_size 256  i_links_count 2  i_flags 0x80000 EXTENTS
      extent: file blocks 0..0 -> disk blocks 1321..1321 (1 block)

Cold, each component costs at least two block reads, one in the inode table and one in the directory. A path ten levels deep is twenty reads before the first byte of data. The kernel avoids nearly all of them with the dentry cache, which remembers (parent, name) → inode, and the inode cache. Both are the subject of lesson 05. The on-disk walk only happens on a cache miss.

The kernel also checks permissions at every step. To pass through a directory you need execute (search) permission on it. That is why chmod 700 ~/private protects every file below it, whatever those files' own modes are.

Mount points are handled one layer up. When the walk reaches a directory that has another filesystem mounted on it, the VFS switches to that filesystem's root inode. ext4 never sees it.

Hard links, link counts and deletion

Because names live in directories, nothing stops two entries from holding the same inode number. That is a hard link. ln a b adds an entry and increments i_links_count. Neither name is the original. In the lab, /docs/hello-again.txt and /docs/notes/hello.txt both resolve to inode 17, and its link count is 2.

Directories have a predictable link count: 2 + the number of subdirectories. One link is the entry in the parent, one is the directory's own ., and each subdirectory's .. adds one. The lab's root has lost+found, data and docs, so its count is 5. (With the dir_nlink feature, a directory with more than 65,000 subdirectories sets its count to 1, meaning "not tracked".)

Deleting a file with unlink() works on names:

  1. Remove the directory entry by merging it into its neighbour's rec_len.
  2. Decrement i_links_count.
  3. If the count reaches 0 and no process has the file open, free it: walk the extents, clear their bits in the block bitmap, clear the inode's bit in the inode bitmap, set i_dtime, and update the free counts.
  4. If a process still has it open, the inode goes on the orphan list, and the space is freed at the last close(). If the system crashes first, the next mount finds the orphan and finishes the job, so the space does not leak.

Nothing is overwritten. The bits flip, and the old bytes remain in the free blocks until something else is allocated there. That is why undelete tools sometimes work and why secure deletion needs more than rm.

Allocation: choosing blocks

Reading the structures is half the job. The other half is deciding where new things go, and the goal is the same at every scale: put things that are read together next to each other, in long contiguous runs.

  • Directories are spread, files are clustered. The Orlov allocator places new top-level directories in groups with many free inodes and blocks, and places files and subdirectories in or near their parent's group.
  • The multi-block allocator (mballoc) allocates many blocks per request, using buddy bitmaps in memory to find free runs of power-of-two sizes quickly. It also keeps per-file and per-CPU preallocations so that small appends land next to each other.
  • Delayed allocation is the biggest win. A write() only copies data into the page cache and reserves space. Real blocks are chosen later, when the data is written back (lesson 05). By then the kernel often knows the file's final size and can allocate one large extent instead of a series of small ones.
Pitfall

Delayed allocation widens the window in which data exists only in memory. In 2009 many applications lost file contents after crashes on early ext4, because they wrote a new file and renamed it over the old one without calling fsync(). The rename was journaled, the data had not been allocated yet, and after the crash the file was empty. ext4 added a heuristic (auto_da_alloc) that forces allocation in that pattern. The safe pattern is still write, fsync, rename, covered in lesson 05.

Over time free space fragments, and new files get split into many extents. filefrag -v shows a file's extents, and e4defrag rewrites fragmented files. Fragmentation matters less on SSDs than on spinning disks, but it never stops mattering completely, because more extents mean a deeper tree and more, smaller I/Os.

Crash consistency: the journal

Creating one file touches several blocks: the inode bitmap, the inode itself, the parent directory's block, the parent's inode (mtime), and the free counts in the group descriptor. The disk writes them one at a time and can reorder them. If the power fails after some writes and before others, the filesystem is inconsistent. A directory entry might point at an inode still marked free, or a block might be marked used with no file owning it.

ext2's answer was fsck: after an unclean shutdown, scan every inode, bitmap and directory and repair the contradictions. That takes time proportional to the size of the filesystem, which means hours on large disks.

ext3 and ext4 add a write-ahead journal, managed by the kernel's jbd2 layer and stored in inode 8. Before any metadata block is written to its home location, the change is first written to the journal:

The commit block is the atomic switch. A transaction either has a valid commit block in the journal or it does not. At mount, recovery replays every committed transaction and discards anything after the last commit. That takes seconds, regardless of the disk's size.

jbd2 batches many operations into one transaction and commits every 5 seconds by default (the commit= mount option), or sooner when a program calls fsync(). ext4 offers three data modes:

ModeWhat goes through the journalAfter a crash
data=ordered (default)metadata only; data blocks are forced to disk before the metadata that refers to them commitsconsistent; a file never shows another file's old blocks
data=writebackmetadata only, with no ordering for dataconsistent metadata, but a recently extended file can contain stale garbage
data=journalmetadata and datastrongest, and every byte is written twice
Pitfall

The journal protects the filesystem's own structures. It does not make your writes durable. Data still in the page cache when the power goes is lost, journal or not, and the journal does not make an update to two files atomic. Durability is the application's job, through fsync(), and lesson 05 shows how to do it right.

The other answer: copy-on-write

btrfs and ZFS solve the same problem without a journal. They never overwrite a live block. A change is written to a new location, which means the block that points at it must also change, and so on up to the root. A commit writes the new root's location into the superblock (ZFS calls it the uberblock) in one atomic write. Before that write the old tree is intact, and after it the new tree is complete, so there is never a moment when the disk holds a half-updated structure.

Copy-on-write has three big benefits. Snapshots are nearly free: keep the old root and its blocks. Every pointer can carry a checksum of the block it points to, so silent corruption is detected on read. And there is no double write of metadata. The costs are fragmentation of files that are overwritten in place (databases, VM images) and more complex free-space accounting, because a block may be shared by several snapshots. Lesson 04 shows the copy-on-write B-tree that btrfs is built on.

XFS in one section

XFS, the default filesystem on Red Hat Enterprise Linux, answers the same questions with trees where ext4 uses arrays. It divides the volume into allocation groups (AGs) of up to 1 TiB, each almost an independent filesystem with its own free-space and inode indexes, so many threads can allocate in parallel. Inodes are not preallocated in fixed tables. They are created on demand in chunks of 64 and tracked by a per-AG B+tree, and an inode number encodes the AG, block and slot where it lives, so it is still an address. Free space is tracked by two B+trees per AG instead of a bitmap. A file's extents live in the inode until they outgrow it and then move to a B+tree, and large directories are B+trees keyed by name hash. Metadata is journaled, data is not. Because every structure is a tree, XFS is the natural next stop after this lesson: lesson 04 takes it apart.

Check yourself

The superblock is at byte 1024. On a filesystem with 1 KiB blocks, which block is that, and where does the group descriptor table start?

Block 1, so s_first_data_block is 1. The descriptor table starts in the next block, block 2. With 4 KiB blocks the superblock is inside block 0 and the table starts at block 1.

s_inodes_per_group is 8192, inodes are 256 bytes, blocks are 4 KiB, and group 3's bg_inode_table is 98304. At what byte is inode 24,600?

Group = 24599 / 8192 = 3 (integer division), index = 24599 − 3 × 8192 = 23. Byte = 98304 × 4096 + 23 × 256 = 402,653,184 + 5,888 = 402,659,072.

Why does mv big.iso archive/big.iso take the same time for a 1 KB file and a 100 GB file on one filesystem?

Only directory entries change: one entry is removed from the source directory and one added to the target. The inode, its extents and the data blocks are untouched, because names are not stored in the inode.

A file's ls -l size is 1 GiB, but du says 8 KiB. How?

It is sparse. i_size is the logical length, and only two blocks are mapped by extents. The rest are holes: no extent covers them, they use no disk space, and they read as zeros. du reports i_blocks.

A directory has three subdirectories. What is its link count, and why?

5: its entry in the parent, its own ., and the .. of each of the three subdirectories.

A 2008 kernel mounts a filesystem whose superblock has an unknown bit in s_feature_ro_compat. What happens? And for an unknown incompat bit?

An unknown ro_compat bit allows a read-only mount only, since writing could leave the new structure stale. An unknown incompat bit makes the kernel refuse to mount, since it might misread the data itself.

With data=ordered, can a file that was being appended when the power failed contain another, deleted file's old bytes after reboot?

No. In ordered mode the new data blocks are written before the transaction that allocates them commits. Either the allocation is not committed (the append is lost) or it is committed with the right data. With data=writeback this ordering is not enforced, and stale blocks can appear.

Why does ext4 store file_type in each directory entry when the type is already in the inode's i_mode?

So readdir() can return each entry's type (d_type) without reading one inode per entry. Tools that only need to know "is this a directory?" (find, ls --color, du) save one random read per file.
