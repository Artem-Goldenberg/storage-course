Lesson 4 · Filesystem layer

B-trees, really

Every filesystem and database you will meet keeps its indexes in some kind of B-tree. This lesson explains why the shape wins on disks, how the tree stays balanced, and then opens the real ones: ext4's extent tree and htree, XFS, btrfs, and three databases.

After this lesson you can
  • estimate a B-tree's height from its node size, entry size and key count, and say what a lookup costs;
  • insert into a B+tree by hand, including a split that reaches the root;
  • read debugfs output for an ext4 extent tree and an htree, and explain each number;
  • name the B-trees inside XFS and btrfs and the question each one answers;
  • say when a log-structured merge tree beats a B-tree, and what it costs.

Why disks want short, fat trees

Every index answers the same question: given a key, where is the thing? In lesson 03 the keys were file block numbers (where is block 700 of this file?) and names (which inode is hello.txt?). The answer has to come back fast even when there are millions of keys, and the index itself lives on the same slow device as the data.

The cost model from lesson 02 decides the design. The device reads whole blocks, and one random read costs about 5–10 ms on a hard disk and 10–100 µs on an NVMe SSD. Reading 12 bytes costs the same as reading 4096. What matters is how many separate blocks a lookup has to touch. Comparisons inside a block are almost free: a CPU can binary-search 340 keys in the time it takes an NVMe drive to notice a request.

A binary search tree, the structure from a first algorithms course, holds one key per node and has two children. Holding a million keys takes about 20 levels (220 ≈ 1,000,000). If each node is a separate disk block, a lookup is 20 random reads: around 160 ms on a hard disk. A sorted array searched by binary search has the same problem, and inserting into it means shifting everything after the insertion point.

A B-tree makes each node exactly one block and packs as many keys into it as will fit. The number of children per node is the fanout. ext4's extent entries are 12 bytes and its tree nodes have a 12-byte header, so one 4 KiB node holds (4096 − 12) / 12 = 340 entries. With fanout F, a tree over N keys has height ⌈logF N⌉:

  • 1,000,000 keys at fanout 340: 3 levels (3402 = 115,600 is too few, 3403 ≈ 39 million is enough);
  • 1,000,000,000 keys at fanout 340: 4 levels.

The second advantage is just as important. The upper levels are tiny. In the million-key tree, the root and the nine nodes below it are 40 KiB, which the kernel keeps in its cache because every lookup touches them. In practice a lookup in a warm tree reads one block from the device, the leaf.

Key idea

A B-tree's height is the logarithm of the key count, base fanout. Fanout is the knob: bigger nodes or smaller entries give a shorter tree. Every design in this lesson is a different answer to "what goes in an entry, and how many fit in a node?"

The rules of a B-tree

Rudolf Bayer and Edward McCreight described the B-tree in 1970, while working at Boeing's research labs, as a way to index files on disk. By 1979 Douglas Comer could title a survey The Ubiquitous B-Tree. The rules are few:

  1. Each node is one block. A node holds up to m − 1 keys, in sorted order, and an internal node with k keys has k + 1 children. m is the order of the tree.
  2. The keys of a node divide the key space. Every key in the subtree left of key i is smaller than it, and every key to its right is greater or equal.
  3. Every node except the root is at least half full.
  4. All leaves are at the same depth. That is the "balanced" in balanced tree, and it guarantees every lookup reads the same number of nodes.
Terminology

"Order" is used inconsistently. Knuth's order, used here and in the demo, is the maximum number of children. Bayer and McCreight's order d was the minimum number of keys, so their nodes hold between d and 2d keys. Check which one a text means before comparing numbers.

Search

Read the root. Binary-search its keys to find the child whose range contains the key, read that child, and repeat until a leaf. The cost is one block read per level, and the comparisons inside each block are free by comparison. ext4 does exactly this in ext4_ext_binsearch_idx() and ext4_ext_binsearch().

Insert

Search for the leaf where the key belongs and put it there in sorted position. If the leaf now has too many keys, split it: keep the lower half, move the upper half to a newly allocated node, and insert a separator key plus a pointer to the new node into the parent. The parent may now be too full too, so the split can repeat one level up, and so on.

If the split reaches the root, the root splits into two nodes and a new root is created above them with one separator and two children. This is the only way the tree gets taller. A B-tree grows at the top, so every leaf moves one level down at the same moment, and rule 4 can never be broken.

Delete

Remove the key from its leaf. If the leaf falls below half full, either borrow a key from a sibling (moving the separator in the parent to match) or merge with a sibling and remove their separator from the parent. A merge can make the parent underfull, so this can cascade too. If the root is left with a single child, that child becomes the root and the tree gets one level shorter.

Real systems often skip most of this. Merging is complex, needs locks on several nodes, and rarely pays off because deleted space tends to be refilled. PostgreSQL's B-tree, for example, only removes a page once it is completely empty, and its documentation says plainly that merging partly full pages is impractical under concurrent scans.

How full are the nodes?

With random insertions, nodes end up about 69% full on average (ln 2, a result due to Andrew Yao in 1978). With ascending insertions, such as auto-increment IDs or timestamps, a 50/50 split leaves every node half full, because the left half of each split never receives another key. PostgreSQL detects this case: when it splits the rightmost leaf, it leaves the left page 90% full (its default fillfactor) instead of half full. ext4 does something similar for append-only files, as you will see below.

B+trees: the variant everyone uses

The original B-tree stores each key, with its value, exactly once, in whichever node it lands in. Almost every real system uses a variant called the B+tree:

  • All records live in the leaves.
  • Internal nodes hold only separator keys and child pointers. A separator only has to sort between its neighbours, so it can be a copy of a key or a shortened version of one.
  • Leaves are often linked left to right, so a range scan ("all keys from 30 to 70") finds the first leaf and then follows links without going back up the tree.

Internal nodes with no values in them have the highest possible fanout, which keeps the tree short. The cost is that every lookup goes all the way to a leaf, but it would have done that in most cases anyway.

The split rule changes slightly. When a leaf splits, the first key of the new right leaf is copied up as the separator, because the key must stay in a leaf where its record is. When an internal node splits, its middle separator moves up and is removed from both halves, because separators are only signposts.

When filesystem documentation says "B-tree", it nearly always means a B+tree: the ext4 extent tree, the XFS trees and the btrfs trees all keep their records in the leaves. They differ in whether leaves are linked. XFS links every level in both directions. ext4's extent tree and btrfs have no sibling links. ext4 finds the next leaf by going back up through the path it has already read, and btrfs cannot have them at all, for a reason we will see in the btrfs section.

ext4's extent tree

Lesson 03 showed that an ext4 inode's 60-byte i_block holds a 12-byte ext4_extent_header and room for four 12-byte entries. That space is the root node of a B+tree. Every node of the tree, in the inode or in a block, starts with the same header:

FieldMeaning
eh_magic0xF30A, so a stray block is not mistaken for a tree node
eh_entriesentries in use
eh_maxcapacity: 4 in the inode, 340 in a 4 KiB block
eh_depth0 means the entries are ext4_extent leaves; above 0 they are ext4_extent_idx index entries

An index entry, ext4_extent_idx, is (ei_block, ei_leaf): "file blocks from ei_block onwards are described by the node in disk block ei_leaf". A block holds (4096 − 12) / 12 = 340 entries, and the last 4 bytes hold an ext4_extent_tail checksum when metadata_csum is on.

Lab 04 builds three files whose blocks are each followed by a hole, so no two extents can merge. debugfs's ex command prints the tree, one line per entry, with Level a/b meaning "a node at depth a of a tree whose leaves are at depth b":

The tree grows in a way worth noticing. When a leaf is full, ext4 first looks up the path for an index node with a free slot and splits below it (ext4_ext_split()). When every node on the path is full, it grows the tree in depth (ext4_ext_grow_indepth()). It does not split the root in two. It copies the entire root out of the inode into a newly allocated block and leaves the inode with a single index entry pointing at that block. That is why both twenty and deep have exactly one entry in the inode.

The kernel also chooses its split point for the common case of appending. If the new extent goes after the last entry in a full leaf, ext4 does not split the leaf in half. It starts a new, nearly empty leaf and leaves the full one alone, so a file written front to back ends up with full leaves. (The lab image was built by mkfs.ext4 -d, whose library splits differently, which is why its leaves hold 339 entries instead of 340.)

The depth is capped at 5 (EXT4_MAX_EXTENT_DEPTH). Depth 4 already allows 4 × 3404 ≈ 53 billion extents, more than the 232 blocks a file can have, so no valid file reaches the cap; the kernel uses it to reject corrupted headers. Real files almost never need more than depth 2, and most files have depth 0. The kernel also keeps an in-memory cache of extents it has looked up, the extent status tree, so a warm read often never touches the on-disk tree at all.

The htree: a B-tree over name hashes

Lesson 03 ended with a problem. A directory is a list of entries, and finding a name means scanning it. ext3 and ext4 solve this with the htree, designed by Daniel Phillips around 2001. It is a B+tree keyed by a 32-bit hash of each name.

Hashing gives fixed-size keys, so an index entry is just 8 bytes, (hash, block), and a 4 KiB index block holds about 500 of them. Hashes also spread names evenly, so leaves fill evenly whatever the names look like. The cost is that the tree can only answer "where is exactly this name?". It cannot list names in alphabetical order or find a prefix.

Hiding an index in plain sight

The htree was added to an existing format, and it is designed so that code that has never heard of it still sees a valid directory. Directory block 0 becomes the dx_root:

OffsetContentsWhat old code sees
0x00. entry, rec_len 12the usual .
0x0C.. entry, rec_len = block size − 12.. followed by a lot of slack space
0x18dx_root_info: reserved_zero, hash_version (byte 0x1C), info_length = 8, indirect_levels (byte 0x1E)slack
0x20limit and count (2 bytes each), then block: entry 0, which has no hashslack
0x28dx_entry array: (hash, block), 8 bytes each, sorted by hashslack

Interior index blocks (dx_node) start with a fake entry whose inode is 0 and whose rec_len covers the whole block, so old code sees an empty block. The leaves are ordinary directory blocks in the lesson 03 format. An old driver can still read the directory linearly, which is why dir_index is a compat feature.

Collisions, depth and order

  • Collisions. Two names can share a hash. Real hashes always have the low bit cleared, and ext4 uses that bit in a dx_entry to mean "this leaf continues the previous hash". When the bit is set, a lookup that misses in one leaf also checks the next.
  • Depth. With indirect_levels 0 the root points straight at leaves, enough for 507 leaf blocks. Beyond that a level of dx_node blocks appears, each holding 510 entries, for 507 × 510 = 258,570 leaf blocks. Without the largedir feature that is the limit. With it a third index level is allowed. In a separate test with 40,000 long names (873 directory blocks), the tree had indirect_levels 1 and every lookup read exactly 3 blocks.
  • Order. readdir() on an indexed directory returns names in hash order, which is why ls -f output looks shuffled. The position a program gets back from telldir() is the hash itself, so a listing can resume correctly even if entries were added in between. NFS servers pass the same positions to clients as READDIR cookies.
Pitfall

Building the 40,000-name directory with mkfs.ext4 -d took almost three minutes, because the library inserted each name into a still-linear directory and scanned it first. The cost is quadratic. Software that creates huge directories without an index, or on filesystems without one, hits the same wall.

XFS: a forest of B+trees

Lesson 03 introduced XFS's allocation groups (AGs). Inside each AG almost every question is answered by its own B+tree. Each tree block starts with a 4-byte magic number, so you can tell them apart in a hex dump:

TreeMagicKeyed byAnswers
bnobtAB3Bstart block of each free extent"Is there free space next to block B?" Used to merge freed space with its neighbours and to allocate near related data.
cntbtAB3Clength of each free extent"Where is a free extent of at least N blocks?"
inobtIAB3first inode of each 64-inode chunk"Where is inode I, and which inodes in its chunk are free?"
finobtFIB3same, only chunks with a free inode"Give me a free inode" without walking a full inobt.
rmapbtRMB3physical block"Who owns block B?" Needed by online repair and reflink.
refcountbtR3FCphysical block"How many files share this extent?" (reflink copies)
bmbt (per file)BMA3file offsetthe file's extent map, once it no longer fits in the inode
dabtree (per directory or xattr set)severalhash of the namelarge directories and attribute sets, like ext4's htree

Keeping free space in two trees with the same records sorted two ways is a classic trick. The allocator usually wants "a free run of 2,000 blocks, near block 1,000,000", which needs both orders. A bitmap answers neither question without scanning.

XFS packs an extent into 16 bytes: 1 bit for "unwritten", 54 bits of file offset, 52 bits of start block and 21 bits of length. Per-AG trees use 32-bit block pointers relative to the start of the AG, which gives them more entries per block than trees that need full 64-bit pointers. Every tree block on a modern (v5) XFS also carries a CRC, its own block number, the owner's identity and the UUID of the filesystem, so a block written to the wrong place or belonging to another file is detected when it is read. Blocks at every level have left and right sibling pointers.

btrfs: copy-on-write B-trees

btrfs builds the whole filesystem from one kind of B+tree, after a design by Ohad Rodeh (B-trees, Shadowing, and Clones, 2008). Every piece of metadata is an item with a 17-byte key:

struct btrfs_disk_key {
        __le64 objectid;
        __u8   type;
        __le64 offset;
} __attribute__ ((__packed__));        /* 8 + 1 + 8 = 17 bytes */

Keys sort by objectid, then type, then offset. Everything about one file has the file's inode number as its objectid, so it all sorts together:

KeyItem
(257, INODE_ITEM 1, 0)the inode: size, mode, times
(257, INODE_REF 12, 256)its name in parent directory 256 (the back pointer)
(257, XATTR_ITEM 24, hash)an extended attribute
(257, EXTENT_DATA 108, 0)file offset 0 lives in this disk extent
(256, DIR_ITEM 84, hash(name))directory 256 has this name: used for lookup
(256, DIR_INDEX 96, seq)the same name by creation sequence: used for readdir

btrfs stores each directory entry twice, keyed two ways, for the same reason XFS keeps two free-space trees. There are separate trees for different jobs: the root tree (which lists the others), the extent tree (who uses which disk space), the chunk and device trees (how logical addresses map to devices), the checksum tree, the free space tree, and one filesystem tree per subvolume. A leaf holds an array of 25-byte item headers growing from the front and the item bodies growing from the back. An internal node holds 33-byte key pointers (key, block, generation). With the default 16 KiB nodes and a 101-byte node header, that is (16384 − 101) / 33 = 493 children per node.

Never overwrite

btrfs never modifies a tree block in place. To change one item, it writes a modified copy of the leaf somewhere free. The leaf's parent must now point at the new address, so the parent is copied too, and so on up to the root. Finally the superblock is updated to point at the new root. Until that write, the old tree is complete and intact on disk, and after it the new tree is. This is the atomic root switch from the end of lesson 03.

Several consequences follow directly from the picture:

  • Snapshots are cheap. A snapshot is a new root that points at the same nodes. Nothing is copied until one side changes something. The extent tree keeps reference counts so a block is freed only when no tree points at it. Rodeh's paper is about doing that counting lazily, so that taking a snapshot does not mean touching every block.
  • No sibling pointers. If leaves were linked, rewriting L3 at a new address would mean rewriting L2 (which points at it) and L4 (which it points at), whose neighbours would then need rewriting too. COW trees therefore have no leaf links. A range scan goes back up through the parent to find the next leaf.
  • Self-checking pointers. Each key pointer records the generation (transaction number) of the child it expects, and each block carries a checksum. A lost write or a block written to the wrong place shows up as a mismatch on the next read.
  • Write amplification. Changing one byte rewrites a whole path of 16 KiB nodes. btrfs amortises this by batching changes into transactions, committed every 30 seconds by default, and handles fsync() with a separate per-subvolume log tree so it does not have to commit everything.

Databases: the same tree with a different page

Databases call their nodes pages, but the structure is the one you have just seen. Three popular engines make three different choices:

EnginePageWhere the rows liveNotable
MySQL InnoDB16 KiBIn the leaves of the primary-key B+tree (a clustered index). The table is the tree.Secondary indexes store the primary key in place of a disk address, so a lookup through one walks two trees.
PostgreSQL8 KiBIn an unordered heap file. Index leaves hold (key, block, offset) tuple IDs.Its B-tree implements Lehman and Yao's B-link tree (see the concurrency section).
SQLite4 KiB by defaultIn the leaves of a B+tree keyed by a 64-bit rowid ("table b-tree").Each index is a separate B-tree whose keys are the indexed columns plus the rowid ("index b-tree").

A million rows, three levels, as the arithmetic predicted. The fanout lesson shows up too. The table's internal pages hold about 395 entries, because their keys are small integers. The index's internal pages hold about 141, because each of its keys is a 12-character string plus a rowid. Bigger keys mean lower fanout, which is why database people care about short index keys, and why PostgreSQL truncates separator keys to the shortest prefix that still separates (suffix truncation).

When a B-tree is the wrong answer: LSM trees

A B-tree updates in place. Every insert eventually rewrites a leaf somewhere random on the device, and a database also writes the change to its log first. For workloads that are mostly small writes, such as metrics, message queues or object metadata, that random write is the bottleneck.

The log-structured merge tree (LSM tree; O'Neil, Cheng, Gawlick and O'Neil, 1996) never updates in place:

Writes become sequential and batched, which suits both hard disks and the flash translation layer of SSDs. The price is paid elsewhere:

B+treeLSM tree

Spacepages partly empty (about 69% full)old versions linger until compaction
Range scanwalk the leavesmerge iterators over all levels
Used inext4, XFS, btrfs, InnoDB, PostgreSQL, SQLiteRocksDB, LevelDB, Cassandra, Ceph BlueStore metadata

The last row matters for lesson 09. Ceph's BlueStore writes object data directly to a raw block device and keeps all of its metadata (which object lives in which extents, checksums, object attributes) in RocksDB, an LSM tree, running on a small internal filesystem called BlueFS.

Many threads, one tree

A split changes a node and its parent, and possibly the parent's parent, while other threads may be descending through those very nodes. Three techniques cover most real systems.

  • Latch coupling (also called crabbing). A short-term lock on an in-memory node is called a latch. A thread latches the child before releasing the parent, like a crab moving hand over hand. An inserter keeps the ancestors latched until it reaches a node with room to spare, which cannot split, and then releases everything above it.
  • Optimistic descent. Most inserts do not split anything: with 340 entries per node, roughly one insert in 170 splits a leaf. So a thread descends with shared latches, takes an exclusive latch only on the leaf, and starts over the slow, careful way only in the rare case where the leaf must split.
  • B-link trees (Lehman and Yao, 1981). Every node gets a link to its right sibling and a high key, the upper bound of its key range. A reader that arrives at a node just after it split sees that its key is above the high key and follows the right link to the new sibling. Readers then need no latch coupling at all. PostgreSQL's B-tree is built this way, and its README walks through the details.

The filesystems use coarser locks. ext4 protects each file's extent tree with a per-inode read/write semaphore, i_data_sem. XFS locks the per-AG header blocks while it changes that AG's trees, so allocations in different AGs proceed in parallel; that is a large part of why XFS scales on big machines. btrfs takes read/write locks on individual tree blocks, and copy-on-write helps it further: the committed tree never changes, so it is always safe to read.

B-trees in RAM, too

The cost model has a second, smaller version inside the computer. A CPU reads memory in 64-byte cache lines, and a cache miss to RAM costs around 100 ns, during which a modern core could have executed hundreds of instructions. A binary tree with one key per node takes one cache miss per level. So the kernel is moving toward wide trees in memory as well:

  • The maple tree, merged in Linux 6.1, stores each process's memory mappings. Its nodes are 256 bytes (four cache lines) and hold up to 16 ranges each on 64-bit machines, and it supports lookups under RCU without locks. It replaced a red-black tree plus a linked list.
  • The XArray that indexes the page cache (lesson 05) is a radix tree with 64 slots per node, keyed by page index within the file.
  • ext4's extent status tree, the cache of extents mentioned above, is a red-black tree per inode. Small, frequently changing sets still suit binary trees.

Check yourself

A tree has 4 KiB nodes with no header and 16-byte entries. How tall is it for 100 million keys?

Fanout 4096 / 16 = 256. 2563 ≈ 16.8 million is too few and 2564 ≈ 4.3 billion is enough, so height 4. Level by level from the leaves: 390,625 leaves, 1,526 nodes, 6 nodes, 1 root.

Why does a B-tree grow by adding a new root instead of adding a level of leaves?

Splitting the root and putting a new root above it moves every leaf down by one level at the same moment, so all leaves stay at the same depth. Growing at the bottom would put some leaves deeper than others.

In a B+tree, why is a separator copied up when a leaf splits, but moved up when an internal node splits?

Every key must remain in a leaf, where its record is, so the leaf keeps its copy and the parent gets another. Separators in internal nodes are only signposts, so the middle one can leave its node entirely.

A file on ext4 has four extents and gains a fifth. What happens to its i_block?

The in-inode root (capacity 4) is full, so ext4 grows the tree in depth. It copies the four extents into a new block, which becomes a leaf with room for 340, and rewrites i_block as an index node with depth 1 and a single entry pointing at that block. The fifth extent then goes into the leaf.

What does the htree gain by indexing hashes of names instead of the names, and what does it give up?

It gains fixed 8-byte index entries (about 500 per block), even distribution regardless of naming patterns, and protection against crafted collisions through the per-filesystem seed. It gives up any ordering by name: no prefix searches, and readdir returns entries in hash order. It also has to handle hash collisions with the continuation bit.

Why can't btrfs link its leaves left to right?

Copy-on-write gives a modified leaf a new address. Its neighbours' links would then point at the old copy, so they would have to be rewritten too, and their neighbours after them, rewriting the whole level. Instead, btrfs goes back up through the parent to find the next leaf.

In Lab 04, a missing name costs 2 block reads with the htree and 20 without. Why does the htree still read 2?

It must read the root to learn which leaf could hold that hash, then scan that leaf to be sure the name is not there. Only a scan of that leaf can prove absence.

You are designing a store that ingests millions of small writes per second and is rarely read. B+tree or LSM tree, and what do you pay?

An LSM tree: writes become sequential appends and batched flushes. You pay in reads, which may have to check several files, in write amplification from compaction, and in space held by old versions until compaction removes them.
